Iridium is an internal documentation platform that merges three things: the vault-and-markdown workflow people know from Obsidian, the simultaneous multi-author editing people expect from Google Docs, and first-class access for AI agents over the Model Context Protocol. A centrally administered server owns the vaults, the accounts and the permissions. Employees read and edit ordinary Markdown in a workspace that runs identically in a hardened desktop application — the supported client at 1.0 — and in a browser. Agents enumerate, read and search the same content through scoped tokens that a user grants and can revoke at any moment.

The source wishlist is `docs/spec/collaborative-markdown-vault-feature-spec.md`. This plan implements it, deviates from it in fifteen places that are each listed and justified, and keeps every one of its deferrals deferred.

## The architecture in one paragraph

One Node 24 process built on Fastify 5 owns all input and output: the REST API under `/api/v1`, the collaboration WebSocket at `/collab` (Hocuspocus 4.7.0 embedded as a library, not a sidecar), the two MCP mounts `/mcp` and `/mcp/connect` (official SDK v2, stateless), Iridium's own OAuth 2.1 authorization server under `/oauth` that the second mount advertises, the attachment routes, the background jobs and the `iridium` command-line tool. MySQL — 8.4 LTS and 9.7 LTS, two required targets with no primary — is the system of record for accounts, memberships, the category tree, note metadata, the authoritative Yjs document state, an append-only update log, revision checkpoints, the hash-chained audit log, integration tokens, OAuth clients, consents and grants, and rebuildable projections. Clients never touch the database or the storage volume. One React codebase serves both the browser host and the Electron 44.3.0 shell through a single platform seam, so there is one UI to build and one UI to test; the Electron application is Iridium's supported client at 1.0. A reverse proxy terminates TLS.

## The decisions that shape everything else

- **Saved means committed.** A note is "Saved" only when a MySQL transaction containing that user's edits has committed and the server has broadcast a state vector that dominates the client's entire local vector and a canonical delete-set fingerprint equal to the client's. Connectivity and server memory are never enough. This is enforced by a per-note writer queue with a compare-and-swap on the note's head sequence, and proven by a test that kills the process immediately after the acknowledgement.
- **One authorization core.** A single `authorize()` function over a single `Principal` union serves REST, the WebSocket and MCP alike. Knowing an identifier grants nothing: non-members receive 404 for every vault-scoped resource. Revoking a role or a membership reaches already-open sessions through version epochs and an in-process bus, not just the next login.
- **Agents read committed content, never live CRDT state.** A shared read core returns Markdown at a named revision, so an agent and a person always see a coherent document. Tokens carry explicit scopes intersected with the owner's live role, a vault allowlist, a mandatory expiry, per-token rate limits and a per-call access log that records which notes were read. Two credentials reach the same six tools — integration tokens at `/mcp`, OAuth access tokens at `/mcp/connect` — one kind per mount, because discovery is a property of a URL and not of a request.
- **The Yjs state is authoritative and is never rebuilt from Markdown.** A document is initialized once, then loaded from its persisted binary state. Markdown is the readable text inside that state, plus rebuildable projections for search, outline and links.
- **Markdown source is preserved byte for byte.** Line endings and byte-order marks are normalized once at import and restored on export from recorded metadata, because the editor and the CRDT disagree about `\r\n`. Obsidian-specific syntax is detected, reported and indexed, never silently reinterpreted.
- **Rendered notes are untrusted content.** Sanitization happens on the parsed tree as the single security boundary, parsing runs in workers under hard caps, and the desktop shell exposes no Node capability to note content.
- **Everything has a limit.** One limits table governs payloads, document sizes, queue depths, rate limits and the loaded-document budget; the server refuses work past the budget rather than degrading silently.
- **Two MySQL lines, both required.** Every statement Iridium executes must have identical semantics on MySQL 8.4.11 and MySQL 9.7.2 — the migrations, every query Kysely builds, every raw `sql` template, the container init scripts and every client command line the runbooks print. 8.4.11 is the floor that an unset image selector resolves to, both lines are merge-blocking CI lanes rather than a nightly courtesy, a construct that requires 9.x or that 8.4 merely deprecates is forbidden, and MySQL 8.0 is end of life and is refused at boot.
- **One UI codebase, one supported client.** The same React application runs in the browser and inside the Electron shell behind a single host seam, exactly as the brief requires. At 1.0 the desktop application is the supported client; the browser host is the development and internal surface the UI is built and tested on, running on current Chrome and Edge. Firefox and WebKit are out of scope.
- **The desktop client ships unsigned at 1.0, and the plan says what that costs.** A zipped bundle per operating system, a published SHA-256 beside it, and a documented first-launch procedure for each platform. Code signing, installers and in-application updates are a post-1.0 epic whose every seam ships now, so it is a configuration change rather than a redesign — and because no installed client records a publisher identity yet, that epic gets to choose one cleanly, which is the one part of this decision that cannot be taken back later.

## Milestone sequence

Ordering only. Each milestone exits when its named automated tests pass, and no milestone carries a time or effort estimate.

## Decisions you made

Answered by the project owner on 2026-09-12 (G1–G8) and 2026-09-24 (G9–G12). Each row records the answer and where the consequence lives in the plan. Of the answers of 2026-09-12, four changed the plan — G1, G3, G6 and G8 — and four confirmed the default it already carried — G2, G4, G5 and G7. All four answers of 2026-09-24 changed settled decisions, so each is an Area 9 ADR of `13-decision-log.md`, AG9–AG12 (D13-13). §G of `14-risks-and-open-questions.md` is the one full record of every question: the owner's words, the reading applied, the assumptions a reading rests on, the section that now owns each consequence and the commit that encoded each answer.

| # | Question | Decision |
|---|---|---|
| G1 | Must claude.ai and Claude Desktop custom connectors work natively at launch, rather than through the bundled bridge? | **Yes.** Iridium ships its own OAuth 2.1 authorization server. Connectors sign in at `/mcp/connect`; token headers keep working unchanged at `/mcp`; the bundled bridge stays for stdio-only clients and intranet-only sites. The flow lands in M3; real connectors complete it before M4 exit (AG9) — `06-mcp-and-agent-access.md`, `04-auth-and-access-control.md`, `03-data-model.md`, `09-api-reference.md`. |
| G2 | Should Obsidian syntax render read-only at launch? | **No** — the default stands. Obsidian syntax is detected, reported and indexed in `note_links` now; the `markdown_flavor` column and the renderer plugin seam stay reserved, and wikilinks, callouts, highlights and comments render as literal text. `08-markdown-pipeline-import-export.md`. |
| G3 | Is MySQL 8.4 a required target alongside 9.7? | **Yes — both are required.** MySQL 8.4 LTS and 9.7 LTS are equal supported targets with no primary; 8.4.11 is the compatibility floor and both run as merge-blocking CI lanes. MySQL 8.0 is end of life and is refused at boot. *(Assumption: "MySQL 8" is read as 8.4 LTS — see `14-risks-and-open-questions.md` §G.)* |
| G4 | Application-level attachment encryption, or volume and database encryption only? | **Volume and database encryption only** — the default stands. The envelope-encryption columns on `attachments` stay reserved, and the posture is documented rather than implemented. `11-operations-and-deployment.md`, `03-data-model.md`. |
| G5 | CJK search at launch? | **No** — the default stands. The default InnoDB full-text parser with a two-character minimum token, no ngram parser and no second index. The parser choice is frozen at M0 either way, which is why the row is recorded rather than dropped. `03-data-model.md`. |
| G6 | Firefox and WebKit as supported targets at 1.0? | **The desktop application is the supported client at 1.0.** The web host keeps running on current Chrome and Edge as a development and internal surface; Firefox and WebKit are out of scope, with no best-effort claim. `07-client-applications.md`, `10-testing-and-quality.md`. |
| G7 | Publish the MCP bridge to the public npm registry? | **No** — the default stands. The bridge is bundled with the desktop application and downloadable from the server. With G1 answered yes it is no longer the required route for Claude Desktop: it serves stdio-only clients, air-gapped and intranet-only sites, and scripted use. `06-mcp-and-agent-access.md`. |
| G8 | Windows installer formats, managed-fleet update policy, and who owns the signing identities? | Not in the first release. 1.0 ships unsigned zipped application bundles per operating system with a published SHA-256 for each, downloaded from your own server; there is no installer and no in-application update. Signing, installers and automatic updates are one post-1.0 epic, and the seams for it ship in 1.0. The consequences are stated plainly in `07-client-applications.md` §7.14 — first-launch warnings on Windows and macOS, macOS quarantine, a macOS sign-in on every launch, and update integrity resting on the checksum and the connection rather than on a signature. |
| G9 | Must real claude.ai and Claude Desktop connectors complete the OAuth flow before M3 exits (spike S15), although no M3 build serves a browser sign-in page? | **No — the real-connector proof moves to M4 exit.** M3 exits on the scripted OAuth client: `oauth.authorization-code.integration` signs in through `POST /auth/sessions`, consents to two vaults on the server-rendered page and reads a note through `/mcp/connect`, in both registration kinds: the client ID metadata document variant in-process only (D06-44), and dynamic registration, which runs again against the production-mode exit image. A production-mode CIMD run needs a publicly hosted client metadata document and is the AG10 nightly row due at M8. Spike S15, the real-connector deliverable and the connector-product behaviours run before M4 exit, against the M4 exit build on a publicly reachable HTTPS staging origin. Until a build serves a browser sign-in surface, `/oauth/authorize` answers a browser with no session with the `access_denied` error redirect, never a redirect to a route the server does not serve. AG9 — `06-mcp-and-agent-access.md`, `07-client-applications.md` §3.2, `12-milestones.md`, `14-risks-and-open-questions.md`. |
| G10 | Must S9 and the nightly real-client matrix drive the GUI clients — VS Code, Cursor, Windsurf, Claude Desktop — and block M3, although they cannot be driven headlessly and neither a public staging origin nor model credentials exist yet? | **No — real-client observation at M3 is headless.** S9 runs before M3 exit as a run of `nightly.yml › mcp-clients`, which drives the Claude Code CLI, `mcp-remote`, the `iridium-mcp` bridge, the SDK client, `curl` and the scripted OAuth clients over real TLS; the job is advisory from M3 to M7 and a gate at M8. GUI clients are observed by hand in `docs/acceptance/mcp-gui-clients.md` before M4 exit and again against the M8 release candidate. AG10 — `06-mcp-and-agent-access.md`, `10-testing-and-quality.md`, `11-operations-and-deployment.md` (the in-process TLS profile, live from M3), `12-milestones.md`. |
| G11 | May the MCP conformance suite and Inspector, which bundle SDK v1, be installed from the registry, and how do `mcp-remote` and the Claude Code CLI reach the real-client matrix? | **Yes, in a dev-only leaf, with registry egress approved for the install.** `@modelcontextprotocol/conformance` 0.1.16 and `@modelcontextprotocol/inspector` 2.6.0 return to the catalog, declared only by `tooling/mcp-conformance` (tag `harness`), the one workspace in which SDK 1.x may resolve. `mcp-remote` and the Claude Code CLI never enter the workspace: a committed client lockfile outside every workspace glob pins them, and only `nightly.yml` installs it. AG11 — `02-system-architecture.md`, `06-mcp-and-agent-access.md`, `10-testing-and-quality.md`, `12-milestones.md`. |
| G12 | Should M3's settings store and `/admin/settings` carry all seven settings groups, or only those M3 code honours? | **Only the groups M3 code honours.** The M3 `SettingsStore` and `GET` and `PUT /admin/settings` carry `mcpEnabled`, `patPolicy` and `oauthPolicy`. `sessionPolicy`, `passwordPolicy`, `retention` and `desktopUpdatePolicy` arrive at M7, each in the change that rewires its consumers, which read the environment until then; a `PUT` naming one of them at M3 is refused with 422. AG12 — `02-system-architecture.md`, `03-data-model.md` §13.1, `09-api-reference.md` §2.15.3, `12-milestones.md` §7 and §11. |

## Open questions

One question is open. It was raised on 2026-09-24, and its working default is encoded in named artefacts, so that the answer is a change of encoding rather than a redesign (D14-04). Its answer is due at M4 entry, the milestone whose work it changes (D12-7). The register check fails an open row once the effective test target reaches its due milestone, which first happens at that milestone's exit rehearsal, so CI enforces the answer there. If M4 begins with the question unanswered, D12-7 applies: the working default stays, the alternative becomes a post-MVP item, and before M4 exit the row moves to *Decisions you made* and to §G's answered table with the applied default recorded in place of your words, as the M4 exit record also states. An answer moves the row to *Decisions you made* in the commit that inverts or removes the encoding. §G of `14-risks-and-open-questions.md` is the one full record: its open table carries the question, the reason for asking, the working default with its encoding, and the recommendation.
