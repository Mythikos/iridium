# Requirements traceability

This section is the matrix that ties every normative statement of the project brief and of the feature spec, plus the five hard properties the plan adds on top of them, to the part of the plan that specifies the mechanism, to the named automated tests that prove it, and to the milestone that retires it. It is the inverse index of the rest of the plan: the other fourteen sections say how Iridium works, this one says where each requirement went and what will fail if it regresses.

Read a row left to right. **Requirement** is one normative statement, split out of its source sentence so that a row is either satisfied or not — compound requirements are separate rows. **Source** is the exact place the requirement comes from (`brief item 5`, `spec §4 para 3`, `spec §9 row 'Durable saving'`, `spec §10 deferral`, `plan hard property` for the plan's own stricter properties, or `owner answer to G<n>, 2026-09-12` for a requirement the project owner's answers to 14-risks-and-open-questions.md §G created). **Covered by** names the plan file and the heading that specifies the mechanism — not a summary of it, the heading to open. **Tests** names the automated tests, verbatim from the inventory of 10-testing-and-quality.md; where a test's own case list contains the assertion, the case is named in parentheses. **Milestone** is the milestone of 12-milestones.md at which the row turns green. **Status** is one of three values.

- **covered** — a mechanism is specified under a named heading *and* at least one named automated test verifies it.
- **partial** — the mechanism is specified but the test is missing, names an assertion weaker than the requirement, or only part of the requirement is covered.
- **missing** — no mechanism in the plan.

A status cell may carry a parenthetical qualifier — `covered (both lines merge-blocking)` — where the strength of the evidence is itself the point. The qualifier narrates the evidence; it never changes which of the three values the row counts as in the Summary.

**A requirement with no named test is recorded as partial, never as covered.** Design prose is not evidence: a statement that something is impossible, a non-goal list, or a manual review gate at a milestone exit all leave a row partial, and the Gaps section below says what each one needs. "none" in the Tests column means the test inventory of 10-testing-and-quality.md carries no name for that requirement — not that a test exists somewhere unnamed. Every test name in this matrix resolves to an entry in that section's inventory; a name cited elsewhere in the plan but absent from the inventory is an undefined reference that `scripts/check-test-name-references.ts` fails on, and it is recorded as a gap rather than copied here as evidence.

No requirement of the brief or of the spec is unaddressed by the plan: there are no `missing` rows. The 16 partial rows are enumerated with their closing actions in "Gaps" below. Four of them are absences that are not mechanically testable at all and are recorded as review-only; the other twelve are specified mechanisms whose named test is missing or asserts something weaker than the requirement, and none of the sixteen sits on a spec §9 acceptance row.

**No deferral or non-goal row is partial any more.** The twelve rows that prose alone used to hold — graph view, per-note or per-category permission overrides, mobile clients, enterprise single sign-on, multi-server collaboration, offline-first editing, cross-vault moves, automatic cross-document link rewriting, full Obsidian syntax compatibility, built-in AI features, "not a complete Obsidian replacement" and "no second content write path" — are now held by `guards.non-goals.guard`, which asserts one absence per `NonGoalId` against the built route, MCP, CLI, client-capability, schema and dependency inventories (10-testing-and-quality.md § The non-goal guard). Two deferral rows arrived later, with the owner's answers of 2026-09-12, and neither was ever partial: browsers outside current Chrome and Edge (G6) and signed desktop installers, MSIX and in-application updates (G8). Each was declared with its guard case already written — `guards.non-goals.guard` for both, joined by `desktop.artifact-names.guard` for the packaging row's artefact vocabulary — so the category is empty at fourteen rows rather than at twelve. **No spec §9 acceptance row is discharged by a manual record**: the three desktop rows that `docs/acceptance/host-parity.md` used to carry are `desktop.viewer-readonly.e2e`, `desktop.revocation-while-open.e2e` and `desktop.durable-save.e2e`, and that checklist is reduced to the route-and-command reachability walk, which is named in no `docs/acceptance-map.json` entry (12-milestones.md § 13.4).

### Acceptance rows (spec §9)

vault's revision history" — is closed by the named case *foreign-vault revision history*, added to
`authz.vault-isolation.integration` and to `mcp.isolation.mcp`. The case exists because a route
enumeration structurally cannot reach it: three of the history-bearing surfaces are query
parameters (`?revision=`, `?includeTrashed=true`) on routes the enumeration already calls without a
query string, so the enumerated call exercises `note:read` and never reaches `history:read`. The
case calls all seven `history:read`-gated REST surfaces, and the four agent-facing ones, as an
outsider against a vault seeded with a named revision and a restored revision, and requires `404`
rather than `403` on every one, since `403` would confirm the note exists and breach deviation F13.

over a union in `@iridium/contracts/authz.ts`, so a new history surface without a case does not
compile.

## How this matrix is maintained

This matrix is prose, and prose rots. What keeps it honest is that every test name in it is also a
key of a generated build artefact, and that the artefact is checked by tests rather than by reading.

`scripts/build-acceptance-map.ts` generates `docs/acceptance-map.json` from
10-testing-and-quality.md — the four inventories (the nine acceptance rows, the five hard properties,
the guards, and the server/client/E2E suites) plus the two "Inventory completeness" tables — as the
last step of `pnpm gen`. The generated file is committed, so `gen.drift.guard`
(`pnpm gen && git diff --exit-code` in the `static` job) fails whenever a prose table and the
committed JSON disagree. `guards.acceptance-map.guard.spec.ts` then reads that JSON, the milestone
named in `docs/milestones/CURRENT`, and the `[spec:<row-id>]`, `[hp:HP-n]` and `[area:<name>]` tags
of every `*.spec.ts[x]` file, and fails when a due layer has no test, when a test claims a row id or
hard-property id the map does not list, when a file under `apps/e2e/` or `apps/server/test/` carries
no requirement tag, or when a `hostContractCases()` case has not passed in every due harness.

The link from that machinery to this section is `scripts/check-test-name-references.ts`, also a
`static`-job step: it greps every markdown file under `plan/` and `docs/` for the
`<area>.<subject>.<layer>` pattern and fails on any match that is not a key of
`docs/acceptance-map.json`, printing the canonical spelling when the match is a superseded variant.
`plan/15-requirements-traceability.md` is one of the files it greps. A test rename therefore breaks
the build in the commit that renames until this matrix is updated with it, and a test name invented
here — for a test that does not exist — fails the same job. That is the whole anti-drift contract:
the Tests column cannot describe tests the repository does not have.

Four rules follow from that, and they are the review checklist for any change to this section.

1. **A row moves to `covered` in the same pull request as the test that earns it.** The sequence is:
   add the test, add its entry to the inventory of 10-testing-and-quality.md, run `pnpm gen` so
   `docs/acceptance-map.json` carries it, then change the status here. Doing it in the other order
   fails `check-test-name-references.ts`.
2. **A row may not name a test to describe an intention.** If the requirement has no test, the row is
   `partial`, the Tests column reads "none" or names only what is genuinely asserted, and the Gaps
   section carries the closing action. Removing a gap bullet without adding the test is a regression
   of this section, not a tidy-up.
3. **The Milestone column agrees with the map's milestone axis.** `docs/milestones/CURRENT` is the
   single place the open milestone lives, and each `(rowId, layer)` entry of the map carries a
   `sinceMilestone`. A row whose milestone has arrived while its status is still `partial` is either
   closed or converted into a recorded deferral with a decision in 13-decision-log.md — it is never
   left to drift.
4. **Milestone exit reads this section alongside 12-milestones.md.** The exit criteria of a milestone
   list the tests that must be green; this matrix is what says which requirements those tests
   discharge and which requirements the milestone leaves open. A milestone exits with partial rows
   only when each of them appears in Gaps with a closing action.

When the acceptance map gains a row id or a hard property, this section gains the rows it covers in
the same change; when a gap here closes, the bullet is deleted and the Summary counts are recomputed.
The counts at the top of this section are therefore a statement about the repository at the commit
that carries them, not an aspiration.
