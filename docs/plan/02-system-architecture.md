# System architecture

This section is the implementer's map of Iridium: which processes exist, what runs inside each, how a request or a WebSocket connection travels through the server, how the repository is cut into packages, how the server is configured, which limits apply everywhere, which in-process singletons sit behind interfaces, and the conventions every module shares (identifiers, error envelope, versioning, logging). Data-model detail is in 03-data-model.md, the authentication and authorization rules in 04-auth-and-access-control.md, the persistence protocol in 05-collaboration-and-durability.md, the MCP surface in 06-mcp-and-agent-access.md, the clients in 07-client-applications.md, the markdown pipeline and transfer jobs in 08-markdown-pipeline-import-export.md, the wire contracts in 09-api-reference.md, the test names in 10-testing-and-quality.md, deployment in 11-operations-and-deployment.md, and the delivery order in 12-milestones.md. This section names those mechanisms and shows where they sit; it does not restate them.

Two reference conventions are used throughout. Identifiers of the form `A19` name a plan-wide settled decision and `F9` a deliberate deviation from the feature spec; both are catalogued in 13-decision-log.md. `§G-4` names one of the questions in section G of 14-risks-and-open-questions.md. The project owner answered G1–G8 on 2026-09-12 and G9–G12 on 2026-09-24 (the latter recorded as AG9–AG12; this section cites AG11 and AG12), so a `§G-n` reference in this section names a recorded decision and its consequences. G13 is the one open question, with its answer due at M4 entry, and nothing in this section depends on it. Identifiers of the form `ARCH-05` are decisions taken in this section and listed at its end.

## Architectural summary

Iridium is a single-server, multi-client system:

- **One server process** (`@iridium/server`, Node 24.21.0, Fastify 5.12.4) owns every I/O path: the REST API at `/api/v1`, the collaboration WebSocket at `/collab` (Hocuspocus 4.7.0 embedded as the `Hocuspocus` class), the MCP surface mounted twice at `/mcp` and `/mcp/connect` (`@modelcontextprotocol/server` 2.0.0 through `@modelcontextprotocol/fastify` 2.0.0), the OAuth 2.1 authorization server at `/oauth/*` with its metadata documents under `/.well-known/`, the static web bundle at `/app/*`, the desktop update feed at `/desktop/updates/*`, the operational endpoints `/healthz`, `/readyz`, `/metrics`, the in-process job scheduler, and the `iridium` operator CLI (same binary, different sub-command).
- **MySQL 8.4 LTS or MySQL 9.7 LTS** (`mysql:8.4.11` and `mysql:9.7.2-oraclelinux9`) is the only system of record — two required deployment targets, neither primary, every schema statement, query and operational procedure identical on both (§G-3): accounts, memberships, hierarchy, metadata, persisted Yjs state, the per-update durability log, revisions, audit and access logs, jobs, settings, and the rebuildable projections (Markdown text, search index, link index).
- **Attachment storage** is a content-addressed blob store behind `StorageDriver` (`fs` on a persistent volume by default; `s3` optional).
- **Caddy 2** (or nginx) terminates TLS in front of the server; an air-gapped profile lets Fastify terminate TLS itself.
- **Two client hosts, one UI**: `@iridium/web` (a Vite 8 entry served by the server) and `@iridium/desktop` (Electron 44.3.0: hardened main process, sandboxed preload, renderer loading `app://iridium/`) both mount the same `@iridium/ui` React application through the single `IridiumHost` seam. The two hosts carry different commitments and identical mechanisms: the desktop application is the supported client at 1.0 and the web host is a development and internal surface (§G-6, 01 §4.6, ARCH-29).
- **Agents** reach the server over Streamable HTTP on one of two mounts of the same MCP surface. `/mcp` accepts an integration token (`irid_pat_…`) and advertises no discovery: Claude Code, Cursor, VS Code, Windsurf, the Messages API connector, `curl`, CI jobs and the first-party stdio bridge `iridium-mcp` (`@iridium/mcp-bridge`) use it. `/mcp/connect` accepts an OAuth access token (`irid_oat_…`) issued by Iridium's own OAuth 2.1 authorization server and advertises discovery: the native claude.ai and Claude Desktop custom connectors use it. The bridge stays for stdio-only clients, air-gapped sites and scripted use; it is no longer the required path for Claude Desktop (§G-1, §G-7).

Three properties shape everything below:

1. **One process, many seams.** The MVP runs exactly one server process (spec §6), so live revocation, ticket consumption, rate limiting, the loaded-document set and the per-note persistence FIFO are all in-process and therefore exact. Each of those singletons sits behind an interface with an in-memory or MySQL implementation now and a documented Redis-backed replacement later (skeleton F9).
2. **One decision function, one read model.** Every surface (REST, WebSocket hooks, MCP tools, jobs, CLI) authenticates through `authenticate()` and authorizes through `authorize()`; every human and agent read of committed content goes through `ContentReadCore`. There is no second permission path and no second read path.
3. **Contracts first.** `@iridium/contracts` (zod 4.6.2) is the only package every other package depends on. REST DTOs, the `ProblemDetails` envelope, identifiers, the permission matrix, token formats, limits, collaboration stateless messages, MCP tool I/O, desktop IPC channels, import reports, export manifests and the audit vocabulary are defined there once; OpenAPI 3.1, the MCP tools schema, the API client types and the IPC typings are generated from it and diff-checked in CI (skeleton A3).

### Boot sequence and plugin order

`apps/server/src/main.ts` is the CLI entry (`serve | migrate | doctor | config | backup | restore | audit | reindex | admin | tokens | sessions | keys | jobs | trash | desktop-updates | mirror | oauth | access-log | repair | version`). `serve` calls `buildApp({ mode: 'container' })` from `apps/server/src/app.ts`; the integration harness calls `buildApp({ mode: 'in-process' })`; the chaos harness spawns the same binary with `serve --child` and calls `buildApp({ mode: 'child' })`. The three modes share one plugin tree and differ only in listening, signal handling and whether the scheduler starts. Beyond the mode, the only differences between boots are the per-boot injected dependencies `buildApp` accepts — `clock`, `logger`, `limits` and `cimdTransport`. `cimdTransport` substitutes the Client ID Metadata Document transport that the `oauth` plugin otherwise constructs itself (`createCimdTransport()` from `oauth/cimd-transport.ts`, with no argument), and `buildApp` refuses it with `BuildOptionRefusedError` for any mode other than `in-process` or any role other than `server`; `main.ts` and `cli/` never pass it, and `app.ts` imports its type only through the type re-export of `oauth/plugin.ts`. No environment variable, `NODE_ENV` branch or policy field relaxes the CIMD address guard (06-mcp-and-agent-access.md D06-44):

| Mode | Listens | Signals | Scheduler | Fault registry | Used by |
|---|---|---|---|---|---|
| `container` | `BIND_ADDRESS:PORT` | SIGTERM/SIGINT drain | on | never (refused unless `NODE_ENV=test`) | production image, `compose.prod.yaml`, systemd |
| `child` | harness-reserved `PORT` (or `0` for a new ephemeral port), reported on stdout as `{"listening":<port>}` | SIGTERM drain; SIGKILL by the test | on unless `JOBS_ENABLED=false` | `IRIDIUM_FAULT` when `NODE_ENV=test` | `@iridium/testkit startServer({mode:'child'})`, chaos and E2E lanes |
| `in-process` | none (`app.inject()`, `app.injectWS()`, or `listen({port:0})` when a real socket is needed) | none | off by default (`jobs.run(type)` callable directly) | `IRIDIUM_FAULT` | Vitest `integration`, `contract`, `mcp` projects |

**ARCH-02 amendment (2026-09-20):** concurrent HTTP, boot and five-second periodic readiness probes share one serial evaluation; the next call after completion starts a fresh scan. Failed outcomes are not cached across later probes, and an evaluation finishing during drain cannot reopen admission. Fastify's plugin/onReady deadline is explicitly 60 seconds in all modes so the sixteen real checks can finish under CH-16's injected database latency. Listening still follows complete boot. Check thresholds, fail-closed behavior and chaos deadlines are unchanged. See [the ADR](../adr/arch-02-readiness-probe-lifecycle.md). **Noted 2026-09-25:** M3 appends the fail-closed `server_settings` check after `access_log_partitions` (seventeen checks); the lifecycle decided here is unchanged.

The one `Fastify(` construction in `app.ts` sets `return503OnClosing: false`, so a request arriving while the server closes runs the hook chain and is refused by the readiness gate in its path's error envelope (09-api-reference.md D09-30, amended 2026-09-25), never with Fastify's own closing body, which bypasses every hook.

Boot order inside `buildApp` (each step fails fast with a redacted reason and a non-zero exit; nothing listens until the last step):

1. **config** — `config/env.ts` parses `process.env` once with the zod `EnvSchema` (`*_FILE` secrets read, unknown `IRIDIUM_*` keys rejected except the reserved harness namespaces of principle 5, the rejected names of principle 5 refused whatever their prefix, `z.prettifyError` on failure), validates the bridge bundle with `loadToolsBundle` when `IRIDIUM_TOOLS_DIR` is set (a missing, empty or non-regular `iridium-mcp.mjs` is `config.tools_bundle_missing`, a banner version other than `BUILD_INFO.version` is `config.tools_bundle_version_mismatch`, both exit 2; 11-operations-and-deployment.md OPS-65), produces the frozen `IridiumConfig` object and logs the redacted summary. `iridium config check` stops here.
2. **db** — creates `dbApp` and `dbPersist` (Kysely 0.29.5 over mysql2 3.24.4), pings both, asserts the connection flags include `FOUND_ROWS` (skeleton A10), asserts the server version is `8.4.x` (≥ 8.4.11) or `9.7.x` (≥ 9.7.2) from `SELECT VERSION()` and exits `2` with `config.mysql_unsupported` otherwise, unless `IRIDIUM_ALLOW_UNTESTED_MYSQL=true` downgrades it to a logged warning and a permanent `/readyz` `mysql_version: warn` (11-operations-and-deployment.md OPS-60), asserts `innodb_flush_log_at_trx_commit = 1` (fatal when `READYZ_STRICT_DURABILITY=true`, warning otherwise), verifies the migration head from `kysely_migration` against the bundled migration list (when `IRIDIUM_MIGRATE_ON_BOOT=true` the pending migrations are applied here through the migrator wrapper under `DATABASE_MIGRATE_URL`; otherwise the process boots into the not-ready state described below and re-checks every 5 s), runs the Yjs single-instance guard (fails on "Yjs was already imported"), and loads `schema_meta` (`api_version`, `min_client_version`, `pepper_version`, `audit_key_version`, `cursor_key_version`, `pipeline_version`). Immediately after the `db` plugin, `app.ts` runs `applySettingsPlugin` (`settings/plugin.ts`, ARCH-31), which constructs the `SettingsStore` (`settings/store.ts`), decorates `app.settings` and registers the fail-closed `server_settings` readiness check, but does not load the store: the check performs the first load once the `migrations` check has recorded a state the process may serve, reading `schema_meta` `server_settings_version` and every `server_settings` row in one read-only `REPEATABLE READ` transaction — strictly when the status is `current`, and tolerantly when `IRIDIUM_ALLOW_NEWER_SCHEMA` tolerates a newer schema (groups this binary does not know are ignored, unknown members of known groups are stripped, known members are still validated strictly, and `settings.newer_schema_tolerated` is logged once per process) — and in database mode `none` it installs the empty row set at version 0 and reports `ok`. Until that load succeeds `effective()` throws `SettingsNotLoadedError` and the check fails with the cause in its detail — waiting for the database or for migrations, a newer schema not tolerated, a missing or regressed validator, a redacted load failure, or an invalid row or unknown key with its remedy; after it, each readiness evaluation refreshes the store when the validator has advanced, and a refresh that cannot complete keeps the installed snapshot and reports `warn`. Settings rows are database state and never stop the boot: an invalid row keeps the check failing instead. The first evaluation runs before the process leaves `starting` (see "Not-ready gating"), and no boot step reads the `SettingsStore` (ARCH-10).
3. **security** — `@fastify/helmet` 13.1.1 with a per-response CSP nonce, `@fastify/cookie` 11.1.2, `@fastify/multipart` 10.1.1, `@fastify/under-pressure` 9.1.0; request-path classification in `security/paths.ts` (`requestPath` — the matched route's pattern, otherwise the raw URL cut at the first `?` or `#` — and `isOpsPath`, `isMcpPath`, `isOAuthClientPath`), which every path rule reads; the Host guard (`Host` must be present, of the form `uri-host [":" port]`, and equal `PUBLIC_HOST`, derived from `PUBLIC_ORIGIN`, under RFC 9110 §4.2.3: the hostname compared case-insensitively and the scheme's default port equivalent to none; `security/host.ts` `isPublicHost`; otherwise 421 `host_rejected`); the routing branch, which answers a URL that matched no route with 405 `method_not_allowed` and `Allow` when another method is registered for the path (found by the concrete-URL `app.findRoute`) or 404 `not_found` otherwise, before body parsing, the body limit, the media-type check, authentication, the CSRF guard and the client-version gate; Origin guard, CSRF guard, `@fastify/rate-limit` 11.2.0 buckets, the request id (the UUIDv7 Fastify's `genReqId` assigns and `requestIdLogLabel` binds as `requestId`; the plugin generates no second id and adopts no inbound one, and logs a trusted proxy's `X-Request-Id` as `upstreamRequestId`, ARCH-14), the error-envelope dispatcher with its `ProblemDetails` renderer (the `oauth-json` and `oauth-browser` renderers are registered by step 7 and the `mcp` renderer by step 10; 09-api-reference.md D09-30) and the not-found handler, `trustProxy` from `TRUST_PROXY`.
4. **auth** — decorates `request.principal`; registers `authenticate()` as an `onRequest` hook, which reads no credential on an MCP path or an OAuth client-endpoint path (`security/paths.ts`; an unmatched URL has already been answered by step 3); wires credentials (argon2id via `@node-rs/argon2` 2.2.1), sessions, the one token verifier `verifyToken` (`irid_pat_` and `irid_oat_`), `TicketStore`, set-password links, login throttling (`rate-limiter-flexible` 11.2.0 `RateLimiterMySQL` on `login_throttle`); constructs the per-credential budget `TokenBudget` from the dedicated `RateLimitStore` and the settings-bound `hourlyDefault` that `app.ts` passes, decorated as `app.tokenBudget`, and registers the ★ REST hook — an instance-level `onRequest` after `authenticate()` that charges a PAT principal on a route whose policy admits tokens, sets the budget headers and marks `request.tokenBudgetCharged`, which the global limiter's `allowList` exempts (04-auth-and-access-control.md D04-37); and constructs the `LastUsedTracker` and its sink (06-mcp-and-agent-access.md D06-49).
5. **authz** — permission matrix from `@iridium/contracts`, `authorize()`, the `AuthzBus` in-process implementation, the epoch table, and the **route-policy boot assertion**: after every route is registered (`onReady`), every route must declare `config.auth`; every mutating route with a cookie-capable principal must be CSRF-guarded unless its path is an MCP or OAuth client-endpoint path (exempt by path) or it is `POST /oauth/consent`, the one route that declares `csrfExempt`; and every MCP route (`POST /mcp`, `POST /mcp/connect`) must carry the MCP-mount arm of `config.auth` (`bearerOnly`, `principalKinds:['token']`, no permission and no `vaultFrom`) with the audience the closed contracts constant `MCP_MOUNT_ROUTES` assigns it (`'pat'` without discovery, `'oauth'` with it — the "one credential kind per mount" rule of 06-mcp-and-agent-access.md). Per-route rules run in `assertRoutePolicies` and registration rules in `assertRouteInventory(routes, {oauthEnabled})`: `/mcp/connect` is registered if and only if `MCP_OAUTH_ENABLED`, every route on an MCP path carries the MCP-mount arm and no route elsewhere does, and the served CSRF-exemption set — the registered non-safe routes the guard exempts — must equal `{POST /mcp, POST /mcp/connect, POST /oauth/consent, POST /oauth/token, POST /oauth/revoke, POST /oauth/register}` while `MCP_OAUTH_ENABLED` is true and `{POST /mcp}` while it is false — a closed enumeration (`CSRF_EXEMPT_ROUTES`, 04-auth-and-access-control.md D04-32, amended 2026-09-25), so a seventh exemption cannot be added silently. The route-policy preHandler is registered for every non-public route except the MCP-mount arm, whose authorization happens per tool call (04-auth-and-access-control.md D04-30, amended 2026-09-25). A violation aborts boot.

12. **jobs** — the scheduler (container and child modes) claims due rows in the `jobs` table with `locked_by = <instanceId>`.

After step 12 the process calls `app.ready()` (which runs the route-policy assertion), then `listen`. `iridium_build_info{version,node,commit}` and `iridium_boot_timestamp` are set at that moment.

#### Not-ready gating

Between `listen` and full readiness the process is alive but must not serve business traffic. `ops/readiness.ts` owns one `ReadinessState` with three values: `starting` (until step 12 completes), `not_ready` (migrations pending, a fail-closed `/readyz` check failing, or draining) and `ready`. The fail-closed checks are exactly `FAIL_CLOSED_CHECKS` in `ops/readiness.ts` — `migrations`, `collab_owner_lease` and, from M3, `server_settings` — and every other check reports without closing admission. The first evaluation (`finishBoot`, run from `onReady`) completes before the process leaves `starting`, so a fail-closed check failing at boot moves it straight to `not_ready`, and no request is admitted before the settings store's first load. While the state is not `ready`, an `onRequest` hook (`applyReadinessGate`, from the ops plugin's module, registered by `app.ts` in step 3 ahead of authentication) answers every route outside `/healthz`, `/readyz` and `/metrics` with 503 `not_ready` and `Retry-After: 5` in the request's error envelope (`ProblemDetails {code:'not_ready', detail}`, the MCP envelope on an MCP path, `temporarily_unavailable` on an OAuth client endpoint; 09-api-reference.md D09-30); `/collab` upgrades are refused with the same status before the WebSocket handshake. The migration re-check runs every 5 s so an operator applying `iridium migrate` from a sidecar brings the server up without a restart (the documented HA procedure in 11-operations-and-deployment.md). The same state machine drives the drain in the shutdown sequence below, which is why there is exactly one place that decides whether the process accepts work.

### Shutdown sequence

On SIGTERM (or `app.close()` in tests) the ops plugin runs the drain within `SHUTDOWN_DRAIN_MS` (20 s). Its hooks run in the phase order `DRAIN_PHASES` lists — `mcp`, `jobs`, `collab`, `writers`, `unload`, `resources` — and `onClose` runs after them (ARCH-06, amended 2026-09-25):

1. `readiness.beginDrain()` (idempotent; the ops plugin's `preClose` hook calls it too, so a `close()` without the ordered drain refuses work the same way) makes `/readyz` return 503 immediately so the proxy and orchestrator stop routing new traffic. The listening socket keeps accepting for in-flight keep-alive requests, but from that moment the readiness gate answers every request outside the ops paths — REST, `/collab` upgrades and MCP calls alike — with 503 `not_ready` and `Retry-After: 5` in its path's error envelope; there is no `draining` code. Fastify's own closing answer is switched off (`return503OnClosing: false`), so no request is answered with a body that bypassed the hooks.
2. **`mcp`** — `closeMounts` (`mcp/plugin.ts`) ends the MCP exchanges already admitted: `handler.close()` writes every `subscriptions/listen` stream its complete frame and ends it, an admitted exchange without a status line answers 503 `not_ready`, a stream under way is ended, and a peer that stops reading is disconnected `MCP_DEADLINE_GRACE_MS` later on the `Clock`, so one client cannot hold the drain to `SHUTDOWN_DRAIN_MS`. The same idempotent routine runs from a `preClose` hook for a `close()` without the drain, because Fastify runs `onClose` only after every in-flight request has finished and an open listen stream never ends on its own.
3. **`jobs`** — The scheduler stops claiming jobs; running import/export jobs are marked `failed` with `error:'shutdown'` and are resumable (import) or re-requestable (export).
4. **`collab`** — Every `note:*` connection receives `{t:'closing', reason:'shutdown', graceMs}`; every `vault:*` connection is closed with `shutdown` (code 4205). After `graceMs` (2 s) all remaining collaboration connections are closed with reason `shutdown`.
5. **`writers`**, **`unload`** — The persistence pipeline drains: every `NoteWriter` queue empties (transactions in flight complete, retries continue with backoff until the deadline); `hocuspocus.flushPendingStores()` awaits every pending compaction (which is truthful because `onStoreDocument` awaits the compaction job, skeleton A16); `hocuspocus.destroy()`.
6. **`resources`**, then `app.close()` — Worker pools are destroyed. `app.close()` then stops the listener, and Node waits for every request already admitted, each appending its `access_log` row at its one append point; after that the `onClose` hooks run, in reverse registration order (avvio runs the last-registered first), so the owning plugins' final flushes of the two in-process write-behind buffers — the `AccessLogWriter` (`audit` plugin) and the `LastUsedTracker` (`auth` plugin) — follow the last admitted request and precede the `db` plugin's pool close (boot step 2). Each flush runs under one deadline, `closeFlushDeadline` = `min(DB_QUERY_TIMEOUT_MS, app.drainRemainingMs() − SHUTDOWN_FLUSH_MARGIN_MS)` (`DB_QUERY_TIMEOUT_MS` alone after a direct `close()` with no drain), applied to connection acquisition and to every statement through `db/query-deadline.ts`'s scoped per-operation deadline: a flush whose deadline is already spent acquires no connection and issues no statement, and one the deadline reaches is cancelled by destroying its connection, so the pool close that follows never waits on it; either way its unconfirmed entries are counted as dropped (`iridium_access_log_dropped_total`, `iridium_token_last_used_dropped_total`) with one `shutdown.flush_abandoned {buffer, dropped}` warning, and the flush never throws. `ShutdownDrain` (`ops/shutdown.ts`) owns the `SHUTDOWN_DRAIN_MS` deadline and exposes the remaining budget as `app.drainRemainingMs()`, which `shutdownServer`'s watchdog reads too. Then pools `dbApp` and `dbPersist` close and the process exits 0. If the deadline expires with a writer still holding un-committed updates, the process exits 1 and logs `persist.drain_timeout` with the affected `noteId`s (exit 1 per the OPS-16 exit-code contract restated in ARCH-22: an unexpected internal condition, not a configuration or verification failure); the durable state is whatever committed, and reconnecting clients recover through the baseline protocol (05-collaboration-and-durability.md).

### The edge

Caddy 2 (pinned tag) is the reference reverse proxy; nginx is documented as an equivalent. Both terminate TLS 1.2+, emit nothing the app does not already emit (HSTS comes from helmet), pass WebSocket upgrades on `/collab` with an idle timeout of at least 120 s, disable response buffering on `/mcp` (`flush_interval -1` in Caddy, `proxy_buffering off` in nginx — the `location /mcp` prefix covers `/mcp/connect` without a second block), pass `Authorization` and leave `Cache-Control` alone on `/oauth/*` and `/.well-known/*`, never answer a `/.well-known/` path themselves (a proxy that serves its own `/.well-known/oauth-protected-resource` re-opens for `/mcp` exactly the client bug the two-mount split exists to avoid, which is why `iridium doctor --oauth` checks the four 404 paths *through* the public origin rather than in process), forward `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Request-Id` (which the server logs as `upstreamRequestId` and never adopts as the request id, ARCH-14), and forward the MCP headers `Mcp-Method`, `Mcp-Name`, `MCP-Protocol-Version` verbatim (a nightly test through the proxied stack asserts it). The server binds `127.0.0.1:4000` and sets `trustProxy` to the proxy's CIDR only; a request whose `Host` is absent or not equal to `PUBLIC_HOST` (the host of `PUBLIC_ORIGIN`, compared under RFC 9110 §4.2.3) is refused with 421 `host_rejected` in its path's error envelope; only the ops routes (`/healthz`, `/readyz`, `/metrics`) are exempt so container health checks can address `127.0.0.1:4000` directly. The air-gapped profile replaces the proxy with Fastify `https: { key, cert }` (HTTP/1.1) and `TRUST_PROXY` unset. Exact configurations are in 11-operations-and-deployment.md.

### Clients

**Web host (`apps/web`).** A ~60-line Vite 8.3.0 entry that constructs a `BrowserHost` and mounts `@iridium/ui`. The bundle is served by the server at `/app/*` from the same origin as the API (`PUBLIC_ORIGIN`), which is why cookie sessions need no CORS and why the CSP can be strict (`script-src 'nonce-…'`, `connect-src 'self' wss:`, `img-src 'self' data:`, `frame-ancestors 'none'`). `GET /` redirects to `/app/` (decision ARCH-07). Routing uses `createBrowserHistory`; the API transport is `FetchTransport` (cookies + `X-Iridium-Client: web`); collaboration uses the browser `WebSocket`; attachments are same-origin cookie GETs. `apps/web` is a development and internal surface at 1.0: it ships in the server image, runs the merge-blocking `chromium` end-to-end lane on every pull request and is how `@iridium/ui` is developed, but the supported client at 1.0 is the desktop application (01 §4.6). Firefox and WebKit are out of scope, and no architecture decision in this section depends on them.

**Electron shell (`apps/desktop`).** Three build outputs: `src/main` (tsdown ESM; owns the session secret through `safeStorage`, performs every REST call through `net.fetch` with the Bearer session, relays collaboration tickets, serves `iridium-attachment://<vault>/<id>`, owns import/export transfers, the updater, deep links and the native menu), `src/preload` (tsdown single-file CJS, sandboxed, exposes fixed `window.iridium` wrappers for the channels in `@iridium/contracts/desktop-ipc.ts`), and `src/renderer` (the shared Vite config with `base:'./'`, loaded from `app://iridium/`, constructing an `ElectronHost` whose `api` is the `IpcTransport`). The renderer never holds a reusable credential. Collaboration normally uses the renderer's `WebSocket` directly against `wss://<server>/collab` with `Origin: app://iridium`; if the M0 Origin spike fails on any OS, the designed fallback `IpcWebSocket` (main opens the socket with `net.WebSocket`, frames relayed over `iridium:collab:{open,send,close}`) is switched on through `host.collab.webSocketFactory`. Hardening and IPC details are in 07-client-applications.md.

**stdio bridge (`packages/mcp-bridge`).** `iridium-mcp --server <origin> [--token-file <path>] [--log-file <path>] [--timeout-ms <n>] [--allow-insecure-http]` (plus `--version` and `--help`; any other argument, `--vault` included, is a usage error, exit 2) runs `serveStdio` from `@modelcontextprotocol/server/stdio`, building a fresh `Server` per factory call over one shared upstream `@modelcontextprotocol/client` (`StreamableHTTPClientTransport`, version negotiation `auto`), and forwards `tools/list`, `tools/call`, `resources/list`, `resources/templates/list`, `resources/read` and `completion/complete` to the remote `/mcp` with the PAT in `requestInit.headers.Authorization`, returning upstream results unchanged. It caches nothing but the tool and resource lists (refreshed every `BRIDGE_LIST_REFRESH_MS`, 5 min), bounds each upstream request by `--timeout-ms` (default `BRIDGE_UPSTREAM_TIMEOUT_DEFAULT_MS`, floor `BRIDGE_UPSTREAM_TIMEOUT_MIN_MS`), sends `User-Agent: iridium-mcp/<version>` and `clientInfo {name: 'iridium-mcp', version}` and neither `X-Iridium-Client` nor `X-Iridium-Client-Version`, and refuses `http://` unless `--allow-insecure-http` (loopback only). On POSIX a token file with any group or other permission bit, or owned by a uid other than the effective one, is refused at startup (exit 2) and at every re-read; Windows makes no mode check, and the documentation says so. A 401 or 403 at startup exits 3. After startup, refusals are handled per credential: a refusal of the current credential triggers at most one re-read of the token file, shared by every concurrent refusal of it; a new `irid_pat_` credential that has never been refused becomes current and each affected request is retried once (rotation with overlap); otherwise the bridge answers every outstanding request with the documented text, sends nothing further upstream and exits 3. A refused credential is never presented again, and 429, 503 `mcp_disabled` and every other per-call failure stay `isError` results or JSON-RPC errors (06-mcp-and-agent-access.md D06-13, amended 2026-09-25). Because the bridge is a transparent proxy, there is exactly one tool implementation and one audit surface (skeleton A36).

**The OAuth consent screen (`apps/server/src/oauth/consent-page.ts`).** One human-facing page is deliberately *not* part of `@iridium/ui`: `GET|POST /oauth/consent` is server-rendered HTML with no application JavaScript at all. It must work before any application bundle has loaded and without the SPA router, the single-use `request_id` must never enter client state or a history entry the SPA manages, and it is a browser surface of the authorization server rather than a route of the workspace. Its CSP is the consent profile, defined once in `security/csp.ts` as `consentCspDirectives(nonce, redirectOrigin)` and set on every consent-flow document that contains the form — `GET /oauth/consent` and every `POST /oauth/consent` response that re-renders the page: `form-action` names `'self'` and the ASCII-serialised origin of the validated `redirect_uri`, or `'self' http:` when that origin's host is the IPv6 loopback literal, which a CSP host-source cannot express; the HTML error pages of `/oauth/authorize` and `/oauth/consent` contain no form and keep `form-action 'self'`. A browser applies the containing document's `form-action` to every redirect hop of the form submission, so a registered `redirect_uri` must answer the redirected request itself or redirect onward only within its own origin: an onward cross-origin redirect is refused by the browser, a constraint on client registrations that `docs/ops/oauth.md` states to operators and that keeps the injection defence on the one page where an injected form could divert an approval. When the validated `redirect_uri` is a loopback URI the page adds a line warning that the application receives the approval on this computer. It is self-contained: it inlines its own stylesheet, `apps/server/src/oauth/consent.css` (copied beside the bundle and read relative to `import.meta.url`; a missing file fails boot while `MCP_OAUTH_ENABLED` is true), in a `<style>` element carrying the response's style nonce, and references nothing under `/app/`, so it renders with `IRIDIUM_WEB_DIR` unset. From M4 `pnpm gen` writes that sheet's custom-property block from `packages/ui/src/theme/tokens.css`, so it does not look foreign without an import across the boundary. Its permission lines are `READ_PERMISSION_LABELS` (`packages/contracts/src/permission-labels.ts`, 06-mcp-and-agent-access.md D06-40), the labels the token dialog shows through `en.ts`. It is served under the nonce CSP with `frame-ancestors 'none'`, `X-Frame-Options: DENY`, `Cache-Control: no-store` and `Referrer-Policy: no-referrer`. This is the one exception to "two client hosts, one UI", and it is recorded as a decision rather than left as an inconsistency (06-mcp-and-agent-access.md D06-31, amended 2026-09-25; 07-client-applications.md D07-47).

Rules encoded in this flow: bearer present means cookies are ignored entirely; non-members receive 404 for every vault-scoped resource and 403 only when they are members lacking a permission (skeleton A30, F13); audit rows are written inside the mutating transaction and never after it; `AuthzBus.publish` and collaboration broadcasts happen only after COMMIT so a subscriber can never observe an event whose row does not exist.

### Open a note

sequenceDiagram

  K-->>N: stateless {t:'participants', users:[{id, name, colorHue, role}]} to every connection of the document
  N->>K: stateless {t:'baseline'}
  K-->>N: stateless {t:'persisted', seq, sv, ds} from lastPersisted

```

Two properties of this flow are load-bearing. First, the document is loaded exactly once per process lifetime while it stays loaded; a second tab or a second user attaching to the same `note:<uuid>` reuses the in-memory document. Second, the ticket is consumed before any document work happens, so a stolen ticket is worthless after one use and after 60 s. The `vault:<uuid>` channel is opened the same way (one provider per open vault per window) but `onLoadDocument` returns nothing and every connection is read-only.

Failure branches (`persist-failed` with `reason` and `retryInMs`, backpressure at 5 000 updates or 32 MiB, `failed` after 10 attempts/30 s, the `save-failed` client rule, `flush {}` for an immediate projection) are specified in 05-collaboration-and-durability.md. Architecturally the important points are: the acknowledgement is emitted only after COMMIT on `dbPersist`; the writer takes parent locks before `note_docs`, without entering the structural vault mutex (A46); and the baseline reply on every `synced` closes the "opened without editing" and "crash after COMMIT before ack" gaps.

The SDK answers a factory throw with a 500 `Response`, which `writeWebResponse` maps, and `onMcpHostError` answers a host-layer exception; both are answered with HTTP 500 `{"error":"server_error"}` without details, logged with the request id and counted in `iridium_mcp_factory_errors_total`; per-argument scope failures inside a tool are `isError:true` results, never HTTP 403 (skeleton A32, A33). The one transport-level exception belongs to the OAuth mount: an access token whose granted scopes contain none of the six read permissions is refused at `/mcp/connect` with `403` and `WWW-Authenticate: Bearer error="insufficient_scope", scope="…", resource_metadata="…"`, because a re-authorization can actually fix that, while no re-authorization can grow a permission the owner's role does not carry (06-mcp-and-agent-access.md D06-36). Because a fresh token row, the owner's status and the membership are read from MySQL on every request, revocation is immediate without any cache. The one input that is deliberately *not* a query is the server-wide kill switch: `mcpKillSwitch` reads `SettingsStore.effective().mcpEnabled.enabled` (below), into which every `PUT /admin/settings` installs, after its transaction, the snapshot it read under the `schema_meta` `server_settings_version` record lock, so a flip is effective on the very next MCP call without adding a SELECT to every agent call. `vaults.mcp_enabled` stays a per-request database read because it arrives with the vault row `authorize()` already loads (06-mcp-and-agent-access.md "Kill switches", 04-auth-and-access-control.md §5.5).

  U->>R: POST /imports/:jobId/commit {options:{collisions, softBreaks, attachmentFolder, markdownFlavor}}
  R->>D: phase = 'committing'. new vault INSERT with status = 'importing' (invisible) or target category locked
  R->>J: run commit (event loop, one transaction per note, resumable)
  loop each note
    J->>D: node row + NoteService.initialize(noteId, lfMarkdown) (FOR UPDATE + initialized_at guard: note_updates seq 1 origin import, note_docs, note_revisions kind import, initial note_projections)
  end
  J->>FS: attachments deduped by SHA-256, path_hint recorded
  J->>D: re-resolve note_links after all notes exist. vault status = 'active'. audit import.committed {report hash}. phase = 'done'
  J-->>U: transfer-progress events (desktop) or polling GET /imports/:jobId (web)
```

A half-imported vault is never visible (`status='importing'` is excluded by `authorize()` and every listing), commit is idempotent per note (`initialized_at` guard), `POST /imports/:jobId/abort` deletes the staging directory, and `jobs/transfer_cleanup` removes expired staging after `import_jobs.expires_at`. Export is the mirror image: `POST /vaults/:vaultId/exports` → `export_jobs` row → the transfer worker flushes loaded documents, streams a yazl ZIP from `note_projections.markdown` with EOL/BOM restored and `manifest.json` → `GET /exports/:jobId/download` (24 h). Details in 08-markdown-pipeline-import-export.md.

### Server restart and recovery

On boot no document is loaded; the first connection to a note triggers `onLoadDocument`, which rebuilds the Y.Doc from `note_docs.snapshot` (V2) plus `note_updates` rows after `snapshot_through_seq` (V1). The client's provider reconnects with a fresh ticket, performs SyncStep1/2 (every pending local update is merged), sends `{t:'baseline'}` and re-derives `saved` from the returned vector's dominance and exact equality of the returned canonical delete-set fingerprint with the local fingerprint. Restart therefore never duplicates initial content (acceptance "Initialization/reconnection", test `collab.restart-no-duplication.integration`) and never loses an acknowledged revision (acceptance "Durable saving", `collab.durable-ack.chaos`).

**The catalog carries every version a manifest declares, not every version this plan pins.** knip 6 reports an unused catalog entry, so a pin added ahead of the milestone that will declare it turns `ci.yml › static` red on the day it is added. The dependency table below is therefore the plan's forward-looking record and the catalog is the present tense: a version stays in that table until the milestone that declares it, and is added to `pnpm-workspace.yaml` in the same change as the manifest that uses it. Five pins were removed from the catalog on 2026-09-13 for exactly this reason and live only in the table until their milestone — `vite-plugin-electron`, `vitest-browser-react`, `electron-playwright-helpers`, `@modelcontextprotocol/conformance` and `@modelcontextprotocol/inspector` (the last two recorded by `docs/spikes/S14-mcp-dual-era-handler.md`, which used them from outside the workspace). The complementary rule lives in 10-testing-and-quality.md L0: where a dependency genuinely must be declared before its milestone, `knip.jsonc` carries it in that workspace's `ignoreDependencies`.

**Single-copy `overrides`.** `pnpm-workspace.yaml`'s `overrides` block pins to `catalog:` every package that must resolve to exactly one copy, and the list is longer than A14's CRDT and CodeMirror entries (`yjs`, `lib0`, `y-protocols`, `@codemirror/state`, `@codemirror/view`). It also carries `@types/node`, because transitive `@types/*` packages depend on `@types/node@*` and would otherwise drag `pnpm dedupe --check` after whatever is newest while Node 24 is the only runtime (A4); `fast-check`, because `@fast-check/vitest` declares its own range and the specs must import the same arbitraries the runner drives; and `axe-core`, because `vitest-axe` declares its own range and one accessibility rule set per run is the point. Every entry exists because two copies would be silently wrong rather than merely wasteful.

Two entries the catalog deliberately does **not** carry, both recorded here because their absence is load-bearing rather than accidental. `electron-updater` is not a 1.0 dependency: the 1.0 desktop build has no in-application updater (§G-8), and an unused dependency fails `knip --production` in `ci.yml › static`; the post-1.0 desktop distribution epic re-adds it at 6.8.9, the companion of electron-builder 26.16.1 (07-client-applications.md D07-43). No OAuth or JOSE library is added either — not `jose`, not `openid-client` — because Iridium's authorization server issues **opaque** credentials hashed with `node:crypto` and never a JWT, so there is no signature to produce, no key to distribute and no `jwks_uri` to serve (§G-1; 06-mcp-and-agent-access.md D06-28). The authorization server's only third-party dependencies are the ones the server already has, plus the zod metadata schemas exported by `@modelcontextprotocol/core` 2.0.0, which `oauth.metadata.contract` validates the served documents against so a hand-written field list cannot drift from the specification.

Language rules for every package: ESM-only (`"type": "module"`), explicit `.ts`/`.tsx` import extensions, `erasableSyntaxOnly`, `verbatimModuleSyntax`, `isolatedDeclarations`, `target es2024`, `exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`. **Compiled** packages build with `tsc -b` (declaration + declarationMap, `dist/` with `.tsbuildinfo` inside `dist/`) and export `./dist/*`; **JIT** packages export `./src/*` and are compiled by the consuming Vite build so React Fast Refresh works across package boundaries. The root `tsconfig.json` is a solution file (`files: []`, `references` to every package) for `tsc -b --builders 8`.

**Compiler API exceptions (A2, amended 2026-09-20).** Exactly three isolated leaf manifests declare `"typescript": "npm:@typescript/typescript6@6.0.2"`: `tooling/mutation` for Stryker's checker, `tooling/api-codegen` for the OpenAPI type printer, and `spikes/s11-markdown` for the AST-based generator of the pinned `markdown-it` packaging patch. The S11 script uses `createSourceFile`, `factory`, transformations and `createPrinter` to split upstream capabilities without copying or rewriting grammar algorithms. The alias is never a workspace catalog or override entry, no product imports these leaves, and all product compilation and type checks stay on TypeScript 7. `guards.mutation-lane.guard` checks the exact three paths and rejects an unreviewed spike as well as a product package. The S11 exception is removed with the packaging patch when an equivalent upstream token entry satisfies the semantic and bundle gates.

| `@iridium/testkit` is a `node`-tagged dev package that both `apps/server` and `apps/e2e` consume | One harness definition for integration, chaos, contract, MCP and E2E lanes; knip `--production` fails if it leaks into a shipped path |

### Boundary tags and allowed dependencies

Tags are declared in each package's `turbo.json` (`"extends": ["//"], "tags": [...]`); rules live in the root `turbo.json` under `boundaries.tags`. oxlint `no-restricted-imports` enforces the banned-import column inside files. Because oxlint overrides replace an earlier override's options for the same rule rather than merging them, and accept no `excludedFiles`, no `no-restricted-imports` configuration is assembled by hand: every one is composed by `restrictedImports()` (`tooling/oxlint-config/base.ts`) from `RESTRICTED_IMPORT_OWNERS` in `oxlint.config.ts` — who bans what where: one row per tag's banned-import column below, the repository-wide families (`bannedEverywhere`, the yjs family by name and by subpath, every `zod` subpath, and `@modelcontextprotocol/sdk` 1.x) and the server-internal rows (the server set with the MCP SDK and `node:async_hooks`, the MCP read graph, ARCH-30, `pagination`, the OAuth module layout, and `sendProblem`'s privacy to `security/`) — minus `DECLARED_EXEMPTIONS`, the only carve-outs, each with its reason: the S11 `markdown-it` adapter, the Yjs imports of `packages/crdt` and of the S04 spike harness, ARCH-30's own module and composition root, the MCP SDK packages under `apps/server/src/mcp/**`, `node:async_hooks` in `mcp/plugin.ts`, `@modelcontextprotocol/core` in `oauth/metadata.ts` and the type-only `@modelcontextprotocol/server` import of `auth/tokens/verify.ts`. Overrides are ordered general to specific, so the last override matching a file carries every ban that applies to it; owner rows carry no `exceptFiles`, and no inline disable directive names the rule. `guards.restricted-imports.guard` checks the effective configuration of every file against the two tables, pins the exemption inventory, and runs the pinned oxlint over probes of every owner and exemption glob, so each configured ban is proven to refuse what it names (13-decision-log.md A6, amended 2026-09-25). dependency-cruiser 18.2.0 is the fallback if `turbo boundaries` proves too immature.

## Runtime configuration model

### Principles

1. **Environment only.** The server is configured exclusively through environment variables (Compose `environment:`/`env_file:`, systemd `EnvironmentFile=`, CI job env). There is no YAML/TOML configuration file: a second source of truth would need its own precedence rules, its own secret handling and its own redaction, and every deployment target already delivers environment variables and files (decision ARCH-08).
2. **Parsed once, fail fast.** `apps/server/src/config/env.ts` parses `process.env` exactly once into a frozen `IridiumConfig`. A validation failure prints `z.prettifyError(error)` to stderr and exits with code 2 (configuration or usage error — see the CLI exit codes in the cross-cutting section and OPS-16 in 11-operations-and-deployment.md); nothing listens, no pool opens, no migration runs. `iridium config check` performs the same parse and stops.
3. **Secrets never travel as plain values when a file is available.** Every secret key accepts a `<NAME>_FILE` variant whose file content (trailing newline trimmed) replaces the value. Setting both `<NAME>` and `<NAME>_FILE` is a validation error, not a precedence question.
4. **No `process.env` outside `config/`.** The oxlint rule `no-process-env` (with `config/**` and `main.ts` as the only exceptions) makes every module receive its configuration slice through plugin options or constructor arguments. Tests build a config object directly; they never mutate `process.env` after boot.
5. **Typo protection, with reserved harness namespaces.** A variable starting with `IRIDIUM_` that the schema does not know is a fatal error (`config.unknown_key`, exit 2) — typo protection for the most sensitive knobs; variables without that prefix are ignored silently. The rule has one carve-out, and it is not a loophole but a requirement: the test harness owns several `IRIDIUM_*` names of its own (10-testing-and-quality.md D10-5), and the `child` harness mode spawns this same binary with the whole job environment, so a fatal unknown-key rule without the carve-out would kill the server in every CI lane that exports `IRIDIUM_PROP_RUNS` or `IRIDIUM_MYSQL_IMAGE` — including the chaos lane, the only lane that can prove the durability invariants. `EnvSchema` therefore lists these as **known-and-ignored**: the prefixes `IRIDIUM_TEST_*`, `IRIDIUM_PROP_*`, `IRIDIUM_CHAOS_*`, `IRIDIUM_E2E_*`, `IRIDIUM_FIXTURE_*`, `IRIDIUM_COVERAGE_*` and the exact names `IRIDIUM_MYSQL_IMAGE`, `IRIDIUM_USER_DATA`, `IRIDIUM_SERVER_URL`, `IRIDIUM_MCP_TOKEN` (the last two belong to the clients and the `iridium-mcp` bridge, never to the server). `iridium config check` prints them under "ignored harness keys" so an operator can see that a name was recognised and deliberately not used. No product key ever uses one of those prefixes, which is what keeps the carve-out from weakening typo protection: the server reads exactly six `IRIDIUM_*` keys — `IRIDIUM_MIGRATE_ON_BOOT`, `IRIDIUM_ALLOW_NEWER_SCHEMA`, `IRIDIUM_ALLOW_UNTESTED_MYSQL`, `IRIDIUM_WEB_DIR`, `IRIDIUM_TOOLS_DIR` (from M3) and `IRIDIUM_FAULT` (`NODE_ENV=test` only). Three names are listed explicitly as rejected names (`REJECTED_KEYS`), each refused with a hint (`config.rejected_key`, exit 2) whatever its prefix: `IRIDIUM_E2E`, which the desktop main process reads and this one never does; `IRIDIUM_ALLOW_NO_ORIGIN_WS`, so nobody reintroduces the Origin bypass (skeleton A24); and `PUBLIC_HOST`, which is derived from `PUBLIC_ORIGIN` and is never a key (ARCH-03). `config.env.unit` asserts that the `IRIDIUM_*` members of the schema's keys are exactly those six and that `REJECTED_KEYS` holds exactly those three names, so this paragraph cannot drift from the schema.
6. **Env values are floors of strictness.** Policy that administrators may edit at runtime lives in `server_settings` (skeleton C.10). The environment supplies both the default and the laxest value an administrator is allowed to choose: an admin may shorten a session TTL, shorten a PAT lifetime or raise the minimum password length, but never the reverse. `PUT /admin/settings` rejects a laxer value for any member it writes with 422 `validation_failed` (`below_env_floor`); a stored value that a later environment change has overtaken is clamped by the merge, never rejected (decision ARCH-10).
7. **The build is diffed against the schema.** Turborepo runs with `envMode: strict`; `apps/server/turbo.json` lists every key the server reads (as `passThroughEnv` on `dev`, the one task that starts the server; the cacheable tasks read no environment, so no key is a cache input, and an `IRIDIUM_*` wildcard keeps the schema's unknown-key rule fatal under strict mode), and the check `check-env-lists` (`scripts/check-env-lists.ts`, run by `ci.yml` › `static`) fails when the Turbo list and the `EnvSchema` keys differ in either direction (skeleton B.2).

### Loading pipeline

```mermaid
flowchart LR
  ENV["process.env"] --> ALIASES["apply KEY_ALIASES<br/>a plan spelling or a renamed key,<br/>mapped with a warning naming its origin"]
  ALIASES --> FILES["resolve NAME_FILE variants<br/>read, trim trailing newline,<br/>reject when both forms are set"]
  FILES --> RINGS["collect keyrings<br/>NAME_V-n and NAME_V-n_FILE<br/>into version to bytes maps"]
  RINGS --> PARSE["zod EnvSchema.parse<br/>types, defaults, enums, ranges,<br/>reject unknown IRIDIUM_ keys<br/>(reserved harness namespaces ignored)"]
  PARSE --> REFINE["cross-field refinements"]
  REFINE --> FREEZE["Object.freeze to IridiumConfig"]
  FREEZE --> SUMMARY["redactConfig() then<br/>pino info event config.loaded"]
  PARSE -. failure .-> EXIT["z.prettifyError to stderr,<br/>exit 2"]
  REFINE -. failure .-> EXIT
  ALIASES -. both spellings set .-> EXIT
```

`KEY_ALIASES` maps each accepted alternative spelling to its canonical key, and every entry records its origin: `plan_spelling` for the four keys this section prints differently from 11-operations-and-deployment.md (`STEP_UP_WINDOW_MINUTES`, `METRICS_ALLOW_CIDRS`, `TRASH_RETENTION_DAYS_DEFAULT`, `COLLAB_MAX_CONNECTIONS`), and `renamed` for `MCP_RATE_LIMIT_PER_HOUR`, the pre-M3 name of `PAT_DEFAULT_RATE_LIMIT_PER_HOUR` (03-data-model.md D03-28). An alias is mapped with a warning, setting both spellings is a named `ConfigError` (exit 2), and both the warning and the error state the entry's actual origin — "the 02-system-architecture.md spelling of X" or "the pre-M3 name of X", never a blanket label. Every alias stays in `apps/server/turbo.json`'s env list, as `check-env-lists` requires.

`loadConfig(env: Record<string, string | undefined>): IridiumConfig` is the only export used by `buildApp()`; `redactConfig(config)` returns the same shape with every secret replaced by `<set: versions v1,v2; sha256:ab12cd34>` (first eight hex characters of the SHA-256 of the material), a file-sourced value additionally naming its origin as `<set: file:/run/secrets/audit_hmac_v2; sha256:ab12cd34>`, and an unset optional secret as `<unset>`. That rendering — not a bare `***` — is what the `config.loaded` line and `iridium config check` print on every surface (11-operations-and-deployment.md uses the same format in its startup summary and its key-mismatch runbooks), because the fingerprint is the control an operator uses to confirm that two hosts carry the same key, and the file path is what tells them which mount to fix, neither of which reveals any material. `iridium config check [--json]` prints the redacted summary and the list of `server_settings` overrides currently in force.

Cross-field refinements (each produces a named error such as `PUBLIC_ORIGIN must use https outside development`):

| Rule | Reason |
|---|---|
| `PUBLIC_ORIGIN` must be `https:` unless `NODE_ENV=development` or `test`; no path, query or fragment; `PUBLIC_HOST` is derived from it and is never settable (a set `PUBLIC_HOST` is refused by name) | Cookies use the `__Host-` prefix, the WebSocket Origin allowlist and the MCP resource URI are built from it (skeleton A24, A26, A31) |
| `TRUST_PROXY` is a comma-separated list of IPs/CIDRs; the literal `true` is rejected | Trusting every hop lets any client spoof `X-Forwarded-For` (digest §5) |
| `TLS_CERT_FILE` and `TLS_KEY_FILE` are both set or both absent, and never together with `TRUST_PROXY` | The air-gapped profile terminates TLS in Fastify (HTTP/1.1) and has no proxy in front (skeleton A48) |
| `IRIDIUM_FAULT` and `DEV_ORIGINS` are rejected unless `NODE_ENV` is `test` (fault registry) or `development` (dev origins) | Fault points and relaxed origins must be impossible in production images |
| `ATTACHMENTS_DRIVER=s3` requires `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`; `ATTACHMENTS_DRIVER=fs` requires `ATTACHMENTS_DIR` | Driver-specific keys are validated as a group |
| `ATTACHMENTS_ENCRYPTION=aes256gcm` requires an `ATTACHMENT_KEY_V<n>` keyring; the value `aes256gcm` is rejected, and the message says that envelope encryption is **not implemented** and that attachments are protected by volume or database encryption instead | The columns and the keyring are reserved; the feature is not built. §G-4 was answered on 2026-09-12 — volume and database encryption only — so the refusal states an unimplemented path, never an undecided question (skeleton A44) |
| `METRICS_ENABLED=true` requires `METRICS_TOKEN` or `METRICS_ALLOW_CIDRS` | `/metrics` is never anonymous on a routable interface (decision ARCH-04) |
| `DB_POOL_PERSIST >= 2`, `DB_POOL_APP >= 5`, `PROJECTION_WORKERS >= 1`, `TRANSFER_WORKERS >= 1` | Below these the writer fairness scheduler and the pools cannot make progress |
| `PAT_DEFAULT_LIFETIME_DAYS ≤ PAT_MAX_LIFETIME_DAYS` and `OAUTH_REFRESH_IDLE_DAYS ≤ OAUTH_REFRESH_ABSOLUTE_DAYS`: refused only when both keys of a pair are set (directly or through an alias) and contradict each other; when either is defaulted and the pair is out of order, the dependent key takes the bound's value with a warning naming both keys and the value used, so `IridiumConfig` never holds a contradictory pair (03-data-model.md D03-28) | An operator who hardens one key must never be refused a boot, and a contradiction written in both keys is a mistake worth stopping for |
| `LOG_FORMAT=pretty` is rejected when `NODE_ENV=production` | Production logs are machine-parsed JSON |
| `UV_THREADPOOL_SIZE` is read back and a warning is logged when it is unset or below 8 | libuv reads it before any JavaScript runs, so the schema can only observe it (skeleton A29) |

The authorization server's operational caps — every `OAUTH_*` limit of the table below — are constants in `@iridium/contracts/limits.ts` with no environment form at all (ARCH-16, invariant 6).

### Admin-editable settings

`server_settings` rows (`key`, JSON `value`, `version`) hold only the members an administrator set; a missing row, or a group stored as `{}`, means every member of the group is at its environment baseline, so a fresh install needs no seeding. The settings document's version and `ETag` is the `schema_meta` validator `server_settings_version`, which only ever grows and is never below the largest row `version` (03-data-model.md §13.1, §13.2). The in-process `SettingsStore` (`settings/store.ts`, ARCH-31) is loaded by the fail-closed `server_settings` readiness check and refreshed when the validator advances (see boot step 2 and the singletons section). Effective policy is computed member by member from `SERVER_SETTING_RULES` in `@iridium/contracts/settings.ts`, taking the stricter of the environment baseline and the stored value (`stricterOf`), and `GET /admin/settings` returns `{version, effective, floors, stored}` from the installed snapshot without a SELECT, so the console can grey out what cannot be loosened and offer to clear a stored value an environment change has overtaken. At M3 the store and the document carry exactly `patPolicy`, `mcpEnabled` and `oauthPolicy`, the three groups with M3 consumers; the other four groups arrive at M7, each in the change that rewires its consumer, and until then those consumers read `EnvSchema` and a `PUT` naming one of them is `422 validation_failed` (13-decision-log.md AG12).

Every consumer therefore reads admin policy through `SettingsStore.effective()` — an in-memory read, never a per-request SELECT. `mcpEnabled` is the switch where that matters most: the `mcpKillSwitch` preHandler evaluates `SettingsStore.effective().mcpEnabled.enabled` on every MCP call. `PUT /admin/settings` is the only writer of `server_settings` and of its validator (there is no CLI or direct-SQL path); it serialises on the validator's record lock, validates only the members it writes, replaces the named groups' known members, and after its transaction installs the complete snapshot it read under that lock — no reload follows — so the flip is a next-call property with no restart, the property 06-mcp-and-agent-access.md and 04-auth-and-access-control.md depend on. A direct `UPDATE server_settings` is invisible to the running process until `schema_meta` `server_settings_version` is raised above the installed version, which the next readiness evaluation observes; that is why `mcp.revocation.mcp` flips the switch through the endpoint (10-testing-and-quality.md). In the post-MVP multi-process deployment `install(snapshot, version)` is fanned out on the `settings.changed` channel, with the validator refresh as the backstop, so a server-wide switch stays server-wide instead of becoming per process.

The row keys in the left column are `server_settings.key` values and stay `snake_case` like every other database identifier. **The JSON stored in `value` is the same object the wire carries**, so its members are `camelCase` (ARCH-17) and are spelled exactly as the zod group schemas of `@iridium/contracts/settings.ts` declare them. Those schemas are `z.strictObject`s: a `PUT /admin/settings` body with `snake_case` members, or naming an M7 group at M3, is rejected with `422 validation_failed`, and a stored row that fails its group schema is database state, never fatal — before the store's first load it keeps the `server_settings` readiness check failing with the key and the remedy, after it the installed policy stays enforced and the check warns. 03-data-model.md §13.1 is authoritative for the spelling; the table below is its projection onto the storage layer, one row per top-level group.

### How configuration reaches the code

- `buildApp({ mode, config })` receives the parsed object; each plugin is registered with its slice (`fastify.register(collabPlugin, { collab: config.collab, limits: LIMITS })`). Nothing reads the whole config except `app.ts` and the ops plugin (which renders `GET /admin/system` and the redacted summary).
- Services are plain modules constructed once with explicit dependencies (`new TreeService({ db: dbApp, audit, gateway, clock })`); there is no dependency-injection container. A stateful service is constructed by the plugin that owns its lifecycle — the `SettingsStore` by `settings/plugin.ts` in step 2, the `AccessLogWriter` by the `audit` plugin, `TokenBudget` and the `LastUsedTracker` by the `auth` plugin — and `app.ts` constructs only the instances passed across plugins by injection: the dedicated bounded `RateLimitStore` of the token budget, `cursorSource()` (which reads `schema_meta` `cursor_key_version` per call and returns a database-free `CursorCodec`), and the REST and MCP `ContentReadCore` instances, built through `content/read/factory.ts` (ARCH-31). The integration harness constructs the same services with Testcontainers pools.
- The web and desktop clients receive no server configuration except through `GET /meta` (`apiVersion`, `minClientVersion`, `serverVersion`, `features`, `publicOrigin`, `collab`, `mcp`, `limits`, `policies`), whose exact field spellings are 09-api-reference.md §2.2's `Meta` schema and nothing else.
- The CLI (`main.ts`) loads the same config; commands that need the migrator or backup role read `DATABASE_MIGRATE_URL`/`DATABASE_BACKUP_URL` and fail with exit 2 (usage error: a required key is absent) when the required URL is absent.
## The single limits policy

Skeleton A.1 is the one place limits are decided; this table is its canonical rendering for implementers. Every value is a named constant in `@iridium/contracts/limits.ts` (`export const LIMITS = { … } as const`, decision ARCH-16) so the client, the server and the tests read the same number. A small operational subset may be overridden by environment (marked in the last column); every override is validated against the constant's documented bounds, and the two overrides that a client must know before sending a request (`MAX_UPLOAD_BYTES`, `MAX_IMPORT_BYTES`) are published additively at `GET /meta.limits` under the wire names `uploadBytes` and `importBytes`.

Three naming rules make the "single policy" claim of 01 §5.8 mechanically true rather than aspirational, because `limits.single-source.guard` and `limits.policy.unit` (10-testing-and-quality.md) both compare identifiers, not values:

1. **The third column is the sole naming authority.** Every other section of this plan cites these exact identifiers for these limits — `NOTE_SOFT_MAX_UTF16`, `NOTE_HARD_MAX_UTF16`, `MARKDOWN_SOURCE_MAX_BYTES`, `MARKDOWN_BLOCKQUOTE_MAX_DEPTH`, `MARKDOWN_LIST_INDENT_MAX_COLS`, `MARKDOWN_LINES_PER_PARAGRAPH_MAX`, `PROJECTION_TIMEOUT_SERVER_MS`, `PROJECTION_TIMEOUT_CLIENT_MS`, `UPLOAD_MAX_BYTES`, `IMPORT_MAX_BYTES`, `IMPORT_MAX_FILES`, `IMPORT_MAX_DEPTH` — and a differing spelling elsewhere is an error in that section, not a second constant. Two spellings of one limit make `limits.policy.unit` unsatisfiable by construction: one of them is an unreferenced constant and the other does not compile against the `LimitId` union.
2. **Environment and constant names are separate vocabularies, with three explicit public exceptions.** The last column lists environment variables. The already documented keys `WS_MAX_PAYLOAD_BYTES`, `UPDATE_LOG_RETENTION_DAYS`, and `SHUTDOWN_DRAIN_MS` intentionally share their constant names; the policy test asserts exactly this intersection and their bounds. Every other environment name differs from its constant name. `MAX_UPLOAD_BYTES` and `MAX_IMPORT_BYTES` are the env keys that override the constants `UPLOAD_MAX_BYTES` and `IMPORT_MAX_BYTES`; `COLLAB_DEBOUNCE_MS`/`COLLAB_MAX_DEBOUNCE_MS` override `COMPACTION_DEBOUNCE_MS`/`COMPACTION_MAX_DEBOUNCE_MS`; `COLLAB_MAX_LOADED_DOCS` overrides `LOADED_DOCS_MAX`; `MCP_REQUEST_TIMEOUT_MS` overrides `MCP_REQUEST_DEADLINE_MS`, `MCP_RATE_LIMIT_BURST_PER_MIN` overrides `MCP_TOKEN_BURST_PER_MINUTE` and `MCP_PROCESS_CEILING_PER_MIN` overrides `MCP_PROCESS_PER_MINUTE`; and `PAT_DEFAULT_RATE_LIMIT_PER_HOUR` and `OAUTH_DEFAULT_RATE_LIMIT_PER_HOUR`, the per-kind hourly baselines, both default to `MCP_TOKEN_PER_HOUR`. Each of these is an entry of `LIMIT_ENV_OVERRIDES`, whose names the test harness's `LIMIT_OVERRIDE_ENV` mirrors, and each environment default equals its constant, which `limits.policy.unit` asserts (06-mcp-and-agent-access.md D06-48). The note-size and Markdown caps have no environment form at all, so `NOTE_*` and `MARKDOWN_*` never appear in `EnvSchema`.
3. **A section may add a limit, never rename one.** Caps that A.1 does not cover — 08-markdown-pipeline-import-export.md's `MARKDOWN_MAX_FOOTNOTE_REFS` and `MARKDOWN_MAX_BRACKETS` (decision D08-03), its `PREVIEW_DEBOUNCE`, `SNIPPET_*`, `IMPORT_UPLOAD_BATCH_*` and `FM_*` constants, 05-collaboration-and-durability.md's `INSERT_CHUNK_MAX_BYTES` (D05-16) and its per-transaction `WRITER_BATCH_MAX_UPDATES` and `WRITER_BATCH_MAX_RAW_BYTES`, and the M3 caps of 06-mcp-and-agent-access.md and 04-auth-and-access-control.md — the MCP tool-output, list, transport, instructions and request-deadline caps (`MCP_*`, `MCP_AUTH_FAILURES_PER_IP_PER_MINUTE` included), the `BRIDGE_*` timings, the `OAUTH_*` authorization-server caps, the token-administration caps (`PAT_MAX_ACTIVE_PER_USER`, `PAT_MAX_ALLOWLIST_VAULTS`, `TOKEN_LIST_*`, `ADMIN_NOTE_MAX_CHARS`), the token and OAuth settings bounds, the failure-audit deduplication bounds (`AUDIT_DEDUP_*`, D04-16), the access-log writer's bounds (`ACCESS_LOG_*`, D06-11) and the last-used tracker's (`TOKEN_LAST_USED_*`, D06-49) — together with the list caps REST and MCP share (`LIST_PAGE_MAX`/`LIST_PAGE_DEFAULT` and `BOUNDED_LIST_MAX`) and the shutdown's `SHUTDOWN_FLUSH_MARGIN_MS` — live in the same `LIMITS` object, are added to the `LimitId` union with an enforcement owner and first enforcing milestone, and are listed by their owning section *and* as a row of the table below, which is what keeps this rendering canonical. Every number on the M3 surface that bounds, refuses, times out or sizes server-held state is such a member, named once; a surface that caps the same quantity as another reuses that member instead of spelling a second one — the MCP tools and resources read `REVISION_LIST_*`, `ATTACHMENT_LIST_*`, `ATTACHMENT_REFERENCE_SAMPLE_MAX`, `SEARCH_LIMIT_*`, `SNIPPET_*`, `LIST_PAGE_*` and `BOUNDED_LIST_MAX`, never an `MCP_`-prefixed copy (06-mcp-and-agent-access.md D06-48). Nothing outside `limits.ts` declares a number. Column widths and protocol hints are not limits. A width a module truncates to at ingestion — `CLIENT_NAME_MAX_CHARS` (120, the width of `oauth_clients.client_name` and `access_tokens.name`), to which the one function that writes `oauth_clients` rows in `auth/oauth/clients.ts` truncates a registered or document-supplied `client_name` on a code-point boundary, never refusing it (06-mcp-and-agent-access.md D06-47); `auth/user-agent.ts`'s `CLIENT_IDENTITY_WIDTHS` (`access_log.client_name` 64, `access_log.client_version` 32, `access_tokens.last_client` 120, 06-mcp-and-agent-access.md D06-23) and `USER_AGENT_MAX_BYTES` (255) — and a value the server only advertises — `Retry-After` 60 on `503 mcp_disabled` and 5 on `503 not_ready`, the `tools/list` `cacheHints` `ttlMs` 300 000 and `GET /meta`'s `META_CACHE_SECONDS` — stay named module constants on the `limits.single-source.guard` allowlist.

The exhaustive `satisfies Record<LimitId, Enforcement>` in `apps/server/src/limits.policy.unit.spec.ts` assigns every identifier an owner, expected outcome, and first enforcing milestone. Missing or invented identifiers fail type checking. Runtime assertions require an actual code reference for every active owner and check configuration-to-consumer wiring; comments and quoted examples do not count. The suite runs M1 policies immediately, then ratchets with the exited milestone or the explicit exit-rehearsal target. M1 covers collaboration, durability and update-log pruning, authentication, REST creation, and shutdown; M2 adds Markdown projection, search, frontmatter and uploads; M3 adds MCP, the per-credential token budget, token administration, the token and OAuth settings bounds, the OAuth endpoints, and the access-log, last-used, shutdown-flush and bridge bounds; M4 adds preview scheduling; M6 adds import. A member that names a cap shipped code already enforces is recorded at the milestone that shipped it: `BOUNDED_LIST_MAX`, `LIST_PAGE_MAX`/`LIST_PAGE_DEFAULT` and the `AUDIT_DEDUP_*` members at M1, `CURSOR_TTL_SECONDS` at M2. A future row is a declared obligation, not evidence of a shipped enforcement site. Exact boundary tests and the corresponding real-wire suites prove the outcomes.

- No module defines a numeric limit of its own; the guard test `limits.single-source.guard` greps `apps/server/src`, `packages/collab-client`, `packages/editor`, `packages/ui` and `packages/mcp-bridge/src` for numeric literals adjacent to the words `limit`, `max`, `cap` outside `limits.ts` and fails on new occurrences (an allowlist file records the few legitimate ones such as CodeMirror viewport sizes).
- `collab.limits.integration` drives every WebSocket limit to its boundary and asserts the exact close reason; `security.rate-limits.integration` does the same for the REST buckets; `mcp.rate-limit.mcp` for the token buckets; `attachments.security.integration` for uploads; `markdown.pathological.unit` for the projection caps.
- Changing a value is a contracts change: it bumps nothing in `apiVersion` (limits are not part of the wire shape) but the `GET /meta.limits` object always reflects the running server, so a client that pre-validates never disagrees with the server it talks to.
- Every limit that closes a connection or refuses a request emits a metric (`iridium_ws_closes_total{reason}`, `iridium_http_requests_total{status="413"|"429"}`, `iridium_token_budget_refused_total{surface,layer}` for the per-credential budget, `iridium_mcp_rate_limited_total{layer}` for the MCP-only `ip` and `process` layers) and, where the cause is a capacity budget, an alert (skeleton A49).
- A `GET` route that carries its own limiter, or whose handler must not run for `HEAD`, declares `exposeHeadRoute: false` (`GET /oauth/authorize`, `GET /oauth/consent`): Fastify would otherwise register a `HEAD` twin with a copy of the route options, a separate limiter store that doubles the bound, and the `GET` handler. The security plugin's `onRoute` check refuses at boot, with a named error, a `HEAD` route whose config carries an object `rateLimit`, so a later limited `GET` cannot silently double its bound (06-mcp-and-agent-access.md D06-47).
## In-process singletons behind interfaces

The MVP runs one server process (spec §6, skeleton F9), which makes several things exact that would otherwise be eventually consistent: a ticket is consumed once, a revocation closes every affected socket within one event-loop turn, a rate-limit bucket is a single counter, and one `NoteWriter` owns each loaded note. Each of these lives behind an interface with the in-process implementation as the only MVP binding. The interfaces are not speculative abstraction: every one has a named second implementation on the post-MVP roadmap (skeleton E, "Redis-backed `AuthzBus`/`TicketStore`/rate-limit stores + `@hocuspocus/extension-redis` → Meilisearch behind `SearchIndex`"), and each ships with a contract test suite (`<name>.contract.spec.ts`, decision ARCH-19) that a future implementation must pass unchanged.

// authz/bus.ts
type AuthzEvent =
  | { type: 'user.disabled'; userId: UserId }
  | { type: 'user.password_changed'; userId: UserId; keepSessionId: SessionId | null }
  | { type: 'session.revoked'; userId: UserId; sessionId: SessionId }
  | { type: 'token.revoked'; userId: UserId; tokenId: TokenId }
  | { type: 'membership.removed'; userId: UserId; vaultId: VaultId }
  | { type: 'membership.role_changed'; userId: UserId; vaultId: VaultId; role: Role; memberVersion: number }
  | { type: 'vault.archived'; vaultId: VaultId }
  | { type: 'note.trashed'; noteId: NoteId; vaultId: VaultId }
  | { type: 'note.purged'; noteId: NoteId; vaultId: VaultId };
interface AuthzBus {
  publish(event: AuthzEvent): void;                        // after COMMIT only (services enforce this: publish() takes the committed event object returned by the transaction helper); synchronous invocation of every subscriber in registration order, observing async failures (D04-14)
  publishAndWait(event: AuthzEvent): Promise<boolean>;     // the same invocation, joining every subscriber; false on any synchronous or asynchronous failure
  subscribe(handler: (e: AuthzEvent) => unknown): Unsubscribe;   // a returned promise is observed, never left floating
}

// auth/tickets/store.ts — every method reads time from the injected Clock
interface TicketStore {
  issue(binding: { sessionId: SessionId; userId: UserId }, count: number): Promise<readonly string[]>;   // returns plaintext tickets once
  consume(raw: string): Promise<{ sessionId: SessionId; userId: UserId } | null>;   // single use; null on unknown/expired/used/mismatch
  revokeSession(sessionId: SessionId): Promise<number>;                             // live entries removed
  revokeUser(userId: UserId, keep?: SessionId): Promise<number>;                    // live entries removed, the kept session's excepted
  sweep(): Promise<number>;                                                         // expired entries removed; reads the injected Clock
  close(): Promise<void>;                                                           // stops the local sweep timer
}

// oauth/consent-request-store.ts — exists only while MCP_OAUTH_ENABLED is true
interface ConsentRequestStore {
  create(entry: { clientId: OAuthClientId | null; cimd: { clientId: string; document: ClientMetadataDocument } | null; userId: UserId; sessionId: SessionId; redirectUri: string; state: string | null; codeChallenge: string; resource: string; scopes: readonly Permission[] }): Promise<string>;   // returns the single-use request_id
  // clientId is null only for a CIMD client_id that has no oauth_clients row yet; cimd then carries the presented client_id and its validated document (oauth/cimd.ts, at most OAUTH_CIMD_MAX_BYTES) until the first Allow creates the row (06-mcp-and-agent-access.md D06-41)
  consume(requestId: string): Promise<ConsentRequest | null>;   // deleted before validation, exactly as TicketStore.consume; the caller compares the stored sessionId
  sweep(): Promise<number>;                                     // OAUTH_CONSENT_REQUEST_TTL_SECONDS against the injected Clock; also run by jobs/session_ticket_sweep
  close(): Promise<void>;                                       // stops the local sweep timer
}

// security/rate-limit-store.ts — one primitive for the global REST limiter and, through injection, the per-credential budget of auth/tokens/budget.ts
interface RateLimitStore {
  consume(bucket: string, key: string, points: number, now: number): Promise<RateLimitDecision>;   // { allowed, remaining, resetAt }
  consumeWithPolicy(bucket: string, key: string, points: number, now: number, policy: FixedWindowPolicy): Promise<RateLimitDecision>;   // capacity resolved per call; counts survive a capacity change
  readWithPolicy(bucket: string, key: string, now: number, policy: FixedWindowPolicy): Promise<FixedWindowSnapshot>;                // non-mutating: allocates, renews and consumes nothing
  reset(bucket: string, key: string): Promise<void>;
}

// search/index.ts
interface SearchIndex {
  index(doc: { noteId: NoteId; vaultId: VaultId; title: string; bodyText: string; revision: bigint }, trx: Transaction): Promise<void>;
  remove(noteId: NoteId, trx: Transaction): Promise<void>;
  query(q: ParsedQuery, scope: { vaultIds: VaultId[]; pathPrefix?: string }, page: { cursor?: string; limit: number }): Promise<SearchPage>;
  rebuild(vaultId?: VaultId): Promise<void>;
}

// attachments/storage.ts
interface StorageDriver {
  put(key: string, body: Readable, expected: { sha256: Uint8Array; size: number }): Promise<void>;   // atomic: temp + rename (fs) or single PUT with checksum (s3)
  get(key: string, range?: { start: number; end: number }): Promise<Readable>;
  delete(key: string): Promise<void>;
  exists(key: string): Promise<boolean>;
  healthcheck(): Promise<void>;                                                                    // used by /readyz
}

### What a second process would need

The order below is the documented scale-out path; nothing in it changes a wire contract, a table, or a client:

1. **Affine collaboration routing.** The document name arrives in the first Hocuspocus message, not in the URL, so a proxy cannot hash on it; pinning would require the client to add the note id as a query parameter on the `/collab` URL purely as a routing hint. The preferred option is therefore the second one: `@hocuspocus/extension-redis` fans updates out between processes, and a single writer per note — elected with `GET_LOCK('iridium_note_<id>', 0)` held for the document's loaded lifetime — performs persistence. That keeps `NoteWriter` untouched; a non-owner process forwards updates and relays the `persisted` and `projected` messages it receives over Redis.
2. **Redis for the four ephemeral stores.** `AuthzBus`, `TicketStore`, `ConsentRequestStore` and `RateLimitStore` get Redis implementations; the interface tests already exist, and because they observe outcomes only, the Redis ticket and consent stores pass them unchanged by deciding expiry against the stored `expiresAt` read with the injected `Clock` (ARCH-19). Redis is *not* a system of record: losing it loses tickets (re-issued), pending consent requests (the authorization restarts) and counters (reset).
3. **Leader for periodic enqueueing.** `JobScheduler` takes `GET_LOCK('iridium_jobs_leader', 0)` before enqueueing scheduled maintenance; runners stay symmetric.
4. **Shared attachment store.** `s3` driver (already in MVP) or a shared volume for `fs`; `STAGING_DIR` and `EXPORTS_DIR` must be shared or the import/export routes pinned to the process that owns the job (`jobs.locked_by`).
5. **Search.** `MysqlFulltextSearch` remains multi-process safe (it is the database); Meilisearch is a capacity decision, not a scale-out requirement.
6. **Per-process identity.** `instanceId = <hostname>:<pid>:<boot-uuid-short>` already labels logs, metrics and `jobs.locked_by`.

Until then the single process is a deliberate, tested configuration: the admission budget (skeleton A50), backpressure (A21), load shedding (`@fastify/under-pressure`) and the k6 SLOs (A51) define its envelope, and `/readyz` reports when it is approached.

### Identifiers

Every entity that appears on a wire surface is identified by a UUIDv7 (RFC 9562) generated in the application, stored as `BINARY(16)` and rendered as the canonical lowercase 36-character string on REST, WebSocket, MCP, IPC and in `iridium://` URIs (skeleton A11).

| Aspect | Rule |
|---|---|
| Generator | `@iridium/contracts/ids.ts` `newId()` with no dependency: 48-bit Unix millisecond timestamp, `ver = 7`, 12-bit `rand_a` used as a per-process monotonic counter that is re-seeded randomly on every new millisecond and increments within the same millisecond (RFC 9562 §6.2 method 1, so ids created in one transaction sort in creation order), `var = 10`, 62 random bits from `globalThis.crypto.getRandomValues` (available in Node 24 and every supported browser, so the `core` package needs no `node:*` import). If the counter would overflow within one millisecond the generator waits for the next millisecond rather than reordering (decision ARCH-13) |
| Types | Branded string types per entity: `UserId`, `SessionId`, `TokenId` (the `access_tokens.id` UUID; the 16-character base62 `token_id` lookup key is `TokenLookupId`), `VaultId`, `NodeId`, `NoteId` (a `NodeId` whose node is a note), `AttachmentId`, `JobId`, `RequestId`, `InstanceId`. zod schemas `idSchema('vault')` accept the canonical form case-insensitively and normalise to lowercase (agents and humans paste uppercase ids; rejecting them would be hostile), and the inferred type carries the brand. Output is always lowercase |
| Database | `db/ids.ts` `toBin(id): Buffer` / `fromBin(buf): string` are the only conversion points; Kysely column types for id columns are declared as `Buffer` and the row mappers convert at the repository edge, never in handlers. Time ordering keeps InnoDB clustered inserts local |

| URIs | `iridium://vault/{vault_id}/note/{note_id}` (MCP resources) and `iridium://open?server=&note=&rev=` (deep links) embed the lowercase UUID; both are validated with the same zod schema before use |

### Error envelope

Every REST error body is a `ProblemDetails` object (RFC 9457) with `Content-Type: application/problem+json`; the zod schema and the closed `ErrorCode` enum live in `@iridium/contracts/errors.ts` and are emitted into the OpenAPI document for every `4xx`/`5xx` response (skeleton A6).

The `ProblemDetails` schema is 09-api-reference.md §1.4: RFC 9457's `type` (`urn:iridium:problem:<code>`, ARCH-12), `title`, `status` and `detail` without `instance`, the two required Iridium members `code` (the only field clients switch on) and `requestId` (echoed in the `X-Request-Id` header), and exactly D09-2's four optional extension members `current`, `errors`, `references` and `retryAfterMs`. The code→status table, its enumerated status variants and the OAuth error values are 09-api-reference.md §1.5, and the MCP envelope's `McpHttpErrorCode` table is §4.6. These are the single normative copies that `ProblemDetails`, `ERROR_CODE_STATUS`, `PROBLEM_VARIANTS`, `OAUTH_ERROR_CODES` and `McpHttpErrorCode` in `@iridium/contracts/errors.ts` mirror (ARCH-12, amended 2026-09-25). `guards.error-shape.guard` asserts each equality — reading the plan through the spawned script `scripts/read-error-envelope.ts`, never by importing across the package boundary — and that this section carries no copy. Every schema failure on a `ProblemDetails` route, whether a type-provider failure, malformed JSON or a semantic refusal, is `422 validation_failed`; its one other status is the `416` `attachment-range` variant. A `429 rate_limited`'s `X-RateLimit-Limit`, `X-RateLimit-Remaining` and `X-RateLimit-Reset` headers are stated in §1.5's `rate_limited` row, and `409 stale_version` carries no `ETag`: its `current` representation carries the `version` a client rebases on (§1.7).

**Two route families are exempt from this envelope**, and the exemption is derived, never declared a second time. Every response's envelope is one value of the contracts constant `ErrorEnvelope` — `'problem'`, `'mcp'`, `'oauth-json'` or `'oauth-browser'`. A matched route's envelope is `errorEnvelopeOf(route.auth)` (`packages/contracts/src/authz.ts`, beside `OAUTH_ROUTE_SURFACES`): the MCP-mount arm gives `'mcp'`, the OAuth `'client'` and `'registration'` surfaces `'oauth-json'`, the `'browser'` surface `'oauth-browser'`, and every other route, the `'metadata'` and `'absent'` surfaces included, `'problem'` — so the envelope follows the route's own authentication declaration rather than a path prefix, and a query string cannot change it; a method refusal on a known path takes the envelope of the routes registered at that path. A URL that matched no route takes it from the `security/paths.ts` predicates (`isMcpPath` gives `'mcp'`, `isOAuthClientPath` gives `'oauth-json'`, anything else `'problem'`), so a mount or endpoint that `MCP_OAUTH_ENABLED=false` leaves unregistered answers byte-identically to the enabled mode's refusal. A route-scoped refusal on an exempt family — the routing branch's `405` and the Host guard's `421` included — uses that family's envelope whichever layer produces it, while a refusal written before a request exists (`400` for a malformed head, `408`, `431`) is `ProblemDetails` on every path, because no path is attributable (09-api-reference.md §1.4). `authz.route-policy.boot.guard` asserts that every registered route on those paths carries the path-derived envelope, that routes sharing a path share one envelope, and that every envelope a registered route uses has a registered renderer (09-api-reference.md D09-30, amended 2026-09-25).

The **MCP mounts** (`/mcp` and `/mcp/connect`, envelope `'mcp'`) answer every product-layer refusal with the MCP envelope `{"error": <code>, "error_description"?: <text>}`, `Content-Type: application/json` and `Cache-Control: no-store, no-transform`, never `application/problem+json`. `<code>` is a member of the closed contracts constant `McpHttpErrorCode`, each with a fixed status: `400 malformed_request`, `401 invalid_token`, `403 origin_not_allowed`, `403 insufficient_scope` (`/mcp/connect` only), `404 not_found`, `405 method_not_allowed` (with `Allow: POST`), `413 payload_too_large`, `415 unsupported_media`, `421 host_rejected`, `429 rate_limited` (with `Retry-After`), `500 server_error`, `503 mcp_disabled` (`Retry-After: 60`), `503 not_ready` (`Retry-After: 5`), `503 unavailable` (with `Retry-After`: load shedding, or the database unreachable during verification) and `504 deadline_exceeded`. `error_description` is present on every code except `server_error`, whose body is exactly `{"error":"server_error"}` (A32). `401 invalid_token` answers *every* credential failure — missing header, wrong scheme, unknown id, wrong secret, revoked, overlap elapsed, expired, inactive owner, the wrong credential kind for this mount, an audience mismatch, a revoked consent, a disabled client, all deliberately indistinguishable — with `WWW-Authenticate: Bearer realm="iridium", error="invalid_token"`, carrying `resource_metadata` and `scope` on `/mcp/connect`'s challenge and neither on `/mcp`'s; `403 insufficient_scope` carries the matching challenge on `/mcp/connect` when a token carries none of the six read permissions (09-api-reference.md §4.3, §4.6; 06-mcp-and-agent-access.md). Three kinds of answer on those paths are not product-layer answers and keep their own form: the SDK's post-hijack JSON-RPC protocol errors (`400` `-32700`/`-32600`/`-32020`, `404` `-32601`, `406`, `415` `-32000`, and in-band errors at `200`); the SDK host-validation hook's JSON-RPC `403`, which step 3's Host guard makes unreachable end to end; and the refusals `security/client-errors.ts` writes on a raw socket before any request exists (`400` for a malformed head, `408`, `431`), which stay `ProblemDetails` because no path is attributable.

The **OAuth endpoints** have two envelopes. The client endpoints (`/oauth/token`, `/oauth/revoke`, `/oauth/register`, envelope `'oauth-json'`) answer with the RFC 6749 §5.2 object `{error, error_description}` and `Cache-Control: no-store`: the endpoints' own client-authentication and grant errors — `401 invalid_client` with `WWW-Authenticate: Basic realm="iridium"` for a failed Basic attempt or a confidential client presenting no authentication, or with the challenge naming the scheme a non-Basic attempt used (RFC 6749 §5.2) — and every shared-layer refusal, mapped per endpoint: `malformed_request`, `validation_failed` and `unsupported_media` to `400 invalid_request` on token and revoke and `400 invalid_client_metadata` on register, never `415`; `not_found` to `404` with an empty body; `payload_too_large` to `413 invalid_request`; `method_not_allowed` to `405 invalid_request` with `Allow`; `host_rejected` to `421 invalid_request`; `rate_limited` to `429 temporarily_unavailable` with `Retry-After`; `not_ready`, `unavailable`, `busy` and `capacity` to `503 temporarily_unavailable`, keeping `Retry-After`; anything else to `500 server_error` with a defect log. The request schemas of the RFC-defined OAuth endpoints — the `/oauth/authorize` query and the `/oauth/token`, `/oauth/revoke` and `/oauth/register` bodies — are the documented exception to 09-api-reference.md §1.1's `strictObject` rule: they strip unknown request members instead of refusing them (RFC 6749 §3.1/§3.2, RFC 7591 §2), so only a member Iridium understands can fail, and a known parameter sent twice is `invalid_request`. On `/oauth/token` an unsupported `grant_type` is `400 unsupported_grant_type`, and any other failure of a known parameter, a repeated parameter, an unparsable body or a wrong media type is `400 invalid_request`; on `/oauth/revoke` such a failure is `400 invalid_request`, and an unknown `token_type_hint` is ignored; on `/oauth/register` it is `400 invalid_redirect_uri` for a redirect-URI failure and `400 invalid_client_metadata` otherwise (RFC 7591 §3.2.2), and an omitted `token_endpoint_auth_method` is registered as `none` and returned while any other explicit value is refused. None of the three answers `415`, and no exempt family answers `validation_failed`: on the MCP mounts the SDK answers a body it cannot accept with JSON-RPC and every product-layer refusal is the MCP envelope. The browser routes (`/oauth/authorize` and `/oauth/consent`, envelope `'oauth-browser'`) answer a browser with a redirect carrying `error`, `error_description`, `state` and `iss`, or with an HTML error page when the `redirect_uri` could not be validated and a redirect would therefore be an open redirect.

Everything else is `ProblemDetails`, and no `ProblemDetails` response carries `WWW-Authenticate`: the application emits that header only in the MCP mounts' Bearer challenges and in the token and revocation endpoints' client-authentication challenge, and the `ProblemDetails` renderer drops a `WWW-Authenticate` header handed to it and logs a defect. 09-api-reference.md §1.5's rows are therefore what the PAT-enabled ★ REST read routes return for the same conditions (`token_expired` for a well-formed PAT past `expires_at` whose rotation overlap, if any, has not elapsed; `unauthenticated` otherwise, an elapsed overlap included even past `expires_at`, because the verifier checks revocation, then overlap, then expiry, then owner status). `invalid_token`, `insufficient_scope`, `origin_not_allowed`, `mcp_disabled` and `deadline_exceeded` are the five mount-owned `McpHttpErrorCode` members and are deliberately **not** members of the closed `ErrorCode` enum; `OAUTH_ERROR_CODES` is the `/oauth/*` vocabulary — RFC 6749's `invalid_request`, `invalid_client`, `invalid_grant`, `unauthorized_client`, `unsupported_grant_type`, `unsupported_response_type`, `invalid_scope`, `access_denied`, `temporarily_unavailable` and `server_error`, RFC 8707's `invalid_target`, and RFC 7591's `invalid_redirect_uri` and `invalid_client_metadata` — and shares exactly `server_error` with `ErrorCode`. `security.problem-details.unit` asserts those relations between the three vocabularies, and `security.problem.unit` asserts that each renderer emits only its own vocabulary.

The error handler in `security/problem.ts` classifies in this order: `ProblemError` (thrown deliberately by services with a code) → Fastify validation errors → Fastify built-in errors (`FST_ERR_CTP_BODY_TOO_LARGE` → 413, `FST_ERR_CTP_INVALID_MEDIA_TYPE` → 415, `FST_ERR_CTP_INVALID_CONTENT_LENGTH` → 400 `malformed_request` on every path, `FST_ERR_NOT_FOUND` → 404) → `@fastify/rate-limit` errors → everything else → 500. Every hook that refuses — the Host guard, the routing branch and the not-found handler, the `ops/` readiness gate, the CSRF guard and `collab/limits.ts` — does so through the `reply.fail(code, extensions?, variant?)` decorator rather than by writing a body, so a thrown error and a hook refusal pass through the same dispatcher; `sendProblem` is private to `security/` (the `security-problem` row of `RESTRICTED_IMPORT_OWNERS`), and every OAuth limiter's `errorResponseBuilder` returns the same `ProblemError('rate_limited')` for the envelope's renderer to translate. The classification is single and path-independent; the dispatcher in `security/` then renders the classified code through the renderer registered for the request's envelope — `'problem'` by `security/` itself, `'oauth-json'` and `'oauth-browser'` by `oauth/errors.ts`, `'mcp'` by `mcp/errors.ts` — so on the exempt paths the classified refusal is rendered in that path's vocabulary and never flattened to `server_error`, and a code with no counterpart there renders `500` and logs a defect. Unknown errors are logged at `error` level with the stack; the response gets only the request id. Every `4xx` on a mutating route is also visible in the audit or access log where the vocabulary has an entry (`authz.denied`, `token.denied`, `collab.write.rejected`), so a security reviewer never needs the application log to reconstruct a denial.

### Time

All timestamps are set by the application (`clock.now()` injected for tests; never SQL `NOW()` except in the job-claim statement where the database's clock is deliberately the arbiter), stored as `DATETIME(6)` UTC, and rendered on every wire as RFC 3339 UTC with millisecond precision (`2026-09-11T10:12:13.456Z`). `/readyz` fails when the database clock and the process clock differ by more than 30 s (skeleton A49) because ticket expiry, session expiry and cursor expiry compare application timestamps with rows written by other requests.

## Concurrency and transaction discipline

Iridium has exactly two kinds of mutation: **structural** changes to metadata (vaults, memberships, nodes, tokens, jobs, settings), which are serialized by database transactions with explicit version checks, and **content** changes to a note body, which are merged by the CRDT and appended to a per-note log by a single writer. The two never share a transaction and never take each other's locks. Every rule below is architectural: it constrains every service, not only the collaboration code.

### Transaction rules

| Rule | Detail |
|---|---|
| Isolation level | `REPEATABLE READ` (the MySQL default) for every transaction except those whose serialisation comes entirely from explicit record locks on parent rows, which run at `READ COMMITTED` through a helper that owns the isolation level: password-link issuance (04-auth-and-access-control.md §3.3), owner-executed session commands (04 §8.3.1), the credential path (`auth/credential-transaction.ts`, "Lock order" below) and the settings write (`PUT /admin/settings`). At `READ COMMITTED` every statement reads the latest committed rows, so a read taken after the locks that fence its writers is exact, and no gap lock is taken on the non-unique ranges these transactions update beside their inserts. Structural (vault) transactions keep `REPEATABLE READ` with the vault lock as their first statement, so their snapshot is established after it, and a `ContentReadCore` page is one `REPEATABLE READ`, `READ ONLY` transaction. No other module chooses an isolation level; the `FOR UPDATE` locks below, not the isolation level, provide the serialization the plan relies on |
| One helper | Every transaction is opened through `db/transaction.ts` `withTransaction(db, ctx, fn)`. Nested calls are a type error (the inner function receives a `Transaction`, which has no `withTransaction` method), so there is no accidental savepoint nesting |
| Structural transactions start with the vault | `withVaultLock(trx, vaultId)` issues `SELECT id, tree_version FROM vaults WHERE id = ? AND status = 'active' FOR UPDATE` as the first statement of every transaction that touches `nodes`, `vault_members`, `attachments` or `vaults` itself (A12). A vault is therefore the unit of structural serialization: two vaults mutate in parallel, one vault's tree mutates one transaction at a time |
| Optimistic concurrency inside the lock | Every mutable metadata row carries `version`; updates are `… SET version = version + 1 WHERE id = ? AND version = ?` and assert `numUpdatedRows === 1n`. A mismatch is `409 stale_version` with the `current` representation, never a silent retry (A13) |
| Assertions are never optional | Every single-row `UPDATE`/`DELETE` whose correctness depends on matching exactly one row asserts `numUpdatedRows === 1n`. In the persistence writer's `head_seq` CAS a mismatch is a corruption alarm, not a retry (A19): it logs `persist.failed` with `reason:'cas_mismatch'`, increments `iridium_persist_failures_total{reason="cas_mismatch"}` — `cas_mismatch` is therefore a member of that metric's closed `reason` label set — and fires `IridiumPersistCasMismatch` off that series. A zero-row CAS is an application condition, never a MySQL error, so it is never counted in `iridium_db_query_errors_total`, whose `code` label carries MySQL error codes only (11-operations-and-deployment.md) |
| No non-MySQL I/O inside a transaction | No HTTP call, no `StorageDriver` call, no worker dispatch, no WebSocket send happens between `BEGIN` and `COMMIT` (decision ARCH-23). Attachment bytes are written to the store *before* the metadata row commits — content addressing makes an orphan blob harmless and a dangling row impossible |
| Side effects run after COMMIT | `withTransaction` returns `{ result, effects }`; the helper runs `effects` only after a successful COMMIT. `AuthzBus.publish`, `CollabGateway` broadcasts and closes, job enqueues and `SettingsStore.install()` are all effects; an `AccessLogWriter` append comes later still, at its request's one append point (before the response's last byte, or at the socket's close), and its `INSERT` never runs inside a request's transaction. A subscriber can therefore never observe an event whose row does not exist, and a rolled-back transaction cannot revoke a live session. **Noted 2026-09-25:** the tree has no single `withTransaction` helper yet; after-COMMIT effects run through per-module deferred lists over Kysely's `transaction().execute` (`authz/bus.ts`'s `DeferredAuthzEvents`, which `authz.bus-after-commit.unit` proves), and the decision and the tree are reconciled — the helper built, or ARCH-23 amended to the per-module form — before the M3 exit record and no later than M8 |
| Audit is the exception that must be inside | `AuditWriter.record(trx, event)` takes the transaction because the HMAC chain must be gap-free and atomic with the mutation it describes (A46). It is the only writer that is called from inside a transaction by design, and it is always the last statement |
| Retries | `ER_LOCK_DEADLOCK` (1213) and `ER_LOCK_WAIT_TIMEOUT` (1205) are retried up to 3 times with 20–200 ms jittered backoff by `withTransaction`, but only for transactions declared `idempotent: true` (structural operations are, because they re-read and re-check versions inside the transaction). A retry budget exhaustion surfaces as `503 busy` with `Retry-After: 1` on REST (never `capacity`, which is reserved for admission-budget refusals), as `503 temporarily_unavailable` with `Retry-After: 1` on the `oauth-json` endpoints, and as `persist-failed {reason:'db_error'}` on `/collab` (decision ARCH-24) |
| Lock wait timeouts are short | Every pooled connection is initialised with `SET SESSION innodb_lock_wait_timeout = 10` on `dbApp` and `= 5` on `dbPersist`. A writer that cannot get its row lock quickly should fail, back off and retry with the truthful-ack protocol rather than hold a request thread for the server default of 50 s (decision ARCH-24) |
| Advisory locks | `GET_LOCK('iridium_migrate', 60)` wraps a migration run (A7); `GET_LOCK('iridium_note_<id>', 0)` and `GET_LOCK('iridium_jobs_leader', 0)` are reserved for the multi-process path and unused in MVP. Advisory locks are never taken inside a transaction that also holds row locks |

### Lock order

**Lock order is normative**, declared in `02-system-architecture.md` section "Lock order": owner-generation fence → `vaults` (exclusive for structural changes, shared for projection publication) → `nodes` → `notes` → `note_docs` → `note_updates` → `note_projections` → `note_projection_terms` → `note_search` → `note_links` → `note_revisions` → `trash_entries` → `audit_chain_heads`. All serving writes first hold the captured owner-generation fence. Publication takes the known immutable vault id through `lockProjectionVault()` immediately afterward, before any consistent snapshot read or source-note lock, and holds that shared gate through COMMIT. This serializes target lookup with rename, trash and purge while allowing concurrent publishers. Raw update appends and explicit revision checkpoints omit the vault gate. Every note persistence path then locks the source `nodes` row `FOR SHARE`, parent `notes` row `FOR UPDATE`, and `note_docs` row `FOR UPDATE` through `lockNoteParents()`, in that order. Explicit parent locks account for foreign-key locks; joined SQL is not a lock-order guarantee. Audit heads remain last.

Trash fences affected writers, locks subtree node, note and document rows through sorted unique-key point reads under `withVaultLock()` (a small-table `IN (...) FOR UPDATE` scan can lock unrelated keys), and captures a protected durable `trash` revision before marking nodes deleted. It may therefore lock a live note's `note_docs`. Purge validates the trashed subtree and starts synchronous local writer fencing while holding a short vault lock, waits for disposal after releasing it, then reacquires the vault lock and repeats all authorization, CAS and tombstone checks before deleting in FK-safe order. No wait for a publisher holding vault-S occurs under vault-X. Queued writers recheck their local lifetime after acquiring the locked head, so a concurrent restore cannot revive a pre-fence queue. Closing marks are owned and balanced. Authentication/load recheck durable tombstones, and post-COMMIT session closure plus startup reconciliation repair missed notifications. `withVaultLock()` refuses a pre-existing child transaction. `tree.purge-fence.integration`, `projection.target-lifecycle.integration` and `lock-order.integration` prove the critical interleavings against MySQL.

The non-audit derived writes commit in projection, term memberships, search, then link order; `projected_seq` is updated last. CPU projection work runs before the transaction, and only broadcasts run after COMMIT. Existing row locks remain held until COMMIT even when a later statement updates an already-locked parent.

**The credential path** has its own normative order (A46, amended 2026-09-25). It shares the content chain's prefix (the fence, then `vaults`) and its tail (`audit_chain_heads`); below `vaults` the two are disjoint, and a future transaction that needs both takes the content chain's rows first and is recorded here. A credential transaction locks only what it needs, in this order: (1) the owner-generation fence, for serving mutations only — the offline CLI holds no generation and takes none; (2) `vaults`, ascending, `FOR SHARE`: the parents of inserted `oauth_consent_vaults` and `access_token_vaults` rows, and every vault a `--vault` or membership-dependent selection reads; (3) `vault_members`, locked only by member-mutation paths — credential transactions read membership without locking it; (4) `users`, ascending, `FOR UPDATE` for create, rotate and user-scope revoke-all, otherwise `FOR SHARE`; (5) `user_credentials`; (6) `sessions`; (7) `oauth_clients`, ascending, `FOR UPDATE` only to stamp `first_authorized_at` or change `status`; (8) `oauth_consents`, then `oauth_consent_vaults`, re-read `FOR SHARE` after the consent lock; (9) `oauth_authorization_codes`; (10) `oauth_refresh_tokens`; (11) `access_tokens`, then `access_token_vaults`; (12) `audit_chain_heads`, last. `vaults` precedes `users` because membership mutations already lock `vaults` and then bump `users.authz_version`, and every writer that inserts a row under a `vaults` or `users` foreign key takes that parent `FOR SHARE` explicitly, because the foreign-key check would otherwise take the lock late, after rows later in the chain. Every read that decides authorization follows the locks that fence its writers: membership and reach after the step-(2) vault locks (every membership write takes its vault `FOR UPDATE` first), the token name and active-token cap checks after `users` `FOR UPDATE`, the consent's vault selection re-read `FOR SHARE` after the consent lock, and liveness re-checked under the credential row's own `FOR UPDATE`. The whole path runs at `READ COMMITTED` through the one helper `auth/credential-transaction.ts`, so each such read sees the latest committed rows and is exact however many reads preceded it in the transaction: a selection that changed between its plain pre-read and its locking re-read raises `LockSetChanged` and restarts the transaction under ARCH-24's retry budget, and exhaustion raises `busy`, rendered `503 busy` in `ProblemDetails` and `503 temporarily_unavailable` through the `oauth-json` envelope, both with `Retry-After: 1`.

The credential writers follow that order. `POST /me/tokens`: fence; the allowlisted vaults `FOR SHARE`; `users` `FOR UPDATE`; the name check — a name is unique among the owner's `kind='pat'` rows whose derived status is active, with no index, so a rotated predecessor is exempt because its successor carries the name (`409 name_conflict`) — and the `PAT_MAX_ACTIVE_PER_USER` check (`422 token_limit_reached`); the membership check; the token and its `access_token_vaults`; the audit row. A rotation: fence; the successor's allowlisted vaults `FOR SHARE`; `users` `FOR UPDATE`; the old token `FOR UPDATE`; D06-01's checks (a revoked, expired or already rotated token is `409 token_not_rotatable`, so a rotation chain cannot fork) and the membership check; the old row's update, the successor and its vault rows; the audit row. A single-token write (`DELETE /me/tokens/:tokenId`, `DELETE /admin/tokens/:tokenId`, `PATCH /admin/tokens/:tokenId`, `iridium tokens revoke --id`) locks only its `access_tokens` row `FOR UPDATE`, then the audit heads: a create racing it can only count the token as still active, which errs toward `name_conflict` or `token_limit_reached`, never past them (06-mcp-and-agent-access.md D06-50). The consent upsert (Allow, and the silent grant): fence; the granted vaults `FOR SHARE`; `users` `FOR SHARE` (a step-up recorded in the same transaction writes its `sessions` row, step (6), never the `users` row); the client row, read plainly first — on the first Allow for a CIMD `client_id` with no row it is inserted here with `first_authorized_at` set, and a loser on `uq_oauth_clients_live` (1062) or a deadlock (1213) re-runs under ARCH-24 and takes the existing row `FOR SHARE`, re-validating the request's `redirect_uri` and scope against it; a row with `first_authorized_at IS NULL` is taken `FOR UPDATE`, its `status='active'` re-checked and stamped; any other row is taken `FOR SHARE` with `status='active'` re-checked, so the client row is locked exclusively once per client lifetime, not once per authorization — then the consent upsert, `oauth_consent_vaults`, the code insert and the audit row (Allow only). The code exchange and the refresh grant: plain pre-reads of the code or refresh row and of the consent's selection, then the fence; the selected vaults `FOR SHARE`; `users` `FOR SHARE`; the client `FOR SHARE`; the consent `FOR SHARE`; a locking re-read of the selection; the code or presented refresh row `FOR UPDATE`; the family's refresh rows `FOR UPDATE` (rotation and reuse detection); the inserts; the audit row — each refusing a non-active client under the lock. Revocations (consent revoke, revoke-all, client disable and retire): the fence; `users` `FOR UPDATE` for a user-scope revoke-all, which serialises with create and rotate, and otherwise only when the operation changes the user row; the client row `FOR UPDATE` for a client cascade; the consents, refresh rows and access tokens `FOR UPDATE`; the audit row — they insert nothing under a `users` or `vaults` foreign key and take no shared parent locks. `POST /oauth/revoke` (RFC 7009): the fence; the grant's consent `FOR SHARE` when only an access token is revoked, `FOR UPDATE` when a refresh token revokes its family; that family's refresh rows; the access tokens `FOR UPDATE` — it writes `revoke_reason='client_revoked'` and no chained row, so it takes no audit heads (06-mcp-and-agent-access.md D06-50). A replayed code or a reused refresh token revokes, in the same transaction, the family's refresh rows and then its access tokens, each in ascending id. The unused-client sweep takes each row `FOR UPDATE` and re-checks its predicate before the `DELETE`. The `LastUsedTracker` flush takes only the chain's tail through the same helper: `oauth_consents.last_used_at`, advanced with `GREATEST`, in ascending consent id, then the `access_tokens` last-used columns in ascending id (06-mcp-and-agent-access.md D06-49). `GET /oauth/authorize` is the one `GET` that mutates, because a silent grant mints a code, so `rest/ownership.ts` captures the fence for route id `oauth.authorize` by name and `authz.route-policy.boot.guard` asserts that the set of mutating `GET` routes is exactly that one. `lock-order.integration` carries the credential races, under the oracle 10-testing-and-quality.md fixes for the file (no `ER_LOCK_DEADLOCK`, no lock-wait timeout): consent Allow against a membership change on the same vault and user; code exchange against a membership change and against client disable; refresh against consent revoke and against client disable; refresh reuse against consent revoke; token create, rotate and revoke-all at every scope, including `iridium tokens revoke-all --user --vault` against a membership add, a role change and a removal of that user in that vault; a server-scope revoke-all against a refresh and against client disable; single-token revoke against create and against rotate; token create or rotate against a membership add, a role change and a removal of the owner in an allowlisted vault; the last-used flush against consent revoke (D06-49, D06-50); silent grants for one CIMD client from eight users against concurrent exchanges and refreshes; concurrent first Allows for one CIMD client, which create exactly one `oauth_clients` row; and the sweep against a first authorization. It also proves read exactness: a refresh and a code exchange, each racing a re-consent that narrows the selection, mint an access token whose `access_token_vaults` equal the selection committed when they locked the consent, never a deselected vault; and a rotate racing the removal of the owner's membership in an allowlisted vault is either refused `422 vault_not_member` or commits before the removal, never creating a successor that allowlists the lost vault.

**Settings writes** lock the owner-generation fence → `schema_meta` `server_settings_version` (a record lock on an existing row, never a gap lock) → `server_settings` → `audit_chain_heads`, at `READ COMMITTED`; no other path locks `server_settings`, and the store's `load()` and `refresh()` take no locks (A46, amended 2026-09-25).

### What runs where

| Work | Thread / context | Concurrency control |
|---|---|---|
| REST handler | main event loop, `dbApp` | one transaction per request; vault lock for structural changes |
| `Y.applyUpdate` into a loaded document | main event loop | Yjs documents are single-threaded; Hocuspocus serializes message handling per connection, and the document is a single in-memory object |
| Note append | main event loop, `dbPersist` | one `NoteWriter` per note, strict FIFO, at most one in-flight transaction per note; global concurrency capped at `DB_POOL_PERSIST` with round-robin scheduling so no note starves (A21) |
| Compaction | enqueued into the *same* per-note FIFO as appends, awaited by `onStoreDocument` while Hocuspocus holds its `saveMutex` | ordering with appends is structural, not advisory: a compaction can never interleave with an append of the same note (A16) |
| Markdown projection | `projectionPool` worker thread | pure function of `(markdown, revision)`; writers guard with `WHERE revision < ?` so an older projection can never overwrite a newer one |
| Import scan / export build | `transferPool` worker thread | one job row claimed by one process; import commit is one transaction per note with an `initialized_at` guard, so a resumed commit is idempotent |
| Scheduled maintenance | main event loop, `dbApp` | `jobs` row claim with `locked_by`/`locked_at`; expired claims are reclaimable |
| CLI command | a separate short-lived process against the same database | takes the same locks in the same order (on the credential path it takes no owner-generation fence, because the offline CLI holds no generation); mutations audited with `credential_type='cli'` |

Two operational consequences follow, and both are measured: the only unbounded queue in the system is the per-note writer queue, which is bounded at 5 000 updates or 32 MiB before it turns the document read-only (A21); and the only work that can block the event loop for longer than a database round trip is `Y.applyUpdate` on a 1 MiB update, which the message cap makes the worst case.

## Architectural invariants and their guard tests

An architectural rule that no test enforces is a comment. Every invariant this section establishes is therefore paired with an automated check; the test names belong to 10-testing-and-quality.md, which owns their configuration, and are listed here so an implementer can see that each rule is falsifiable.

### How this architecture is built up

The component set above is not delivered all at once; the order is owned by 12-milestones.md, and the architectural reading of it is that every milestone adds a *surface* to an already-proven core rather than a new core:

| Milestone | Architectural addition |
|---|---|
| M0 | Repository, boundaries, harnesses, the spikes that de-risk `onLoadDocument` V2 application, the Electron WebSocket `Origin` question and the k6 Yjs generator |
| M1 | `buildApp`, config, db, security, auth, authz, audit, `/collab` with the persistence pipeline, readiness, drain — the whole vertical for one note, headless |
| M2 | `tree/`, `notes/`, `projection/`, `search/`, revisions — structural concurrency on top of the proven kernel |
| M3 | `mcp/` plugin on both mounts, the single token verifier dispatching on credential kind, the `oauth/` plugin (authorization server, metadata documents, server-rendered consent page), `ContentReadCore` consumers, the stdio bridge |
| M4 | `@iridium/ui` + `apps/web`, the `vault:<id>` channel, `IridiumHost` in its `BrowserHost` binding |
| M5 | `apps/desktop`, the second `IridiumHost` binding, main-process credential custody |
| M6 | `transfer/`, `attachments/` UI, the Obsidian report |
| M7 | Admin surface over the already-existing services |
| M8 | Operations hardening: backup/restore verification, alert rules, release pipeline |

No milestone introduces a new process, a new datastore, a new authentication path or a second read model. The OAuth 2.1 authorization server of M3 is not an exception: it issues a second *credential kind*, which resolves through the same `verifyToken`, produces the same `TokenPrincipal` and is authorized by the same unchanged `authorize()` — a branch on `tokenKind` inside `authz/` would be a defect, and `oauth.principal-parity.prop` is the test that says so. That is the property this section exists to protect.
