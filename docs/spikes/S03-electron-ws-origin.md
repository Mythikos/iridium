# S03 — WebSocket and `fetch` `Origin` from an `app://iridium` renderer

## Question

What `Origin` header does the server receive from `new WebSocket('ws(s)://…/collab')` and from
`fetch()` issued by a renderer loaded from `app://iridium/` in Electron 44.3.0, in dev
(`http://127.0.0.1`) and over TLS — and do sub-pages of the SPA keep the same origin?

## Why it blocks

`security.ws-origin.integration` rejects an absent or unexpected `Origin` on the `/collab` upgrade
with **no bypass knob**, because CSWSH is in the threat model (13-decision-log.md A24;
04-auth-and-access-control.md §"Absent `Origin` is rejected, with no bypass switch", threat T9). The
allowlist contains the literal string `app://iridium`. If a renderer on that scheme sends nothing, or
sends `null`, or sends a spelling with a trailing slash or a path, the desktop client cannot connect
and the policy must not be weakened to fix it.

The verdict decides code shape, not architecture: it determines whether `@iridium/collab-client` must
expose `webSocketFactory` and whether `ElectronHost` defines `collab.webSocketFactory`
(07-client-applications.md §7.10, §7.3's host-capability table), whether
`packages/contracts/src/desktop-ipc.ts` registers `collab:open|send|close` with the matching
`iridium:event:collab-message|collab-close` events, and whether
`desktop.ipc-websocket-fallback.e2e` is registered at all (10-testing-and-quality.md). All of that is
written at M5, so M0 owes it an answer. S3 does not gate M1 (12-milestones.md §4.4).

## Method

Harness: `apps/desktop/spikes/s03/`, run with

```
node apps/desktop/spikes/s03/run.mjs [--workdir <dir>]
```

The runner exits `0` when every observation is exactly `app://iridium` and writes the full event log
(every request, every renderer event, the certificate verification, the version block) to
`<workdir>/results.json`.

**Listeners** (`server.mjs`), all bound on `0.0.0.0` with an ephemeral port, none of which rejects
anything, because the question is what the client sends:

| Target | Transport | Purpose |
|---|---|---|
| `plain-loopback` | `http://127.0.0.1` + `ws` 8.21.3 on `/collab` | the register's dev shape; logs `request.headers.origin` on upgrade and on `GET /meta`, completes the handshake, round-trips a binary frame, closes with `4001` |
| `tls-loopback` | `https://127.0.0.1` + `ws` 8.21.3 | the register's TLS shape; self-signed certificate (`CN=127.0.0.1`, SAN `IP:127.0.0.1,DNS:localhost`) generated by `openssl` into the work directory |
| `raw-plain` | bare TCP, handshake written by hand | records the **literal bytes** of the request head. Node's HTTP parser consumes the socket handle, so no `data` listener on an `http.Server` socket can observe an upgrade's bytes; this listener computes `Sec-WebSocket-Accept` itself and answers with a `4001` close frame |
| `raw-tls` | bare TLS, same | the same byte-level evidence over TLS |
| `plain-lan` | `http://<LAN IPv4>` (same listener as `plain-loopback`) | not part of the register row: a non-loopback plain-HTTP origin, to see whether the secure `app://iridium` context treats it as mixed content |

**Shell** (`main.mjs` + `pages/`): an Electron main process that reproduces the load-bearing parts of
`apps/desktop/src/main/` — the `app` scheme privileges of `scheme.ts` (`standard`, `secure`,
`supportFetchAPI`, `corsEnabled`, `stream`, `codeCache`), `app.enableSandbox()` before `ready`, the
hardened `webPreferences` of `web-preferences.ts` including the `persist:iridium` partition, the
scheme handler's traversal guard, SPA fallback and per-load nonce substitution, and the `packagedCsp()`
shape of `csp.ts`. It loads `app://iridium/` and the page issues one `fetch()` and one `WebSocket` per
target.

Two deliberate deviations, both forced and both recorded here rather than hidden:

1. **The shell is mirrored, not imported.** `apps/desktop/src/main/main.ts` hard-codes
   `activeServerOrigin = null` until profiles arrive at M5, which makes the per-load CSP
   `connect-src 'none'`; the M0 shell as built cannot be pointed at any server, so the register's
   method ("the M0 desktop shell pointed at the S2 server") is not executable against it. The harness
   supplies the harness servers where `packagedCsp()` will name the active profile, and changes
   nothing else.
2. **The self-signed certificate is pinned, not ignored.** `setCertificateVerifyProc` accepts exactly
   the harness certificate's PEM for host `127.0.0.1` and defers everything else to Chromium —
   the same shape as the M5 per-profile fingerprint pin. Neither `--ignore-certificate-errors` nor
   `webSecurity: false` is used; either would have invalidated the result (and both are banned by the
   CI greps of 07-client-applications.md §7.4).

**Legs.** Four, five document loads in total, every leg probing every target:

| Leg | Document URL |
|---|---|
| `root` | `app://iridium/` |
| `subpage-navigated` | `app://iridium/vault/notes/deep/child`, served through the SPA fallback |
| `subpage-pushstate` | `app://iridium/` then `history.pushState(…, '/vault/notes/deep/child')` before probing |
| `root-reload` | `app://iridium/`, probed, then `webContents.reload()` and probed again |

## Result

**pass**, on the operating system this machine can run for real.

**Every one of 50 request observations carried `Origin: app://iridium`.** That is 5 targets × 2
request kinds (`fetch`, WebSocket upgrade) × 5 document loads, with zero renderer-side failures.

| Measurement | Value |
|---|---|
| Request observations | 50 |
| Observations whose `Origin` was exactly `app://iridium` | 50 / 50 |
| Observations with the header absent, empty or `null` | 0 |
| Distinct `Origin` values received across all targets and legs | 1 |
| `Origin` header value, hex | `4f726967696e3a206170703a2f2f6972696469756d` — `Origin: app://iridium`, 21 bytes: no trailing slash, no port, no path |
| CORS preflights triggered | 0 |
| Binary frames round-tripped over the `ws` targets | 15 |
| Close code / reason delivered to the renderer | `4001` / `spike-s03` (and `spike-s03-raw` from the raw listeners) on 25 / 25 sockets |
| TLS certificate verifications | 1 (pinned; Chromium's own verdict was `net::ERR_CERT_AUTHORITY_INVALID`, and the result is cached per session) |
| `fetch` latency | 1–17 ms |
| WebSocket open → close round trip (`ws` targets) | 2–5 ms |

**Sub-pages keep the origin.** In the navigated leg the document URL was
`app://iridium/vault/notes/deep/child` and in the pushState leg it became the same path in place;
`location.origin`, `window.origin` and `document.location.origin` were `app://iridium` in every leg
and phase, `isSecureContext` was `true`, `crossOriginIsolated` was `false`. The `Origin` the server
received never carried the path: a custom `standard` scheme serialises its origin as scheme + host,
and `app://iridium` has no port component to vary. The reload leg was byte-identical to the first
load.

**Shape of the request, beyond the one header.** The upgrade carries no `Sec-Fetch-*` metadata and no
cookie; `fetch` to a loopback target carries `Sec-Fetch-Site: cross-site`, `Sec-Fetch-Mode: cors`,
`Sec-Fetch-Dest: empty`, and to the non-trustworthy LAN target no `Sec-Fetch-*` at all. So
`Sec-Fetch-Site` cannot distinguish the desktop client from a cross-site attacker on the upgrade
path — `Origin` is the only discriminator, which is what A24 already assumes.

**Two ancillary measurements**, outside the register row but decided by code the shell already ships:

- A same-origin `fetch('/probe.js')` from `app://iridium` was **blocked in 5 / 5 loads**, with a
  `securitypolicyviolation` whose `effectiveDirective` was `connect-src`. `packagedCsp()` builds
  `connect-src` from the active profile alone and never adds `'self'`.
- The plain-HTTP non-loopback target (`http://<LAN IPv4>`) was **not** blocked as mixed content: all
  10 of its requests reached the listener from the `secure: true` `app://iridium` context.

**Untested here.** This machine is Windows only.

|---|---|

| `ubuntu-latest` (xvfb) | untested here — carried by the `e2e-electron` job (`ci.yml`, matrix `ubuntu-latest`, `windows-latest`, `macos-latest`, merge-blocking, `--grep @smoke`), see Follow-ups |
| `macos-latest` | untested here — same job |

## Decision

The desktop renderer opens `/collab` directly, so `ElectronHost` does not define
`collab.webSocketFactory`, `@iridium/collab-client` needs no `WebSocketPolyfill` seam for the desktop,
the `collab:open|send|close` IPC channels and the `iridium:event:collab-message|collab-close` events
are not registered, and the server's Origin allowlist keeps the literal `app://iridium` with
"absent `Origin` → 403, no bypass knob" unchanged.

## Fallback executed

n/a — the pass criterion is met on the measured leg, so the `IpcWebSocket` fallback of A53 stays
designed and unbuilt: no `WebSocketLike` shim, no `net.WebSocket` in main, no `wss:`-free CSP variant,
and `desktop.ipc-websocket-fallback.e2e` is **not** registered at M5. If the `e2e-electron` assertion
of Follow-up 1 shows either remaining operating system deviating, that spike row reopens and the
fallback is executed in the milestone that finds it, per the register.

## Follow-ups

1. **Close the two untested operating systems with a test, not a promise.** Add to
   `apps/e2e/electron/desktop.launch.e2e.spec.ts` — which exists from M0 precisely so the lane is
   never empty, and carries `@smoke` — an assertion that a renderer at `app://iridium/` sends
   `Origin: app://iridium` to a listener the spec starts, on both the upgrade and a `fetch`. That
   spec runs in `e2e-electron` on `ubuntu-latest` (xvfb), `windows-latest` and `macos-latest` on every
   pull request, which is what converts this note's Windows-only evidence into a standing three-OS
   guarantee. The packaged variant belongs in `release.packaged-smoke.e2e` (`release.yml`).
2. **Re-score the register rows.** R-T14's Origin half is observed-good on Windows and still
   unobserved on Linux and macOS until Follow-up 1 lands; ASM-24's clause "a packaged `app://iridium`
   page sends `Origin: app://iridium`" is confirmed unpackaged on Windows.
3. **Correct 04-auth-and-access-control.md §"The Electron contingency".** It names the spike
   `spike-electron-ws-origin` and its note `docs/spikes/electron-ws-origin.md`; the register's id is
   S3 and the path is `docs/spikes/S03-electron-ws-origin.md`. The same paragraph describes the
   fallback as "main opens the socket with the `ws` library and an explicit `Origin: <PUBLIC_ORIGIN>`",
   which contradicts both A53 and the register row ("main opens `net.WebSocket` with
   `Origin: app://iridium`") in two places — the library and the header value. The fallback is not
   being built, but the contradiction should not outlive this note.
4. **The register's method for this row was not executable.** "The M0 desktop shell pointed at the S2
   server" presumes a way to give the M0 shell a server origin; `activeServerOrigin` is hard-coded
   `null` until M5 and there is no environment variable or IPC that sets it, so the shell's own CSP
   (`connect-src 'none'`) refuses every outbound request. Any future spike that needs the shell to
   reach a server needs the same mirror the harness uses, or an M5 profile.
5. **Decide whether `connect-src` should include `'self'`.** Measured above: the renderer cannot
   `fetch()` an asset of its own origin. Nothing in M0 does, but a JSON manifest, a `.wasm` module
   fetched by a worker, or a source map requested at runtime would fail with a CSP violation rather
   than a 404, and the failure mode is a bare `TypeError: Failed to fetch`.
6. **A custom privileged scheme does not get mixed-content blocking.** The `connect-src` the profile
   generates is therefore the only thing keeping the desktop renderer off plain HTTP on a routable
   address. M5's profile layer should refuse an `http://` profile origin that is not loopback, rather
   than relying on Chromium to refuse the connection.
7. **`base: './'` plus the SPA fallback is a trap for genuinely navigated deep paths.** A document
   served by the fallback at `/vault/notes/deep/child` resolves `./asset.js` against that path, and
   the scheme handler answers with `index.html` under the asset's content type; the harness page uses
   an absolute `/probe.js` for this reason. The desktop renderer routes with `createMemoryHistory`, so
   its document URL never leaves `app://iridium/` and this cannot bite today — it would the first time
   a history-based router or a deep link restores a sub-path URL.
