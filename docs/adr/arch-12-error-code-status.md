# ARCH-12: error codes, statuses and the normative envelope

Status: accepted (2026-09-11); amended 2026-09-25: 09 §1.4 and §1.5 are the single normative `ProblemDetails` schema, code→status table, variant list and OAuth vocabulary; there is no `instance` member; `validation_failed` is `422` on every `ProblemDetails` route, with the `416` attachment-range variant; the RFC-defined OAuth endpoints strip unknown members and never answer `415`; `409 stale_version` carries `current`, not an `ETag`.

**As accepted.** `ProblemDetails.type` is `urn:iridium:problem:<code>`; `instance` is the request path; `errors[]` accompanies `validation_failed`; `X-Request-Id` is echoed on every response; the code→status table is normative and adds six codes to skeleton D.1: `unauthenticated` (401), `node_trashed` (409), `token_not_rotatable` (409, D06-01), `host_rejected` (421), `not_ready` (503) and `busy` (503). That table and the closed `ErrorCode` enum in `@iridium/contracts/errors.ts` are the same set; a test asserts every code thrown by `apps/server/src` is in the enum, and no surface invents a synonym — "up but not serving" is always `not_ready`, lock contention is always `busy`, and admission-budget refusal is always `capacity`. Two route families are exempt: the MCP mounts with their OAuth-shaped `{error, error_description}` bodies, and the OAuth endpoints with their RFC 6749 §5.2 bodies. RFC 9457 wants a stable `type`; a URN never depends on the deployment's hostname; one code per condition is what makes the closed-enum test and the generated error vocabulary satisfiable.

**Amended 2026-09-25.**

- **One normative copy of each artefact, in 09.** 09 §1.4's `ProblemDetails` block — RFC 9457's `type`, `title`, `status` and `detail` without `instance`, the two required Iridium members `code` and `requestId`, and exactly D09-2's four optional extensions (`current`, `errors`, `references`, `retryAfterMs`) — equals `ProblemDetails`. 09 §1.5's code→status table equals `ERROR_CODE_STATUS`. A §1.5 table "Enumerated status variants" equals `PROBLEM_VARIANTS`: `attachment-range` (`validation_failed`, 416, an unsatisfiable `Range`) and `attachment-missing` (`server_error`, 503, an attachment row whose bytes are missing, never 404). A §1.5 table "OAuth error values" equals `OAUTH_ERROR_CODES`, the `/oauth/*` vocabulary of thirteen values: RFC 6749's `invalid_request`, `invalid_client`, `invalid_grant`, `unauthorized_client`, `unsupported_grant_type`, `invalid_scope`, `unsupported_response_type`, `access_denied`, `server_error` and `temporarily_unavailable`, RFC 8707's `invalid_target`, and RFC 7591's `invalid_redirect_uri` and `invalid_client_metadata`; it shares exactly `server_error` with `ErrorCode`. `invalid_token`, `insufficient_scope` and `mcp_disabled` are members of `McpHttpErrorCode`, whose table is 09 §4.6, and `unsupported_token_type` is never emitted, because both token types Iridium issues are revocable. 02 "Error envelope" references 09 instead of carrying copies; of the header facts only 02's table carried, `X-RateLimit-*` on `429` moves to §1.5's `rate_limited` notes, and the `ETag` on `409 stale_version` is dropped, because `current` carries the `version` a client rebases on.
- **`validation_failed`** is `422` on every route that answers `ProblemDetails`, whether the cause is a type-provider failure, malformed JSON or a semantic refusal; its only other status is the `416` `attachment-range` variant. The OAuth and MCP families never answer it.
- **The RFC-defined OAuth endpoints.** The request schemas of `/oauth/authorize` (query), `/oauth/token` and `/oauth/revoke` (form) and `/oauth/register` (JSON) are a documented exception to 09 §1.1's `strictObject` rule: they are `z.object`, so unknown members are stripped and ignored (RFC 6749 §3.1 and §3.2, RFC 7591 §2), and a known parameter sent more than once is `invalid_request`. `/oauth/token` answers a missing `grant_type` with `400 invalid_request`, an unsupported one with `400 unsupported_grant_type`, and any other known-parameter, repeated-parameter, body-parse or media-type failure with `400 invalid_request`. `/oauth/revoke` answers a missing `token`, an unparsable body or a wrong media type with `400 invalid_request` and ignores an unknown `token_type_hint`. `/oauth/register` answers any `redirect_uris` failure with `400 invalid_redirect_uri` and every other failure of an understood member, an unparsable or non-object body or a wrong media type with `400 invalid_client_metadata`; it registers an omitted `token_endpoint_auth_method` as `none` and returns it (RFC 7591 §3.2.1) and refuses any other explicit value. None of the three client endpoints answers `415`. `/oauth/consent` is Iridium's own form and stays strict; `/oauth/authorize` and `/oauth/consent` answer with the error page or error redirect. On the MCP mounts the SDK answers a body it cannot accept with JSON-RPC, invalid tool arguments get the in-band `-32602`, and every product-layer refusal is the MCP envelope (D09-30 as amended).
- **Plan parity.** `guards.error-shape.guard` asserts each equality — the code table, the variants, the OAuth values, the `McpHttpErrorCode` table, the block's members, and that 02 carries neither copy — through `scripts/read-error-envelope.ts`, spawned under `process.execPath` rather than imported across the package boundary, and proves in-file that it refuses a mismatched row, a missing variant and a second copy in 02.

Rejected: `400` for schema failures, which gives one code two statuses; two normative copies; `invalid_request` on `/oauth/register`; strict OAuth request schemas, which refuse what the RFCs require the server to ignore; `415` on the OAuth client endpoints; an undelivered `ETag` in the normative table.

Verification: `guards.error-shape.guard`, `security.problem-details.unit`, `security.problem.unit`, `oauth.token-endpoint.integration`, `oauth.revoke-endpoint.integration` and `oauth.dcr.integration`.
