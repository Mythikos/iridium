# ARCH-10: environment floors and the settings store's lifecycle

Status: accepted; amended 2026-09-25: the store installs whole snapshots by document version, loads consistently, is loaded first by its fail-closed readiness check and refreshed on every readiness evaluation, throws before its first load, and is never fatal to the process; post-MVP a fan-out installs snapshots in every process with the refresh as backstop.

**As accepted.** Environment values for editable policy are floors of strictness: `SettingsStore` computes `tighten(envFloor, adminValue)` per field and rejects laxer admin values with `422 validation_failed`; retention floors are minimums; the store is reloaded after every settings COMMIT. Admin policy is always read from the store in memory, never re-queried per request — including `server_settings.mcp_enabled`, which `mcpKillSwitch` evaluates as `SettingsStore.effective().mcp_enabled`; `PUT /admin/settings` is the row's only writer and its `reload()` is a post-COMMIT effect of the same request, so "effective on the next call" holds without a `SELECT` per `/mcp` call, and a direct `UPDATE server_settings` is by definition invisible to the running process. This gives the skeleton's "env values are floors" (A26) an exact, testable meaning that never lets a console user weaken what the operator deployed, and naming the read source once stops other sections from specifying a per-request query.

**Amended 2026-09-25.**

- **The merge.** The per-member merge is `settings/merge.ts`, driven by `SERVER_SETTING_RULES` through the contracts helpers `stricterOf` and `isWeakerThanBaseline` (D03-28); no `tighten()` exists. Consumers read the camelCase `ServerSettings` shape, `effective().mcpEnabled.enabled` and `effective().oauthPolicy.*`, never row keys.
- **Install.** Every `PUT` installs the complete snapshot it read under the validator lock, with its version (D09-10 as amended); `install(snapshot, version)` replaces the whole snapshot when the version is greater than or equal to the installed one and ignores a lower one. A later effective write always carries a strictly greater version, so an out-of-order continuation can never regress a group or the version, and an equal version carrying different rows (a DBA repair) lets the fresher read win. There is no re-read after COMMIT.
- **Construction and first load.** `settings/plugin.ts` runs at boot step 2, after the database plugin, and only constructs the store and decorates `app.settings`. The first load is performed by the readiness check `server_settings`, appended after `access_log_partitions` and fail-closed (OPS-24, D09-11 as amended), once `migrations` records `current` or a tolerated `newer_schema`. `load()` reads the validator and every row inside one read-only `REPEATABLE READ` transaction, so snapshot and version always come from one committed state, and checks the validator and every row and key. Until the first load succeeds, `effective()` throws `SettingsNotLoadedError` and the check fails with a named detail — waiting for the database, waiting for migrations, a newer schema not tolerated, a redacted load failure, a missing or regressed validator with its remedy, or an invalid row with its key and remedy — so no route is admitted and no fabricated policy is ever observable. In database mode `none` the store loads the empty set at version 0, the baseline policy, and the check is `ok`.
- **Refresh.** After the first load, each readiness evaluation (boot, every `READINESS_RECHECK_MS` re-check and every `GET /readyz`) re-reads `schema_meta 'server_settings_version'` by primary key and reloads when it exceeds the installed version; an equal value does nothing. A refresh that cannot complete — an outage, an invalid row, a missing or regressed validator — keeps the installed snapshot enforced and reports `warn`, naming the version enforced and the failure; an invalid row found after load logs `settings.row_invalid`. The check never fails again after the first load. A direct change to `server_settings` is therefore invisible until the validator is raised above the installed version, which the next evaluation observes, or until a `PUT` reads the table.
- **Never fatal.** Settings rows are database state: an invalid row keeps the check failing before the first load and warning after it, and never exits the process, following `boot/db.ts`'s doctrine that only configuration is fatal. `settings.row_invalid`, `settings.validator_invalid` and `settings.newer_schema_tolerated` join `LOG_EVENTS`, logged when first seen and again only when the key or reason changes.
- **Rolling restart.** A successor loads while its predecessor still serves, but it is not ready until its `collab_owner_lease` check acquires the lease, which publishes the new owner generation only after every predecessor transaction holding the fence has committed — every settings `PUT` takes the fence first. The `server_settings` check runs after `collab_owner_lease` in the same evaluation, and admission stays closed until that evaluation ends, so the successor's first admitted request enforces every `PUT` its predecessor committed.
- **Multi-process (post-MVP seam).** A `settings.changed` fan-out carrying `(snapshot, version)` calls `install()` in every process, so a server-wide switch stays a next-call property everywhere (06 "Kill switches"); the validator refresh remains the bounded backstop for a missed message.

A store that never re-reads once loaded would leave a rolling-restart successor enforcing a stale snapshot and make an operator's validator repair inert. A store that throws before its first load, behind a fail-closed check, fabricates no policy an in-process caller could read. Rejected: a store that never re-reads once loaded; replacing the fan-out with the refresh alone, since a poll cannot keep a server-wide switch a next-call property across processes serving at once; fail-closed defaults installed before the first load; exiting the process over an invalid row.

Verification: `readyz.integration` (an unloaded store fails the check and throws; database mode `none` is `ok`; a failed refresh warns and keeps the snapshot; the rolling-restart successor enforces its predecessor's `PUT`), `admin.settings.integration` and `settings-store.contract`.
