# OPS-65: the bridge download is built into the server image and served from M3

Status: accepted 2026-09-25. Carries the operational half of the D06-14 amendment of the same date ([d06-14-bridge-distribution.md](./d06-14-bridge-distribution.md)).

**Build.** `infra/docker/server.Dockerfile` declares global `ARG`s `NODE_IMAGE` (`node:24.21.0-bookworm-slim`), `PNPM_VERSION` and `TURBO_VERSION` before the first `FROM`, used by every stage including the server's, so one pin serves every `FROM` and every tool install. The bridge is built once, on the build platform, whatever the target list: `bridge-base` is `FROM --platform=$BUILDPLATFORM ${NODE_IMAGE}` and repeats the base stage's pnpm setup, because a stage based on another stage would inherit the per-target platform; `bridge-prune` runs `turbo prune @iridium/mcp-bridge --docker`; and `bridge-build` fetches and installs frozen and offline from the pruned lockfile, keeping `turbo prune --docker`'s two-phase cached install, runs `pnpm turbo run build --filter=@iridium/mcp-bridge`, and asserts that `dist` holds exactly `iridium-mcp.mjs`, that its first line is `#!/usr/bin/env node`, that its second line is `// iridium-mcp <v>` with `<v>` the version in `packages/mcp-bridge/package.json`, and that `node dist/iridium-mcp.mjs --version`, run from an empty directory, prints that version. `packages/mcp-bridge/tsdown.config.ts` bundles every dependency with `deps: {alwaysBundle: [/.*/]}` — only `node:` builtins stay external, so no chunk file is emitted and the file runs alone — turns sourcemaps off and writes that two-line banner from the package manifest at build time, the same value `--version` prints. The runtime stage copies the file as a root-owned `0444` file into a `0555` `/app/tools`, so uid 10001 cannot rewrite it, sets `ENV IRIDIUM_TOOLS_DIR=/app/tools`, and asserts, beside the existing `iridium version --json` check, that `node /app/tools/iridium-mcp.mjs --version` equals the server's version.

**Configuration.** `EnvSchema` gains `IRIDIUM_TOOLS_DIR`, an optional path; unset means no bridge route. When it is set, the directory contract is one fixed file, `iridium-mcp.mjs`, whose banner version must equal `BUILD_INFO.version` — a content check, stronger than a file name. The pure `loadToolsBundle(dir, serverVersion)` validates it at configuration load, at boot step 1 and in `iridium config check`, and returns a discriminated outcome; anything but `ok` is a `ConfigError` in `CONFIG_ERROR_CODES` with keys `['IRIDIUM_TOOLS_DIR']` and exits 2 naming the path and the remedy: `config.tools_bundle_missing` for a missing, empty or non-regular file, and `config.tools_bundle_version_mismatch` for a second line that is not `// iridium-mcp <semver>` or a version that differs from the server's, naming the version found (or `none`) and the server version. `apps/server/src/rest/desktop-tools.ts` builds the three-name table at boot step 8 from a re-verified read, and the server holds the bytes and their SHA-256 in memory, so no request reaches the filesystem. Failing closed is deliberate, unlike `IRIDIUM_WEB_DIR`'s warn-and-serve-nothing: the image always bakes the file, so its absence is a build defect; an absent or mismatched file would be published under a version it is not and vouched for in `SHA256SUMS`; and unset already means "no download".

**Serving.** The rest plugin registers one hidden route, `GET /desktop/tools/*` (`desktop.tools.static`; `config.auth {public: true}`; `schema.hide`; no `API_ROUTES` row and no OpenAPI operation, following `app.static`). It serves three names fixed at boot. `iridium-mcp-<serverVersion>.mjs` returns the bytes as `application/octet-stream` with `Content-Disposition: attachment; filename=iridium-mcp-<version>.mjs`, `X-Content-Type-Options: nosniff`, a strong `ETag` `"<sha256 lowercase hex>"` equal to the hash `SHA256SUMS` publishes, and `Cache-Control: public, max-age=60`; a matching `If-None-Match` gets `304` with the `ETag`, the same `Cache-Control` and no body. It is never marked `immutable`, because a version name can carry a re-cut build and nothing refuses that as `409` refuses a re-published desktop release. `iridium-mcp-latest.mjs` answers `302` to the versioned name with `Cache-Control: no-store`. `SHA256SUMS` returns one `sha256sum`-format line, `<hex>  iridium-mcp-<version>.mjs` and a LF, with exactly the headers of `/desktop/updates/<channel>/SHA256SUMS` (`09-api-reference.md` §2.16): `Content-Type: text/plain; charset=utf-8` and `Cache-Control: public, max-age=60`. Any other name gets `404` with an empty body, because static surfaces are not ProblemDetails (09 §1.4).

**Release.** `release.yml › bridge` (M3 and later) runs in this order: pull both platform variants of the release digest; extract `/app/tools/iridium-mcp.mjs` from each into `$RUNNER_TEMP` and assert the two are byte-identical; assert the banner version equals the release version; run `bridge.parity.contract` by path, without `--passWithNoTests`, with `IRIDIUM_TEST_SERVER_MODE=container`, `IRIDIUM_TEST_SERVER_IMAGE=<release digest>` and `IRIDIUM_TEST_BRIDGE_BUNDLE=<the extracted file>` (D10-5), executed from a scratch directory outside the workspace so module resolution cannot fall back to the repository's `node_modules`; check that the served `SHA256SUMS` and the versioned name's `ETag` both equal the file's hash; upload the file as `iridium-mcp-<version>.mjs`; and compare `RELEASE_MIN_CLIENT_VERSION` with the previous tag (A54). M5 adds only the desktop copy: `release.yml`'s desktop job places the image-extracted release artefact in `extraResources` and asserts byte identity, while pull-request and local desktop builds copy `packages/mcp-bridge/dist/iridium-mcp.mjs`.

**Proof.** `bridge.download.integration` (integration, M3, `[area:bridge]`) runs over a scratch `IRIDIUM_TOOLS_DIR` holding a stub `iridium-mcp.mjs` whose banner carries the server's version, and covers the three names and their exact headers, including the strong `ETag` equal to the `SHA256SUMS` hash, `Cache-Control: public, max-age=60` and the absence of `immutable` on the versioned name; a matching conditional `GET` answered `304` with no body and a non-matching one answered `200` with the bytes; the `302`; the `SHA256SUMS` line and headers; an empty `404` for every other name, including traversal and encoded-traversal attempts; no route when the variable is unset; and boot refusal with the named code for a missing, empty or non-regular file, for a stub whose banner names another version, and for a stub with no version banner. `infra/docker/runtime-smoke.ts` fetches the three names from the built image and asserts that the hash equals `sha256sum /app/tools/iridium-mcp.mjs` and the versioned name's `ETag`, that the version equals `iridium version --json`, and the mode and owner of `/app/tools`.

The bridge shares the product version, so a server of version X serving the bridge of version X needs no compatibility matrix, but that premise holds only if the served file is checked; a version line in the banner is the cheapest check that needs no child process at boot and makes the operator's directory as safe as the image's. A version-named file is immutable only where something guarantees the name can never carry other bytes; for the bridge nothing does, so a strong `ETag` equal to the SHA-256 ties the cache validator to the published checksum and `max-age=60` bounds any disagreement to the checksum's own lifetime. Rejected: trusting the operator's file unchecked; executing the file at boot to ask its version; a version-named file in the directory in place of the banner check; `FROM --platform=$BUILDPLATFORM base`; a `DESKTOP_UPDATES_DIR` subdirectory; resolving from the server's own `dist`; `@fastify/static` over a directory; per-platform builds; an identical-bytes alias; a no-cache `SHA256SUMS`; warn-and-serve-nothing for a baked file; deferring the download to M5; year-long immutable caching of the version-named file; a `release.yml` refusal of a second hash per version as the only protection.
