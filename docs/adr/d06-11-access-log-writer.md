# D06-11: the access-log writer

Status: accepted; amended 2026-09-25: the writer's bounds are rows and bytes, every producer appends each row exactly once before the response's last byte or at the socket's close, the final flush runs after every admitted request, and each authenticated MCP request writes one row whose action and status come from closed lists; D03-25 is amended with it, and tests read `access_log` only through the flushing reader.

**As accepted.** `AccessLogWriter` batches on the `onResponse` hook: flush at most every 2 s or every 200 rows (the cadence `03-data-model.md` states with the column), bounded queue of 10 000 rows, drop-oldest on overflow with `iridium_access_log_dropped_total` and a throttled warning, flushed during the shutdown drain. The skeleton says the writer is batched but not how it behaves under pressure. Blocking a read or growing memory without bound to protect telemetry would be the wrong trade; denials — the security-relevant subset — are additionally in the tamper-evident audit chain, which is never dropped.

**Amended 2026-09-25.**

- **The writer.** `apps/server/src/audit/access-log-writer.ts` (`AccessLogWriter`: `append(row)`, `flush()`, `close()`), constructed by the audit plugin at boot step 6 from the injected `dbApp` handle, `Clock` and logger, inserts rows with one multi-row `INSERT` on `dbApp` outside any read transaction, at `ACCESS_LOG_FLUSH_INTERVAL_MS` (2 000) or `ACCESS_LOG_FLUSH_ROWS` (200), whichever comes first, on an owned, cancellable timer; one flush is in flight at a time, and a failed batch is retried once, then dropped. The queue has two bounds, `ACCESS_LOG_QUEUE_MAX_ROWS` (10 000) and `ACCESS_LOG_QUEUE_MAX_BYTES` (16 MiB): `append()` truncates `note_ids` to `ACCESS_LOG_MAX_NOTE_IDS` and sets `note_ids_truncated`, serialises the row once into the form the `INSERT` sends, charges the UTF-8 byte length of that form, and drops the oldest rows until both bounds hold, which also keeps every batch far below `max_allowed_packet`. Every lost row increments `iridium_access_log_dropped_total{reason='overflow'|'write_failed'}`, and a warn (`access_log.dropped` or `access_log.write_failed`) fires at most once per 60 s. 03 §12.5's 500 ms/500 rows and 11's 1 s were transcriptions.
- **The append point, exactly once.** Every producer appends each row exactly once, at the earlier of the point just before the response's last byte — REST and OAuth in `onSend`, MCP in `writeWebResponse` immediately before `reply.raw.end()`, and MCP replies sent before the hijack in `onSend` — and `reply.raw`'s `close` event, subscribed once the request is attributable; a shared per-request guard, `appendOnce` in `audit/`, makes the second trigger a no-op. At the first point `latency_ms` is measured to the append and `bytes_out` counts the body including the final chunk — for REST the serialized payload's length or an explicit `Content-Length`, `null` only for a stream without one; at a close before completion the status is the handler's recorded outcome if it set one, else `error`. The REST and OAuth producer is appended by an `onRoute` hook to the end of every logging route's own `onSend` array, so it is the last `onSend` hook of that route and no hook after it can throw; if an earlier `onSend` hook throws, the chain stops before the producer, the error handler's replacement reply re-runs it, and the producer appends the one row with the replacement's status. The producer never throws: a failure to build a row is counted as a drop. MCP responses are hijacked, so `onSend` never runs for them, and a stream the server ends — every 2025-era SSE response, and a listen stream the drain ends — appends at its end, with `latency_ms` and `bytes_out` measured then. Appending before the last byte, rather than at `finish`, keeps the barrier: a flush awaited after a client received its response always sees that row, and `flush()` never waits on an open stream. A stream the client closes has no server-written final byte, so its row is appended in its `close` handler; the writer counts open MCP streams and `streamsClosed()` resolves, event-driven, when the count reaches zero.
- **The flushing reader.** `flush()` is decorated as `app.accessLog.flush()` and serves both the shutdown drain and the tests. `TestAppInstance` gains an optional `accessLog?: {flush(opts?)}`, and the testkit's reader `TestServer.accessLog` flushes before every read: in-process through `app.accessLog.flush()`, in child mode (`NODE_ENV=test`) through `POST /__test__/access-log/flush`, which accepts `{afterStreamsClosed}`, and in container mode, a production image with no test namespace, it refuses with a named error until `stop()`, whose drain closes the streams and flushes the writer. `flush({afterStreamsClosed: true})` is used only by a test that has itself closed every stream it opened. Every test reads `access_log` rows through `srv.accessLog`, once, never with `expect.poll`, and `guards.test-table-access.guard` refuses any spec or support file that reads `access_log` rows outside `packages/testkit/src/db/access-log.ts`; partition and metadata observations stay in `db/inspect.ts` and `db/maintenance-observations.ts`, which gain `holdTableMetadataLock(trx, 'access_log')` and `inspectAccessLogPartitionRows(executor, {userId})`.
- **Shutdown.** Once the drain begins, every non-ops request answers `503 not_ready` (ARCH-06 as amended). The MCP handler closes in `preClose`, ending every open `subscriptions/listen` stream so each appends its row; in-flight requests finish and append theirs; then the `onClose` hooks run in reverse registration order, so the audit plugin's final flush — and the auth plugin's last-used tracker flush (D06-49) — run after the last request finished and before the pools are destroyed, under `closeFlushDeadline` within the one `SHUTDOWN_DRAIN_MS` deadline.
- **MCP rows.** One row per HTTP request on either mount for which `patAuth` or `oauthAuth` produced a principal, whatever happens afterwards; unauthenticated refusals write none. `action` is `mcp.` plus an operation from the closed `MCP_OPERATIONS` list: the six tool names for a `tools/call` naming a registered tool; `tools.list`, `resources.list`, `resources.templates.list`, `resources.read`, `completion.complete`, `initialize`, `server.discover`, `subscriptions.listen`, `ping`; `notifications`; `batch` for a 2025-03-26 JSON-array body (one row, the de-duplicated union of note ids, the first non-`ok` member status in the order `error`, `rate_limited`, `denied`, `not_found`); and `other` for any other method or unknown tool, never the caller's string. The producer reads the call record from `AuthInfo.extra.call` (D06-18 as amended).
- **MCP status** follows what the caller was answered, and each canonical text in `apps/server/src/mcp/errors.ts` declares its status beside its wording (D06-09): `denied` for the server kill switch, a scope refusal and a cursor refusal, which is audited as `mcp.access.denied {reason: 'cursor'}`, so the row agrees with the audit whatever the cause; `not_found` for every not-found-text outcome, including an allowlist, membership or MCP-disabled-vault refusal, as a REST `404` is logged; `rate_limited` for the budget; `error` for an ambiguous path, the deadline, an internal failure, a JSON-RPC protocol error and a socket that closed before an outcome; `ok` otherwise, including a projection-unavailable read and a truncation.
- **Client fields** come through `auth/user-agent.ts`'s `clientIdentityFrom({declared?, userAgent?})`: MCP passes `_meta['io.modelcontextprotocol/clientInfo']` when present, REST passes `X-Iridium-Client` and its version when sent, else the `User-Agent`, and OAuth rows pass the `User-Agent`, whose first RFC 9110 product token gives `client_name` and `client_version` within `CLIENT_IDENTITY_WIDTHS` (D06-23 as amended).
- **Export (M6, recorded now).** The writer accepts `surface='export'` rows from M3. The producer lands with M6's transfer module and writes one row per exported note with the id of the request that queued the job, through a durable method that inserts in batches of `ACCESS_LOG_FLUSH_ROWS` on the job's own connection and resolves after COMMIT, so a large export neither loses its rows nor evicts request rows.

Rejected: a row-count-only bound, about a gigabyte with full id lists; appending at `finish`, which loses the flush barrier; flushing before the last admitted request, which loses rows; logging `denied` for refusals the caller saw as not found.

Verification: `audit.access-log-writer.unit`; `access-log.on-send.unit` (a throwing `onSend` hook registered before the producer yields exactly one row carrying the error reply's status, and the producer is the last `onSend` hook of a route that declares its own); `mcp.web-response.unit` (the JSON, SSE-end and client-close append points); `access-log.integration` (one row per request, including the listen row after the test closes its stream); `guards.test-table-access.guard`; `mcp.error-texts.unit` and `metrics.integration`.
