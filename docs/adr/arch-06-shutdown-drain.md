# ARCH-06: the shutdown drain

Status: accepted (2026-09-11); amended 2026-09-25: every non-ops request answers `503 not_ready` once the drain begins, a first drain phase, `mcp`, ends admitted MCP exchanges and listen streams, and the write-behind buffers take a bounded final flush in `onClose`.

**As accepted.** Shutdown sequence: readiness → `not_ready`; `{t:'closing', reason:'shutdown', graceMs: 2000}` to note connections and immediate close of vault connections; close remaining sockets; drain every `NoteWriter` and `flushPendingStores()`; stop the scheduler (running transfers marked `failed`/`shutdown`, resumable); destroy pools and close DB pools; exit 0, or exit 1 with `persist.drain_timeout` and the affected note ids when `SHUTDOWN_DRAIN_MS` expires (ARCH-22/OPS-16); REST keeps being served during the drain while new `/collab` upgrades and `/mcp` calls get 503 `not_ready`. The truthful-ack protocol (A19) means an un-flushed writer holds acknowledged work only in MySQL, never in memory; the ordering guarantees that no `persisted` message is sent for a transaction that did not commit and that operators can distinguish a clean stop from a truncated one.

**Amended 2026-09-25.**

- **Refusal once the drain begins.** Once `readiness.beginDrain()` runs, every non-ops request — REST, `/collab` upgrades and MCP calls alike — answers `503 not_ready` with `Retry-After: 5` in its path's envelope (D09-30 as amended); there is no `draining` code, and "REST keeps being served during the drain" is corrected accordingly. `beginDrain()` is idempotent and is called from a `preClose` hook as well as by the ordered drain, so a `close()` that does not run the drain (`abandonBoot`, a non-graceful harness stop) refuses work exactly as one that does; Fastify's own closing short-circuit is disabled (`return503OnClosing: false`), so its hard-coded body, which bypasses every hook, is never sent.
- **The order.** `preClose` — `beginDrain` and `closeMounts`; then the drain phases `DRAIN_PHASES = ['mcp', 'jobs', 'collab', 'writers', 'unload', 'resources']` — `mcp`, then `jobs` (stop the scheduler; running transfers marked `failed`/`shutdown`, resumable), `collab` (the `closing` message to note connections, immediate close of vault connections, then the remaining sockets), `writers` (drain every `NoteWriter`), `unload` (`flushPendingStores()` and destroy) and `resources` (destroy worker pools); then `onClose` — the final flushes of the `AccessLogWriter` and the `LastUsedTracker` — and then the pools; exit 0, or exit 1 with `persist.drain_timeout` when `SHUTDOWN_DRAIN_MS` expires.
- **The `mcp` phase.** It runs `closeMounts` as the drain hook `{phase: 'mcp', name: 'mcp.handler'}`, registered from `onReady` as the collaboration plugin registers its hooks; `closeMounts` is idempotent, so whichever of the phase and the `preClose` hook runs first does the work and the other joins it. It sets the scope's closed flag; awaits `handler.close()`, which writes every `subscriptions/listen` stream its complete frame and closes every modern per-request server still in flight; aborts every exchange still registered, an unowned one answered `503 not_ready` and a writer-owned stream ended; and resolves when the registry is empty, each exchange settled, including the `access_log` row a listen stream writes when it closes. A response the drain ended that has not finished `LIMITS.MCP_DEADLINE_GRACE_MS` later has its socket destroyed, so one peer that stops reading cannot hold the drain to `SHUTDOWN_DRAIN_MS`. Neither `closeMounts` path is an `onClose` hook, because Fastify runs `onClose` only after `server.close()` has waited for every in-flight request and an open listen stream never ends on its own, while `preClose` is the hook Fastify documents for streams that would keep `server.close()` waiting.
- **The write-behind flushes.** Each in-process write-behind buffer — the `AccessLogWriter` (D06-11) and the `LastUsedTracker` (D06-49) — takes its final flush in an `onClose` hook of its owning plugin, which Fastify runs after the listener has stopped and every admitted request has completed, and which avvio runs last-registered first, so before boot step 2's pool close. `ShutdownDrain` (`ops/shutdown.ts`), which owns `SHUTDOWN_DRAIN_MS`, records its start on the monotonic clock and exposes `remainingMs(): number | null` — `null` before any drain, as in a direct `app.close()`, otherwise the budget minus the elapsed time, floored at 0 — decorated as `app.drainRemainingMs()`; `shutdownServer`'s watchdog and every close-time bound read that one value. Each close flush runs under one deadline, `closeFlushDeadline` = `min(DB_QUERY_TIMEOUT_MS, remaining − SHUTDOWN_FLUSH_MARGIN_MS)` (`DB_QUERY_TIMEOUT_MS` when no drain is running), where `LIMITS.SHUTDOWN_FLUSH_MARGIN_MS` (1 000) covers the steps after the flushes — the idle-connection pool close and the final log flush — applied to connection acquisition and every statement through a scoped per-operation deadline that `db/query-deadline.ts` gains, clamped to the pool's. A flush with no budget left acquires nothing and issues no statement; one the deadline reaches is cancelled by destroying its connection, so the pool close never waits on it; either way its unconfirmed entries are counted as dropped (`iridium_access_log_dropped_total`, `iridium_token_last_used_dropped_total`) and one `shutdown.flush_abandoned {buffer, dropped}` warning is logged. A statement the server applies after its connection was destroyed is harmless — the last-used write is an idempotent `GREATEST`, and a late access-log insert means only that the counter counted an unconfirmed entry. A close flush never throws, so an informational write cannot turn a clean stop into exit 1.

The MCP exchanges already admitted end before the scheduler stops claiming, because an open listen stream never ends on its own and would otherwise hold `server.close()` to the deadline; a drain-phase flush would miss the requests still being served, so the flushes run in `onClose`, after the last one. The SDK's own close leaves legacy exchanges running, which is why the exchange registry exists. Rejected: serving REST during the drain; a `draining` error code; closing the mounts in `onClose`; a drain-phase final flush; an unbounded close flush.

Verification: `mcp.fail-closed.mcp` (the ended legacy stream and the drain-race answers), `mcp.factory-error.mcp` (the drain-race case), `access-log.integration` (the listen row written as its stream closes), `tokens.last-used.unit` (the close flush passes the computed bound as its statement deadline, an expired bound destroys the connection and counts the entries, and at or below the margin no connection is acquired), `ops.shutdown.unit` (`remainingMs()` is `null` before the drain and falls with the monotonic clock after it), `db.query-deadline.unit` (a scoped deadline shorter than the pool's destroys the connection at the shorter deadline, and a longer one is clamped) and `shutdown.drain.integration` (with a lowered `SHUTDOWN_DRAIN_MS` and the flush's `UPDATE` held behind a row lock, the process exits 0 before the deadline, logs `shutdown.flush_abandoned` with `dropped` 1 and logs no `persist.drain_timeout`); the last three are "(extended)" at M3 (D12-23).
