# D09-10: the server-settings document

Status: accepted (2026-09-11); amended 2026-09-25: the document is an `effective`/`floors`/`stored` envelope versioned by a monotonic validator row, a `PUT` validates only the members it writes, `428` and `409` carry the document read under the lock, every `PUT` installs the snapshot it read, and `GET` serves the installed snapshot.

**As accepted.** `ServerSettings` is exposed as one grouped document with a single `version` (the maximum of the underlying `server_settings` row versions) for `If-Match`, written under one transaction with per-row CAS; a value weaker than its environment floor is `422 validation_failed` with `errors[0].code='below_env_floor'`. Its groups and fields are exactly those of 03-data-model.md §13.1 (that table is the naming authority): the wire carries no flat alias of a settings key, `desktopUpdatePolicy.mode` is the update discriminator, `mcpEnabled` is `{enabled}`, and `requireSecureStorage` lives in `desktopUpdatePolicy` (never in `sessionPolicy`, which has exactly five members). The skeleton makes `/admin/settings` an `If-Match` route but stores settings as independent rows; one document with one validator is the only shape that gives an admin UI a coherent optimistic-concurrency story.

**Amended 2026-09-25.**

- **The wire.** `ServerSettings = z.strictObject({patPolicy, mcpEnabled, oauthPolicy})` of complete groups (AG12; M7 adds its four groups to every schema below). `ServerSettingsStored` has the same three keys, always present, each group's members optional, with no refinement; `ServerSettingsPatch` is `ServerSettingsStored.partial()` refined to name at least one group and is used only as the `PUT` body. `ServerSettingsDocument = z.strictObject({version, effective, floors, stored})`: `effective` is the enforced policy, `floors` the `EnvSchema` baselines (the laxest admissible values), and `stored` only administrator-set members; a group shown as `{}` has every member at its baseline, whether it has no row or a row cleared with `{}`, so a fresh install answers `stored {patPolicy: {}, mcpEnabled: {}, oauthPolicy: {}}` at version 0.
- **`GET` and `PUT`.** `GET` returns `200 ServerSettingsDocument` built from the installed snapshot, `floors()` and `version()` — exactly what this process enforces — with no `SELECT`, and `ETag "<installed version>"`. `PUT` takes `If-Match "<version>"`, step-up and a patch, and returns `200` with the new document and `ETag`. A group present in the body replaces that group's stored values (an omitted member is cleared, `{}` clears the group); groups absent from the body are untouched; the API never deletes a row. Under a tolerated newer schema, `settings/service.ts` merges members unknown to the binary back from the locked row. Errors: `403 step_up_required`; `403 token_scope_insufficient` for a token principal; `409 stale_version` and `428 precondition_required`, both carrying `current`, the document read under the lock; `422 validation_failed` (`below_env_floor`, `exceeds_related_field`, or the strict refusal of an M7 group key or a snake_case member); `503 unavailable` for a missing or regressed validator or an invalid row.
- **Member-level validation.** In each group the body names, a member whose new value differs from its stored value, or that was not stored, is checked against `floors()`; a related pair (`patPolicy.defaultLifetimeDays` ≤ `maxLifetimeDays`, `oauthPolicy.refreshIdleDays` ≤ `refreshAbsoluteDays`) is checked when either member is written and both are stored afterwards. A member re-sent equal to its stored value, a cleared member and every member of an unnamed group are never re-validated and never cause a refusal: `merge.ts` clamps each member to the stricter of floor and stored (D03-28), and `stored` beside `floors` shows an overtaken value so the console can offer to clear it. A `PUT` whose named groups' resulting stored values equal the current ones writes nothing and is a no-op.
- **Version, validator and locking.** A one-statement data migration, `0065_server_settings_version`, inserts `schema_meta 'server_settings_version' = COALESCE(MAX(server_settings.version), 0)` with the idempotent `ON DUPLICATE KEY UPDATE` form of `0049_admin_users_lock`. That value is the document version and `ETag` and only ever grows; the invariant is that it is never below `MAX(server_settings.version)`, because every effective `PUT` writes the same `v+1` into the validator and each row it changes, and the server never re-creates or lowers it, since that could reuse an `ETag`. Rows are serialised by this validator, not by per-row CAS (A13 as amended); a row's `version` records the document version that last changed it. `PUT` runs one `READ COMMITTED` transaction in the order owner-generation fence → the validator row `FOR UPDATE` (a record lock on an existing row, never a gap lock) → every `server_settings` row → `audit_chain_heads` (A46 as amended). An invalid validator rolls back to `503 unavailable` naming the row, the value found or `missing`, the maximum row version, the installed version and the remedy "set the row to a value greater than or equal to both", logging `settings.validator_invalid {reason}`; an invalid row or a key outside 03 §13.1 rolls back to `503 unavailable` naming the key and the remedy "correct or delete the row and increment `schema_meta server_settings_version` in the same transaction", logging `settings.row_invalid`. Otherwise `If-Match` is compared, the named groups validated, each changed group upserted with `version = v+1`, the validator updated to `v+1` asserting one row, and one `admin.settings.changed {key, before, after}` of stored values written per changed group.
- **Install.** Every `PUT` that read a valid snapshot — effective, no-op, `409` or `428` — calls `install(snapshot, version)` after its transaction ends with the complete snapshot it read under the validator lock, including its own writes, so the switch is a next-call property in the writing process even if the database is unreachable after COMMIT (ARCH-10 as amended).

The envelope is the only shape that satisfies 02's "GET reports the effective value and floor", D03-09's "a missing value means the baseline" and a lossless round-trip. A seeded validator row is the codebase's serialisation idiom, and `READ COMMITTED` with a record lock on an existing row avoids the gap-lock deadlock a `FOR UPDATE` scan of an empty table meets. Member-level validation keeps a console that re-sends a whole group, and the kill-switch `PUT`, from being refused over an untouched overtaken member, while never storing a value weaker than the current floor. Rejected: `MAX(row version)`, which does not move on insert, has no empty-table value and regresses on delete; a `FOR UPDATE` scan of `server_settings`; a validator the server re-creates or lowers; re-validating stored members a `PUT` does not change, which would refuse every `PUT`, the kill switch included, after an environment tightening; a response `stored` schema that requires a group, which fails on a fresh install.

Verification: `admin.settings.integration`, `settings-store.contract`, `settings.merge.unit` and `lock-order.integration`.
