# D06-18: `AuthInfo.extra`, the one channel across the Fastify↔SDK boundary

Status: accepted; amended 2026-09-25: the field is `extra`, the `@modelcontextprotocol/server` 2.0.0 name, carrying `{principal, call, rateLimited?, serverDisabled?, deadline, requestId}`; the verifier takes only the mount and derives the resource (D04-26, D04-30 and D06-15 amended the same day).

**As accepted.** `AuthInfo.extra` (spelling amended 2026-09-25) is the only channel across the Fastify↔SDK boundary: `{principal, call: McpCallRecord, rateLimited?, serverDisabled?}`. `chargeRateLimit` writes `rateLimited`, `mcpKillSwitch` writes `serverDisabled` on a `tools/call`, and one tool gate reads both; handlers write the call record through the single helper `recordAccess(ctx, …)` in `mcp/access-log.ts` and the `onResponse` hook reads it back from `request.mcpAuthInfo.extra.call`. `toNodeHandler` forwards nothing but `req.auth`, so a tool handler can reach neither the Fastify request nor the route's state. Both the per-call `access_log` row and the hourly-budget gate need data to cross that boundary; naming one mutable per-request record keeps "every note id returned" in one function and keeps factory rule 2 intact, because the record is created per request and dies with it.

**Amended 2026-09-25.**

- **The field.** It is `AuthInfo.extra`, the member SDK 2.0.0 declares (`extra?: Record<string, unknown>`); the plural spelling would not type-check. It carries `{principal, call: McpCallRecord, rateLimited?, serverDisabled?, deadline, requestId}` and is the only channel tools read. `chargeRateLimit` writes `rateLimited`, `mcpKillSwitch` writes `serverDisabled` on a `tools/call`, `runExchange` writes `deadline`, and the MCP route sets `requestId`, the Fastify request id, before handing the request to the SDK; the tool gate reads all four and the resource gates read `deadline` (D06-09 uses `requestId` in its retry and internal-error texts). `handler.fetch` replaces `toNodeHandler` as the forwarding path and forwards nothing but `authInfo`. The `access_log` producer reads `extra.call` at its append point (D06-11 as amended). `mcp/plugin.ts`'s one `AsyncLocalStorage` (ARCH-11 as amended) is not a second channel: it only attributes the SDK's context-free error reports to their request for logging.
- **The verifier.** `verifyToken(raw, {mount: 'mcp' | 'mcp-connect' | 'rest'})` takes no `resource`. One `TokenVerifier` is constructed with the two canonical resource URIs from `IridiumConfig` — `mcp.resource = <PUBLIC_ORIGIN>/mcp`, derived beside `oauth.resource` from `PUBLIC_ORIGIN` alone, as AG1 derives the issuer and the canonical resource, and printed by the redacted `config check` summary as `MCP_RESOURCE: <value> (derived from PUBLIC_ORIGIN)` beside `OAUTH_RESOURCE` — and derives the resource from the mount: on `/mcp` it fills `AuthInfo.resource` and is never compared; on `/mcp/connect` step 5a compares it with `access_tokens.resource` and it fills `AuthInfo.resource`; the REST reads have none. The mount also fixes the accepted kind (`MOUNT_ACCEPTED_KIND`) and the principal's `surface` (`rest` for the ★ REST reads, `mcp` for both mounts). The two SDK verifier instances are `makeVerifier('mcp')` and `makeVerifier('mcp-connect')`, differing only in the mount, over one verification path and one symbol. Every printed call site uses the mount form, 04 §6's REST row included (`verifyToken(raw, {mount: 'rest'})`). This is the same day's D04-26 amendment (the option bag is the mount and nothing else) and supersedes the "differing only in the resource they are constructed with" of A31, D04-30 and D06-15.

The installed SDK and the landed verifier are authoritative for an external type and for M1 code. The mount carries strictly more information than `surface`, and deriving the resource inside the verifier makes an audience mismatch impossible to construct and removes the plugin's duplicated URI derivation. Rejected: a caller-supplied `resource` guarded by an equality assertion.

Verification: `mcp.auth.mcp`, `mcp.verifier.unit`, `oauth.audience.contract` and `access-log.integration`.
