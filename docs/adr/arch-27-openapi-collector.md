# ARCH-27: the documentation routes and the OpenAPI collector

Status: accepted (2026-09-11); amended 2026-09-25: `app.ts` registers the collector exactly once, in every boot, immediately before boot step 7.

**As accepted.** The documentation surfaces are ordinary Iridium-registered routes, not plugin defaults: `GET /openapi.json` (operationId `meta.openapi`) and `GET /docs` (`meta.docs`) are registered by the `rest` plugin with an explicit `config.auth = {serverAdmin: true}` (any principal when `NODE_ENV=development`), `Cache-Control: no-store`, and Swagger UI's "try it out" disabled outside development; they are part of the M1 route set and of the `openapi.contract` coverage list like every other operation. The route-policy boot assertion refuses to boot on a route without `config.auth`, and `openapi.coverage.contract` fails on a documented `(operationId, status)` pair that no test exercises — so a documentation route that nobody registers deliberately is either a boot failure or a red coverage job, never a harmless omission.

**Amended 2026-09-25.**

- **One registration.** The collector itself — `@fastify/swagger`'s `onRoute` hook, `applyOpenApiPlugin` — moves out of `applyRestPlugin`. `app.ts` calls it exactly once, unconditionally, immediately before the `7. oauth` region, the first route-registering step, in every boot including `MCP_OAUTH_ENABLED=false`, because the hook documents only routes registered after it. `buildApp` is the only construction site (invariant 1) and this is the only registration, so the `if (!hasOpenApi(app))` guard and the fallback registration in `scripts/export-openapi.ts` are dead code and are deleted; `apps/server/src/index.ts` stops re-exporting `applyOpenApiPlugin`, `hasOpenApi` and `openApiDocument`, which becomes module-private. The `rest` plugin registers `GET /openapi.json` and `GET /docs` over the collector as before.
- **What is documented.** Every route that boot steps 7–12 register is documented unless it declares `schema.hide`, and the hidden ones are absent by decision: `/collab`, the Swagger UI bundle, the four `OAUTH_ABSENT_ROUTES` and `/desktop/tools/*`. The export runs with `MCP_OAUTH_ENABLED` at its default, so `openapi.json` carries every `/oauth/*` operation, `POST /oauth/register` included, and the four `200` metadata operations; `scripts/export-openapi.ts`'s undocumented-routes message names the hidden surfaces.
- **Boot steps.** Every boot-step reference in `apps/server/src` and `apps/server/test` follows 02's twelve steps: 3 security; 4 auth, 5 authz, 6 audit; 7 oauth; 8 rest, 9 collab, 10 mcp; 11 ops, 12 jobs. Step 7 always constructs `app.oauth.grants`, the consent-grant service the `rest` routes consume whatever the flag says, so grants issued while `MCP_OAUTH_ENABLED` was true stay listable and revocable after it is turned off; the flag gates only the `/oauth/*` routes, the four `200` metadata routes and the `ConsentRequestStore`, held in the union `app.oauth.surface`.

The placement is this amendment's own decision: A5 never placed the collector, and its plugin order gains the oauth step through AG1 (A5 as marked). The collector cannot stay in the `rest` plugin, which now runs after step 7 has registered the OAuth routes, and the export script's fallback is dead code once `buildApp` always registers it.

Verification: `openapi.contract` (the documented operations are the registered ones minus the hidden ones), `rest.route-index.contract` (each `oauth.metadata.absent.*` row is registered and none is documented), `app.boot-modes.integration` (invariant 1's mode parity) and `oauth.disabled-mode.integration` (with the flag false, `/me/connector-setup` answers `200` with `oauthEnabled: false`, a grant issued earlier is still revoked through `DELETE /me/oauth-consents/:id`, and the `/oauth/*`, `/mcp/connect` and four `200` metadata paths answer `404` with the routing branch's bytes).
