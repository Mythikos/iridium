# OPS-24: the readiness checklist and the server-settings check

Status: accepted; amended 2026-09-25: M3 adds the fail-closed `server_settings` check, the seventeenth.

**As accepted.** The readiness checklist adds `mysql_version` (OPS-62), `grants`, `key_versions`, `projection_workers`, `tls_cert` and `access_log_partitions` (03 D03-03 / I-20) to the skeleton's set — sixteen checks, the set `ReadyzCheckName` in 09-api-reference.md enumerates — and `clock_skew` warns at 5 s and fails at 30 s. While a fail-closed check fails (or migrations are pending, or the drain has started) every route outside `/healthz`, `/readyz` and `/metrics` answers `503 not_ready` with `Retry-After: 5`, never `server_error` or `unavailable`: one code for "up but not serving". Each added check corresponds to a failure that is otherwise discovered by a user: an unverifiable audit chain, users unable to log in, a dead worker pool, an expired certificate, or TTL and ticket logic silently misbehaving.

**Amended 2026-09-25.**

- **The check.** `server_settings` is appended after `access_log_partitions`, making seventeen checks, and `FAIL_CLOSED_CHECKS` is `migrations`, `collab_owner_lease` and `server_settings`. The check performs the settings store's first load once `migrations` records `current`, or a tolerated `newer_schema`; boot step 2 only constructs the store (ARCH-10 as amended).
- **Before the first load** the check fails with a named detail — waiting for the database, waiting for migrations, a newer schema not tolerated, a redacted load failure, a missing or regressed `schema_meta 'server_settings_version'` validator with its remedy, or an invalid row with its key and remedy — and `SettingsStore.effective()` throws `SettingsNotLoadedError`, so every non-ops route answers `503 not_ready` and no fabricated policy is observable. In database mode `none` the store loads the empty set at version 0 and the check reports `ok`.
- **The load.** `load()` reads the validator row and every `server_settings` row inside one read-only consistent-snapshot transaction under the serving SQL deadline, so a load never pairs rows with a validator from a different commit. It is strict when the migration status is `current`; under a `newer_schema` that `IRIDIUM_ALLOW_NEWER_SCHEMA` tolerates it ignores groups the binary does not know, strips members it does not know from known groups, validates every known member strictly and logs `settings.newer_schema_tolerated` once per process with the ignored keys, and a `PUT` from such a binary merges the unknown members of a named group back from the row read under the validator lock (ARCH-31). Keys 03 §13.1 lists that the M3 binary does not carry — the M7 groups and the reserved `smtp` key — are ignored with one warning in both modes. The first evaluation runs before the process leaves `starting`, the readiness gate precedes authentication at boot step 3, the job scheduler starts only on the ready transition, and the CLI, which builds the same app, observes the same first load at `onReady`; no boot step reads the store.
- **After the first load** each evaluation re-reads the validator by primary key and reloads when it has advanced, so a `PUT` on any process is enforced by every other process on the schema within one `READINESS_RECHECK_MS`, a rolling-restart successor included; a direct `UPDATE` of `server_settings` is invisible until the validator is incremented. A failed refresh keeps the installed snapshot and reports `warn`, naming the version enforced and the failure; an invalid row found after load reports `warn` and logs `settings.row_invalid`. The check never fails after the first load, and the process never exits over settings rows.
- **Operations.** 11's readiness table, its detail vocabulary and the `/readyz`-failing runbook name the check and each detail's remedy; `settings.row_invalid`, `settings.validator_invalid` and `settings.newer_schema_tolerated` are named events.

Settings rows are database state, so a bad row yields `not_ready` before the first load and a warning after it, never a crash, and the fail-closed position after `collab_owner_lease` is what lets a rolling-restart successor enforce every `PUT` its predecessor committed from its first admitted request (ARCH-10). Rejected: a `settings` check placed immediately after `collab_owner_lease`, which renumbers existing checks; fail-closed default values installed before the first load; a check that never warns.

Verification: `readyz.integration`, `ops.readiness.unit`, `admin.settings.integration` and `settings-store.contract` (an unloaded store throws, database mode `none` reports `ok`, a failed refresh warns).
