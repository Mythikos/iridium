# D03-26: OAuth code-replay provenance and first-detection stamps

Status: accepted 2026-09-25.

**Schema.** Migration `0060_oauth_codes_access_token` is one `ALTER TABLE oauth_authorization_codes` statement adding `access_token_id BINARY(16) NULL`, `replay_detected_at DATETIME(6) NULL` and `CONSTRAINT fk_oauth_codes_token FOREIGN KEY (access_token_id) REFERENCES access_tokens(id)`. It names no `ALGORITHM`: MySQL cannot add a foreign key with `ALGORITHM=INSTANT`, and the table holds no row on any deployment before M3, so the default algorithm is correct, which `migrations.parity.integration` proves on both required images. Migration `0064_oauth_refresh_reuse_stamp`, after the client-retirement migrations `0061`–`0063` (D03-27), adds `oauth_refresh_tokens.reuse_detected_at DATETIME(6) NULL, ALGORITHM=INSTANT` in a file of its own, because 03 §14.1 allows one DDL statement per file. Neither needs a grants companion: `iridium_app` already holds table-level `SELECT`, `INSERT`, `UPDATE` and `DELETE` on both tables. The `RESTRICT` on `fk_oauth_codes_token` never fires, because `access_tokens` rows are never deleted and a code row is swept 24 h after it expires.

**One meaning per column.** `access_tokens.refresh_id` is the refresh row issued in the same token response as the access token: at code exchange the family's first row, at refresh the newly inserted rotated row, and `NULL` for a PAT and for a client whose `grant_types` exclude `refresh_token`. Family membership, RFC 7009 revocation and reuse detection read it unchanged, and a refresh row's access tokens are those "issued with" it (D03-24's wording). `consumed_at` is set by exactly one statement, the `UPDATE` of a successful exchange, which sets `consumed_at` and `access_token_id` together after the access token and the first refresh row have been inserted in the same transaction; no failed validation, error branch or replay branch writes it.

**The `authorization_code` grant.** Before the transaction, on plain reads: the client authenticates (D04-36), its presented `client_id` resolved by `WHERE live_client_id = ?` (D03-27), so a retired client does not resolve and answers `401 invalid_client` while a disabled one resolves and fails the status check under the lock; the `code` parses as kind `oac` and its row is read by `code_id` (an absent row still pays one constant-time comparison against a fixed digest and answers `400 invalid_grant`); and `timingSafeEqual(secret_hash, SHA-256(secret43))` holds, a mismatch answering `400 invalid_grant` with nothing written, revoked or audited and one pino line. Then one transaction locks in the credential order of A46 (amended 2026-09-25) — the owner-generation fence, the consent's selected `vaults` rows `FOR SHARE` in ascending id, the owner's `users` row `FOR SHARE`, the client row `FOR SHARE`, the consent row `FOR SHARE` followed by a locking re-read of its vault selection (a changed set restarts under ARCH-24's bounded retry), and the code row `FOR UPDATE` — and under those locks checks `consumed_at IS NULL` first, taking the replay branch otherwise, so a replay is detected whichever client presents it. It then checks, the first failure answering `400 invalid_grant`: the code's `client_id` is the authenticated client; `expires_at > now`; the client is `active`; `redirect_uri` is byte-equal; PKCE `S256` passes; `resource` is equal; the authorizing session, the consent and the owner are live. A client mismatch is checked first, so it is always observed; it leaves the code unconsumed and redeemable by its own client, writes and audits nothing, logs one warn line `oauth.code.client_mismatch {clientId, codeClientId, codeId}` and increments `iridium_oauth_code_client_mismatch_total`. On success the transaction inserts the first refresh row when the client is refresh-capable, then the access token with `refresh_id` set and its `access_token_vaults` rows, then sets `consumed_at` and `access_token_id`.

**The replay branch**, still under those locks, reads the access token named by `access_token_id`; when its `refresh_id` is not `NULL` it locks and revokes every live row of that refresh family; it then locks and revokes every live access token of the code's consent whose id is `access_token_id` or whose `refresh_id` is in the family, all with `revoke_reason='code_replayed'`, and touches nothing else under the consent. It then runs `UPDATE oauth_authorization_codes SET replay_detected_at = :now WHERE id = :id AND replay_detected_at IS NULL` on the row it already holds `FOR UPDATE`, so exactly one transaction across all processes sees the `NULL`→now transition, and that transaction alone writes the chained `oauth.code.replayed {clientId, codeId, accessTokensRevoked, refreshTokensRevoked}` (zero counts included) with target `oauth_consent`, attributed to the presented code row (D04-35). Every detection writes the pino error line `oauth.code.replayed {clientId, codeId, firstDetection, accessTokensRevoked, refreshTokensRevoked}` and increments `iridium_oauth_code_replay_total`, commits, publishes one `AuthzBus` `token.revoked` per revoked access token and answers `400 invalid_grant`. A replay after the consent was revoked or the client disabled is therefore chained once with zero counts, and every later replay during the row's 24-hour life is logged and counted only.

**The `refresh_token` grant** has the same shape: client authentication, the presented `ort` read by id and its secret compared before the transaction (a mismatch is `400 invalid_grant` with nothing written); then the credential lock order with the presented row and the family's rows `FOR UPDATE`. The presented row is classified in order. Reuse is `rotated_at IS NOT NULL`, or `revoked_at IS NOT NULL AND revoke_reason IN REUSE_SIGNAL_REVOKE_REASONS` (`'refresh_reuse'`, `'code_replayed'`, a family already revoked as a theft response): it revokes every live row of the family and every live access token issued with it with `revoke_reason='refresh_reuse'`, stamps `reuse_detected_at` by the same `NULL`→now statement, writes the chained `oauth.refresh.reuse_detected {clientId, familyId, accessTokensRevoked, refreshTokensRevoked}` if and only if it made that transition, logs the pino error line with `firstDetection`, increments `iridium_oauth_refresh_reuse_total`, publishes `token.revoked` per revoked access token and answers `400 invalid_grant` (D06-29 as amended). A row revoked for any other reason is not reuse: it answers `400 invalid_grant` with no stamp, revocation, audit row or reuse count, and one warn line `oauth.token.denied {reason: 'refresh_revoked', grantType: 'refresh_token', clientId, revokeReason}`; it does not touch `iridium_token_auth_failures_total`, which counts `401 invalid_token` at a bearer surface. Otherwise the expiry, client-status, consent and owner checks run, then rotation.

**Contracts and invariant.** `REUSE_SIGNAL_REVOKE_REASONS = ['refresh_reuse', 'code_replayed'] as const` lives in `packages/contracts/src/tokens.ts` beside `REFRESH_TOKEN_REVOKE_REASONS`, whose subset it is by a compile-time check; `auth/oauth/refresh.ts`'s classification and `iridium doctor` read that one definition. Invariant I-27, OAuth grant-credential provenance, has three clauses: `consumed_at IS NOT NULL` if and only if `access_token_id IS NOT NULL`, and the referenced token has kind `oauth` and the code's `user_id`, `client_id` and `consent_id`; `replay_detected_at IS NOT NULL` implies `consumed_at IS NOT NULL`; and `oauth_refresh_tokens.reuse_detected_at IS NOT NULL` implies `rotated_at IS NOT NULL OR revoke_reason IN REUSE_SIGNAL_REVOKE_REASONS`. Its primary layer is protocol; `iridium doctor --credentials`, which the default `doctor` run also executes, checks it with I-21 and I-24–I-26 and I-28–I-29, and the repair is reported. 03 §4's no-FK paragraph names code replay (code → access token → refresh row → family) as the second reader of `refresh_id`, which cannot dangle because a code row is swept 24 h after its 60 s expiry and a refresh row no earlier than 30 days after revocation or absolute expiry. The phrase "every token minted from it" in 04 T18, 11 C51, 06's threat table and AG1 means exactly this set.

OAuth 2.1 §4.1.3 asks for exactly the tokens issued on the basis of the code, and one provenance column reaches them all; checking the secret before `consumed_at` keeps the replay defence from becoming a revocation oracle. A durable first-detection column on the presented credential row bounds the chain at one row per issued code and one per issued refresh row across processes and restarts, while the pino line and the counters keep the full volume. RFC 9700 §4.14.2 defines the theft signal as presenting a token invalidated by rotation; a row revoked by a person, an administrator, the client or a cascade carries no theft information, so it is an ordinary refusal. The code stays redeemable by its own client after a mismatch, because burning it would let any holder of an intercepted code cancel a legitimate authorization. Rejected: revoking the whole consent; a `family_id` copy; burning codes on failure; bounding by effect; an in-process window; chaining client mismatches; treating every revoked refresh row as reuse; counting token-endpoint refusals in `iridium_token_auth_failures_total`.

Verification: `oauth.authorization-code.integration`, `oauth.refresh-rotation.integration` and `migrations.parity.integration`; I-27 through `iridium doctor --credentials`.
