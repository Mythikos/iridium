# D10-43: the real-client matrix lane

Status: accepted 2026-09-25.

The real-client matrix is three specs in `apps/e2e/mcp-clients` — `clients.static-header.mcp`, `clients.oauth.mcp` and `clients.coexistence.mcp`, tagged `[area:clients]`, at `apps/e2e/mcp-clients/<name>.spec.ts` — joined from M8 by `proxied-stack.headers.mcp` at `apps/e2e/mcp-clients/proxied-stack.headers.mcp.spec.ts`. All four are selected by a dedicated, nightly-only Vitest project, `mcp-clients`: include `apps/e2e/mcp-clients/**/*.mcp.spec.ts`, `fileParallelism: false`, rows sequential within a file, long test and hook timeouts, and the MySQL global setup and worker-schema setup of the `mcp` project. No `ci.yml` job runs the project; `nightly.yml` runs `--project mcp-clients`, advisory from M3 to M7 (D12-21). The four inventory rows in `10-testing-and-quality.md` state their file and project explicitly, overriding the L8 location convention.

**Transport.** Every server the matrix drives serves `PUBLIC_ORIGIN` over the product's in-process TLS profile with a per-run CA (AG10). In container mode that is the image at `NODE_ENV=production`; the CIMD row of `clients.oauth.mcp` runs in-process through `buildApp`'s `cimdTransport` seam (D06-44), outside the coexistence container, until its production row joins at M8. Every client process trusts the CA through `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE` and `CURL_CA_BUNDLE`, and nothing disables verification. OAuth-audience clients connect directly to the TLS origin, because the Protected Resource Metadata's `resource` must equal the URL they were configured with.

**Snippets.** Each row drives the snippet the server renders for its client (`GET /me/tokens/:tokenId/snippets`, `GET /me/connector-setup`), never a hand-written command, applying exactly the client UI's substitutions — `{{IRIDIUM_MCP_TOKEN}}` and `<bridge-path>` — and changing only the origin of static-header rows. `mcp.snippets.unit` asserts that route-rendered token templates carry no placeholder other than those two and that connector templates carry none, so the substitution list is complete by test. Third-party clients resolve from the clients directory the nightly job installs outside the checkout (`IRIDIUM_TEST_MCP_CLIENTS_DIR`, AG11), and rendered `npx` forms run offline against it. Trust comes from the environment, so the bridge runs without `--allow-insecure-http`, as users run it.

**Attribution.** Each static-header client reaches the server through its own harness-owned TLS recording listener on a loopback port, which terminates TLS with the per-run leaf, records every request line, re-originates TLS to the server verifying the per-run CA, and forwards bytes unmodified and unbuffered except for `Host`, which it rewrites to the public host derived from `PUBLIC_ORIGIN`, as the reference proxies do. A request is attributed to the listener that received it.

**Assertions.** A discovery request is any request whose path contains `/.well-known/` anywhere. Each static-header listener sees no discovery request and no request outside its client's configured paths. `clients.coexistence.mcp`, against one matrix container, runs the static-header rows, the scripted dynamic-registration client, `claude mcp login` and `mcp-remote` in OAuth mode, joined from M8 by the production CIMD row, and asserts three things: no listener saw a discovery, `/oauth/` or unconfigured request; every OAuth client read the note with its own access token and no `/mcp` request reached the server beyond those the listeners forwarded; and every direct discovery request was answered `200` at one of the four metadata routes or `404`, the four registered `404` paths answered only `404`, and any other `404` is tolerated and listed in the run summary.

**Budgets.** Every row reaches the server from one source address, so the IP-keyed and session-keyed `LIMITS` budgets are shared and cannot be raised in production mode. The harness reuses one sign-in per run, starts a fresh container for each OAuth-bearing spec, checks its row plan against the `LIMITS` budgets before running, and reports any `429` in the server log as a harness budget breach naming its bucket and the request that hit it, never as a client failure. An unprovisioned prerequisite is a named skip, which fails the gate from M8.

A dedicated project is the only selection that keeps nightly-only, client-installing specs out of the pull-request lanes while still giving them a real include. Real TLS is the only transport in which the OAuth rows run at all, and trusting the CA through the environment exercises each client's real certificate handling. Attributing a request by the listener that received it is certain, where time windows and path shapes are inferences. Defining discovery by `/.well-known/` anywhere in the path is required because one metadata route, the appended OIDC form, begins with `/oauth/`. Rejected: adding the specs to the `mcp` or `contract` projects; a job-level `if: false` until M8; User-Agent, time-window or path-shape attribution; routing OAuth clients through listeners; plain-HTTP container rows or listeners; failing a run on a tolerated `404` probe; a `/.well-known/` prefix filter; a test-only override of the `LIMITS` budgets; one shared container for both OAuth-bearing specs; attributing a `429` to the client that received it.
