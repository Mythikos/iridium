# D04-19: revoke-all, and one chained row per bulk revocation

Status: accepted; amended 2026-09-25: every revoke-all and every other bulk revocation writes exactly one chained event whose capped `targets` list the revoked consents and access tokens; the per-token and per-consent rows are withdrawn; every revoke-all selects live credentials only and revokes each grant whole, `POST /me/tokens/revoke-all` answers `{count, consentsRevoked}`, and verification is split by surface.

**As accepted.** `POST /me/tokens/revoke-all` exists alongside the admin route, offered in the settings UI next to a password change. Contract: `auth: {self: true, stepUp: true}`, request `{}` → `200 {count: int}` (`0` when nothing was live; idempotent), setting `revoked_at = now`, `revoked_by = the caller` and `revoke_reason = 'revoke_all_self'` on every live token of the caller — a value distinct from the admin path's `'revoke_all_user'`, so a user's own action stays forensically distinguishable from an administrator's; one audit `token.revoked_all {scope:'user', user_id, count}` with the affected token ids in `targets`, plus a per-token `token.revoked {reason:'revoke_all_self'}` row; after COMMIT one `token.revoked` `AuthzBus` event per token. Errors: `403 step_up_required`; a PAT principal is refused (`403 token_scope_insufficient`). The operation id is `me.tokens.revokeAll`, and the service function is the shared `revokeAll({userId, actor: 'self' | 'admin' | 'cli'})`. G1 widens what the one action covers without changing its shape: the same call revokes the caller's OAuth access tokens, refresh tokens and consents as well, `{count}` still counts access tokens, and the response gains `{consentsRevoked}`. A user who suspects compromise needs one action that stops every agent they configured, without an administrator.

**Amended 2026-09-25.**

- **One row per bulk operation.** Every bulk operation writes exactly one chained row: the three REST revoke-alls (`POST /me/tokens/revoke-all`, `POST /admin/users/:userId/revoke-tokens`, `POST /admin/tokens/revoke-all`), `iridium tokens revoke-all` at every scope, the client cascades and user deletion, whose rows are `token.revoked_all`, `oauth.client.disabled|deleted` and `admin.user.deleted`. Its `targets` list the revoked consents (`oauth_consent`) and then the revoked access tokens (`token`), each group in id order, capped at `AUDIT_TARGETS_MAX` (1 000) with the writer's reserved `targets_truncated` marker, and its metadata carries the totals. No bulk operation writes a per-token `token.revoked` or a per-consent `oauth.consent.revoked`; this also withdraws the per-consent rows of a client delete, which writes one `oauth.client.deleted` with its consents in `targets` (D06-43).
- **The `token.revoked_all` shape** is `{scope: 'user' | 'vault' | 'server', userId?, vaultId?, count, consentsRevoked, note?}` (D04-35). `scope` is `vault` for `--vault` without `--user`, and `user` with both `userId` and `vaultId` when both flags are given. `POST /admin/tokens/revoke-all {userId?, reason?}` writes `revoke_all_user` with `userId` and `revoke_all_server` without it; an administrator's free text is `metadata.note`, at most `ADMIN_NOTE_MAX_CHARS` (120), because the row's `reason` column carries the operation's `revoke_reason`.
- **Unchanged per credential.** Every revoked row keeps its operation's `revoke_reason` (`revoke_all_self`, `revoke_all_user`, `revoke_all_server`, `cli`, …), and `AuthzBus` still publishes one `token.revoked` per access token after COMMIT. A single revocation still writes one row — `token.revoked` for `DELETE /me/tokens/:tokenId`, `DELETE /admin/tokens/:tokenId` and `iridium tokens revoke --id`, `oauth.consent.revoked` for a consent route — and `iridium oauth consents revoke` writes one `oauth.consent.revoked` per consent it revokes, its selection being at most one user's live consents, one per client.
- **Selection and response.** Every revoke-all selects live credentials only (`active` or `rotated`, D06-50), revokes each OAuth grant whole — the consent, its refresh family and its access tokens, because revoking only the access token is undone at the next refresh — and writes its path's `revoke_reason` on every consent and access token it revokes; its metadata is camelCase (`userId`, never `user_id`, D04-35). `POST /me/tokens/revoke-all` answers `{count, consentsRevoked}`, `count` counting access tokens of both kinds; `POST /admin/tokens/revoke-all` and `POST /admin/users/:userId/revoke-tokens` answer `{revoked}` (D06-02 as amended).
- **The CLI selection.** `iridium tokens revoke-all --vault <id>` selects every live access token whose effective vault set includes the vault (an `access_token_vaults` row, or `all_vaults` with a live explicit membership of the owner) and every live consent selected the same way, with its refresh rows and access tokens; `--user` narrows the selection. The transaction follows the credential lock order of A46 (amended 2026-09-25), the selected vaults taken `FOR SHARE`, and the audit head last.

Per-item rows for a bulk operation contradict 03 §12.2's constant bound and the shape the M1 CLI and `session.revoked_all` have written since v0.1.0; one row per operation bounds chained writes, and the hold on the server chain head, per operation rather than per credential. Rejected: per-token and per-consent chained rows for bulk operations; an `access_token` target type beside the deployed `token`.

Verification is split by surface. `tokens.self-revoke-all.integration` asserts the REST contract: two live PATs give `200 {count: 2, consentsRevoked: 0}` and one `token.revoked_all {scope: 'user', userId, count: 2, consentsRevoked: 0}` with both ids in `targets` and no `token.revoked` rows; each token's next ★ REST call (`GET /api/v1/auth/me`) answers `401 unauthenticated` through the same `verifyToken` row read the mounts use; a second call gives `200 {count: 0, consentsRevoked: 0}`; a token principal is refused `403 token_scope_insufficient`, and a caller without step-up `403 step_up_required`. The agent-visible consequence is asserted by `mcp.revocation.mcp` for PATs and by `oauth.revocation.mcp` for grants, the latter including the response for a caller holding one PAT and one grant (`count` 2, counting both access tokens, `consentsRevoked` 1, one `token.revoked_all` with the consent in `targets`, and the next refresh refused). `cli.audit-coverage.integration` asserts one row per revoke-all, and one `token.revoked {reason: 'cli'}` for `tokens revoke --id`.
