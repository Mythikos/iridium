# D06-13: the `iridium-mcp` CLI contract

Status: accepted; amended 2026-09-25: `--vault` is removed, token-file permissions are checked at every read, mid-session refusals are handled per credential, the bridge sends no client-version header, and its timings are `LIMITS` members. A36 is superseded in part by this amendment ([0036](./0036-stdio-bridge.md)).

**As accepted.** `iridium-mcp` CLI contract: flags `--server`, `--token-file`, `--vault`, `--allow-insecure-http`, `--log-file`, `--timeout-ms`, `--version`, `--help`; token sources `--token-file` then `IRIDIUM_MCP_TOKEN` and never an argument; a token file group- or world-readable is refused; `--allow-insecure-http` accepted only when the host resolves to loopback; exit codes 0/2/3/4/5 (clean, usage, auth, unreachable, protocol); `429` and per-call failures are `isError` results, not exits; stdout carries protocol frames only and all diagnostics go to stderr; `--vault` is documented as a convenience filter, not a security boundary.

**Amended 2026-09-25.** The flags are `--server` (required), `--token-file`, `--allow-insecure-http` (loopback only), `--log-file`, `--timeout-ms` (default `LIMITS.BRIDGE_UPSTREAM_TIMEOUT_DEFAULT_MS`, 60 000, floor `LIMITS.BRIDGE_UPSTREAM_TIMEOUT_MIN_MS`, 5 000), `--version` and `--help`; any other argument is a usage error. `--vault` is removed, because real scoping is the token's allowlist and filtering would make the proxy rewrite results. The token-file rule is the pure `checkTokenFile(mode, fileUid, euid, platform)`: on POSIX a file with any group or other permission bit (`(mode & 0o077) != 0`), or owned by a uid other than the effective uid, is refused with a message naming the path and `chmod 600`, at startup (exit 2) and at every re-read; Windows performs no mode or owner check, because the POSIX bits there are synthesised, and `--help` and the documentation say so. A `401` or `403` at startup exits 3. After startup, refusals are handled per credential. Each request remembers the credential it was sent with, and the bridge remembers the SHA-256 fingerprint, never the secret, of every credential refused in the process. A refusal of a credential that a re-read has already superseded is retried once with the current credential. A refusal of the current credential triggers at most one re-read of the token file, shared by every concurrent refusal of it; the re-read file is re-checked, and a new `irid_pat_` credential that has never been refused becomes current, with each affected request retried once. Otherwise the bridge latches: it answers every outstanding request with the documented text (the chmod-600 text for a permission failure, the revocation text otherwise; `isError` for `tools/call`, a JSON-RPC error for other methods), sends nothing further, closes the stdio handle after stdout drains and exits 3. Each request is retried at most once, a refused credential is never presented again, and rotation works any number of times in one process. `429`, `503 mcp_disabled` and other per-call failures stay `isError` results or JSON-RPC errors. `serveStdio` from `@modelcontextprotocol/server/stdio` builds a fresh low-level `Server` per factory call over one upstream client with automatic version negotiation. The bridge identifies itself by `User-Agent: iridium-mcp/<version>` and `clientInfo {name: 'iridium-mcp', version}`, and sends neither `X-Iridium-Client` nor `X-Iridium-Client-Version`; a server that supports no protocol era the bridge speaks is a startup protocol error (exit 5) whose message points at the bridge matching the server's version. The bundle is one file that inlines every dependency and ships no sourcemap. Parity is byte-identical per era pair after JSON-RPC id and cursor normalisation. The three bridge timings — `BRIDGE_LIST_REFRESH_MS` (300 000), `BRIDGE_UPSTREAM_TIMEOUT_DEFAULT_MS` and `BRIDGE_UPSTREAM_TIMEOUT_MIN_MS` — are `LIMITS` members owned by `packages/mcp-bridge/src`. The gate that evaluates `X-Iridium-Client-Version` is scoped by A54's amendment of the same date.

A permission rule applied only at startup is not a rule: moving a file from a temporary location is the ordinary way a rotation lands a new token, and a mode set carelessly at that moment is what the rule exists to catch. Keying the re-read on the refused credential rather than on the process removes the undefined "changed" base and the ambiguous "once": a refusal of an already-superseded credential is expected overlap, only a refusal of the current credential can trigger a re-read, single-flight makes parallel refusals cost one read, and the fingerprint set makes "never present a refused credential again" checkable without keeping secrets. Answering every outstanding request before exiting means no host request hangs. Rejected: re-parsing without re-checking; keeping `--vault`; a warn tier for mode `0640`; exiting only at startup; latching alive; answering only the triggering request; a once-per-process re-read; comparing a re-read with the last credential read rather than with the refused one.

Verification: `bridge.parity.contract` (in-process on every pull request, in container mode on release against the release digest with the extracted bundle), `bridge.token-sources.unit`, `limits.policy.unit` and `limits.single-source.guard`.
