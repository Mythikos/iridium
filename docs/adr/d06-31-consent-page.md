# D06-31 and D07-47: the server-rendered consent page

Status: accepted; amended 2026-09-25: the page's CSP is defined once and names the validated redirect origin in `form-action`, a loopback redirect adds a warning line, the page inlines its own stylesheet under the response's style nonce and references nothing under `/app/`, its permission lines are `READ_PERMISSION_LABELS` (D06-40), it is described as a browser surface of the authorization server rather than as quoted in `service_documentation`, and the closing clause of D06-31's rationale is superseded by AG9. AG1's Decision clauses that repeat these facts are marked inline ([0060](./0060-oauth-authorization-server.md)).

**D06-31 as accepted.** The consent screen is a server-rendered page from `apps/server/src/oauth/consent-page.ts`, not a `@iridium/ui` route, and contains no `<script>` element at all. Its rationale: it must work before any application bundle has loaded and without the SPA router; it must carry no application JavaScript under the nonce CSP; the `request_id` must never enter client state or a history entry the SPA manages; and it is an OAuth browser surface quoted in `service_documentation` rather than part of the product's UI. It shares `packages/ui`'s CSS custom properties through a static stylesheet so it does not look foreign. This is a deliberate, bounded deviation from the one-UI-codebase principle, and it is also what lets M3 exit with a flow a real connector can complete rather than waiting for M4.

**D07-47 as accepted.** The OAuth consent screen at `/oauth/consent` is the single, bounded exception to "every user-facing screen is a `@iridium/ui` route": it is server-rendered (D06-31), contains no `<script>` element at all, and reuses `packages/ui`'s design tokens through the static stylesheet `/app/assets/tokens.css` rather than through the application bundle. The exception is enumerated so it cannot grow: no other server-rendered user-facing page exists.

**Amended 2026-09-25.**

- **The consent CSP.** The profile is defined once, in `security/csp.ts`, as `consentCspDirectives(nonce, redirectOrigin)`, and is set on every consent-flow document that contains the form: `GET /oauth/consent`, and every `POST /oauth/consent` response that re-renders the page (a wrong step-up password, the login-limiter A throttle). Its `form-action` is `'self'` plus the ASCII-serialized origin of the validated `redirect_uri`, or `'self' http:` when that origin's host is the IPv6 loopback literal, which CSP host-source cannot express. The HTML error pages of `/oauth/authorize` and `/oauth/consent` keep `form-action 'self'` and contain no form. A browser that implements CSP3 `form-action` on redirects (Chromium, which the desktop shell embeds) checks the containing document's `form-action` on every hop of the form-submission navigation, so the flow completes when the registered `redirect_uri` answers the redirected request itself or redirects onward only within its own origin; an onward cross-origin redirect is refused by the browser and the consent page stays put with a console violation. That constraint on client registrations is stated in 06 "Clients", 09 §2.19.3 and `docs/ops/oauth.md`.
- **The loopback warning.** When the validated `redirect_uri` is a loopback URI (`127.0.0.1`, `[::1]`, `localhost`), the page adds after the return-target line: "This application receives your approval on this computer. Only continue if you started it yourself."
- **Revocation at M3.** A grant is revoked at M3 with `DELETE /me/oauth-consents/:consentId` (step-up) or `iridium oauth consents revoke`; the Settings › Integrations demonstration moves to M4 with the real-connector deliverable (AG9). The page's duration and footer lines keep naming Settings › Integrations, because a person can reach the page only from M4, when the sign-in route exists.
- **Stylesheet.** The page's stylesheet is `apps/server/src/oauth/consent.css`, owned by the oauth module. It is loaded once when the OAuth routes register, from `new URL('consent.css', import.meta.url)`, following the `blocklist.txt` pattern: tsdown's main configuration copies it beside the bundle, so a run from source and the bundle read byte-identical files, and `server.Dockerfile`'s build-stage assertion gains `test -f /prod/server/dist/consent.css`. A missing file fails boot when `MCP_OAUTH_ENABLED` is true. The sheet is emitted inline in a `<style>` element carrying the response's style nonce, which the page's CSP `style-src` carries, and the page references no `/app/` URL; the page is `Cache-Control: no-store`, so an inline sheet costs nothing a cacheable asset would save and needs no extra public route. At M3 `consent.css` uses its own values meeting the contrast rules of 07's accessibility table. From M4, once `@iridium/ui`'s token file exists, a `pnpm gen` step writes the sheet's custom-property block, between generated-region markers, from `packages/ui/src/theme/tokens.css`, drift-checked by `gen.drift.guard`, so the page matches the SPA without an import across the boundary. This supersedes the static-stylesheet clause of both decisions.
- **Permission labels.** The page's six Read-permission lines are `READ_PERMISSION_LABELS` from `packages/contracts/src/permission-labels.ts` (D06-40), a frozen map over `READ_SCOPES` exported through the contracts barrel and declared so that a new read scope without a label does not compile. `consent-page.ts` imports it, and `packages/ui/src/i18n/en.ts` sources its six scope keys from it, so the typed table stays the UI's only string source (A55, D07-17) and the consent page and the token dialog cannot describe one permission two ways.
- **What the page is.** The page is a browser surface of the authorization server rather than part of the workspace. Neither metadata document advertises a documentation URL (the D06-16 amendment of the same date), so the words "quoted in `service_documentation`" are withdrawn from D06-31's rationale; the rationale never depended on them.
- **Superseded by AG9 (2026-09-24).** The closing clause of D06-31's rationale no longer holds: the page needs no SPA, but the sign-in a browser with no session needs is the M4 `/app/login` route, reached only once the served entry document carries the `iridium-sign-in` marker (every M3 build answers the `access_denied` error redirect instead), or the surface G13 chooses; so M3 exits on the scripted OAuth client and the real-connector proof moves to M4 exit. The page remains the surface every connector consents on.

The consent page is the one document in the product where an injected form could send an approval somewhere else, so `form-action` is kept there, naming the single redirect origin; an onward cross-origin redirect is the client's to avoid, since RFC 8252 loopback listeners and the known connector callbacks answer the request themselves. That trade-off is recorded, stated to operators and proven in a browser rather than claimed away: dropping `form-action` removes the defence for every client, origins learnt from a redirect chain are unknowable when the page is rendered, and a meta-refresh completion page changes the `302` contract that clients and the scripted M3 flows rely on.

The exception stays closed: D07-47's enumeration is unchanged, and the page takes only data across the package boundary — the generated token block and the permission labels. A stylesheet under `/app/` exists only where the server serves the web bundle, which an API-only deployment does not, and `packages/ui`'s token file does not exist before M4 while the page is live from M3; `apps/server` cannot import the browser-tagged `@iridium/ui` either. Rejected: `/app/assets/tokens.css` (a web-directory and M4 dependency on a path Vite does not produce); a second public stylesheet route under `/oauth`; importing `@iridium/ui` from the server; hand-copying token values or labels; generating the labels from `en.ts` into the server.

Verification: `oauth.consent-page.integration` (the page contains no `/app/` reference, renders its stylesheet with `IRIDIUM_WEB_DIR` unset, and its permission lines equal `READ_PERMISSION_LABELS`; its `form-action` names exactly `'self'` and the one redirect origin, never a second origin, for https, `127.0.0.1`, `localhost` and `[::1]` redirect URIs); `oauth.connector.e2e` at M4 (in Chromium, a `redirect_uri` that completes itself or redirects within its origin finishes, and one that `302`s to another origin is blocked with the violation on the console); `oauth.permission-labels.unit`; `oauth.metadata.contract` (no documentation fields); `gen.drift.guard` from M4.
